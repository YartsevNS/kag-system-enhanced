Как устроена онтология: уроки и примеры

Учебная страница рядом с редактором онтологии. Она ничего не меняет в базе: только объясняет, как устроена схема TypeDB и почему в ней именно такие типы. Все примеры синтаксиса взяты из нашей рабочей схемы и проверены на TypeDB 3.14.1.

01Онтология — это три слоя

Онтология в TypeDB — не картинка и не список сущностей. Это три уровня, каждый живёт отдельно:

СлойЧто описываетКак создаётсяМеняется когда
Схема (TBox)какие бывают типы, какие у них свойства и связиdefineредко, по решению человека
Данные (ABox)конкретные объекты: этот документ, эта мераinsertпри каждом разборе документа
Правилачто следует из данных: «если A и B, то нарушение»funкогда меняется логика проверки

Путаница, которая случается чаще всего: пытаются «завести новый вид документа» как данные. Если у документа другие свойства и другие связи — это новый тип в схеме. Если те же свойства — это новый объект существующего типа.

Почему в этом продукте схема важнее данных. Данные извлекает модель из текста, и она ошибается. Схема — это рамка, за которую модель не может выйти: если в схеме нет типа penalty, то «штраф» не появится в базе как отдельная сущность, сколько бы раз он ни встретился в тексте. Поэтому сначала договариваются о схеме, потом наполняют.
02Кирпичи схемы: сущность, атрибут, связь, роль
ПонятиеВ TypeQLСмыслПример из нашей схемы
Атрибутattribute code, value string;значение с типом: строка, число, датаcode — код меры защиты
Сущностьentity security_measure, owns code;объект, у которого есть свойствамера защиты
Связьrelation measure_definition, relates core_measure;факт об отношениях между объектами«пункт определяет меру»
Рольrelates core_measure @card(1..1)место в связи, которое занимает сущностьмера в роли определяемой

Три глагола, которые надо запомнить:

  • owns — «сущность имеет атрибут». Пишется у сущности.
  • relates — «в связи есть такая роль». Пишется у связи.
  • plays — «сущность может занимать эту роль». Пишется у сущности.
Связь в TypeDB — не стрелка между двумя объектами «напрямую», а отдельный объект с ролями. Это позволяет одной связью описать и пару, и тройку участников, и добавить связи собственные атрибуты (например, дату вступления в силу).
03Урок: первая сущность

Задача. Нужно хранить нормативные документы: номер, название, вид.

Шаг 1. Объявить атрибуты. Один атрибут — одно значение одного типа. Не надо делать «универсальное поле» на всё сразу.

define
attribute number, value string;
attribute title, value string;
attribute doc_type, value string;

Шаг 2. Объявить сущность и привязать атрибуты.

entity regulatory_document,
  owns number,
  owns title,
  owns doc_type;

Что это даёт. Теперь в базе может появиться объект этого типа, и TypeDB не пропустит атрибут, которого нет у типа: попытка записать «дату» туда, где объявлены только три поля, будет ошибкой схемы, а не тихой потерей данных.

Частая ошибка: назвать сущность во множественном числе или с глаголом (documents, has_measure). Тип отвечает на вопрос «что это», поэтому regulatory_document, а не documents.
04Урок: связь с ролями

Задача. Документ выпущен регулятором. Регулятор и документ — разные сущности, между ними факт.

Шаг 1. Связь с ролями.

relation document_issuance,
  relates issuer @card(1..1),
  relates regulated_item @card(1..1);

Шаг 2. Сущности объявляют, какие роли они могут играть.

entity regulator,
  owns name,
  plays document_issuance:issuer;

entity regulatory_document,
  owns title,
  plays document_issuance:regulated_item;

Как это читается вслух: «есть связь document_issuance; в ней роль issuer, её занимает regulator; роль regulated_item, её занимает regulatory_document».

Зачем роли, если можно просто две ссылки. Роли не дают перепутать стороны: записать регулятора в роли regulated_item TypeDB не позволит, потому что regulator не объявил, что играет эту роль. Это ловит зеркальные ошибки, которых не видно в тексте.

Если забыть plays, связь создастся в схеме, но вставить её с конкретными объектами не получится: ошибка «type does not play role». Сначала plays у сущности, потом вставка.
05Урок: запись данных

Объект. Создаём документ с тремя свойствами.

insert
$d isa regulatory_document,
  has number "57580.2-2018",
  has title "ГОСТ Р 57580.2-2018",
  has doc_type "ГОСТ";

Связь между существующими объектами. Сначала находим объекты запросом, потом вставляем связь с ролями. Так это делает и наш код записи в онтологию:

match
  $r isa regulator, has short_name "ФСТЭК";
  $d isa regulatory_document, has number "57580.2-2018";
insert
  document_issuance (issuer: $r, regulated_item: $d);

Проверка, что записалось.

match
  $d isa regulatory_document, has title $t;
  document_issuance (issuer: $r, regulated_item: $d);

Если запрос вернул строку — связь есть. Если пусто — либо не нашлись объекты по условию (опечатка в номере), либо не выполнено plays.

Правило нашего продукта: ручная вставка в рабочую базу запрещена. Запись делает только конвейер обработки документа или принятие предложения из очереди — так у каждого факта есть источник.
06Урок: вопросы к базе

Запрос в TypeQL — это match с шаблоном. Переменные начинаются с $, условия перечисляются в одном блоке.

Сколько мер защиты в базе.

match $m isa security_measure;
reduce $count = count;

Меры с определённым кодом. Условие по атрибуту: код начинается с «Б.» — меры по обеспечению безопасности.

match
  $m isa security_measure, has code $c;
  $c like "Б.%";

Вывести значения, а не объекты.

match
  $m isa security_measure, has code $c;
  $m has description $dsc;
В TypeDB 3 не работает get $x в конце запроса (это синтаксис второй версии) и не работает match $e isa entity — слово entity зарезервировано. Считать объекты «вообще» нельзя: только по конкретному типу.
07Урок: правило, которое выводит нарушение

Правило в TypeDB 3 — функция, которая возвращает набор объектов. Она не хранит данные, а вычисляет вывод каждый раз по текущему состоянию базы.

Наше правило «несертифицированное СЗИ у объекта КИИ 1 категории»:

fun violated_certification() -> { cii_object, security_requirement }:
    match
      $asset isa cii_object, has cii-category 1;
      $szi isa security_software, has is-certified false;
      asset_protection(protected_system: $asset, deployed_szi: $szi);
      $law isa security_requirement, has requirement-id "ФСТЭК-239-п11.1";
    return { $asset, $law };

Как читать. «Вернуть пары (объект КИИ, требование) такие, что: у объекта категория 1, на нём работает несертифицированное СЗИ, и есть требование с конкретным идентификатором».

Проверка правила — обычный вызов в запросе:

match let $asset, $law in violated_certification();

Почему это сильнее, чем проверка текстом. Правило срабатывает на любых данных, удовлетворяющих условию, и его результат воспроизводим: те же объекты всегда дают тот же вывод. Но у него есть цена — правило выдаёт ровно то, что описано. Если условие записано как «категория 1», объекты категории 2 в вывод не попадут, и это не ошибка базы, а ошибка описания.

Проверка обязательна на тестовых данных. Правило, которое не возвращает ни одной строки, ничего не доказывает: оно может быть верным, а может быть написано мимо. Сначала вставляют три-четыре объекта, один из которых обязан попасть в вывод, и смотрят, что он попал.
08Кардинальность и уникальность
ЗаписьЧто значитПример у нас

owns source-chunk-ids @card(0..)ноль или больше значений: объект встречается в нескольких фрагментахпровенанс

relates protected_system @card(1..1)ровно один объект в ролиСЗИ стоит на одном объекте

Зачем @key. Он превращает повторную вставку в безопасную: наш код записи сначала ищет объект по ent-key, и если нашёл — не создаёт второй, а добавляет провенанс. Без ключа один и тот же ГОСТ после повторной обработки появился бы дважды.

Как строится ent-key. Не случайно и не «как пришло из модели», а из устойчивых признаков типа, затем sha1 и первые 16 символов:

ТипИз чего ключ
regulatorshort_name + name
regulatory_documentnumber + doc_type + title
structural_elementдокумент + индекс пункта + первые 200 символов текста
security_measureкод меры + первые 200 символов описания
Цена ключа. Если признак нестабилен (например, номер документа в тексте записан по-разному), один объект распадётся на два. Если признак слишком общий — два разных объекта склеятся в один. Поэтому ключ выбирают по тому, что в документах действительно постоянно.
09Провенанс: откуда взялся факт

Провенанс — это ответ на вопрос «на каком фрагменте текста основано утверждение». Без него онтология становится набором утверждений без доказательств, и проверить её нельзя.

У нас у каждой сущности есть три поля:

ПолеЧто хранит
source-chunk-idидентификатор фрагмента, из которого извлечён объект. Один.
source-chunk-idsвсе фрагменты, где объект встретился повторно
source-clauseномер пункта, если он есть в тексте

Идентификатор фрагмента совпадает с тем, что лежит в поиске (Qdrant): chunk_id. Поэтому связка «факт в онтологии → текст в поиске» вычисляется, а не ищется заново.

Следствие для доступа. Если пользователь не видит фрагмент, он не должен видеть и факт, выведенный из этого фрагмента. Поэтому факты из онтологии проходят ту же проверку прав, что и текст: считается пересечение видимых фрагментов.
10Наша схема целиком

Два контура, они разделены по смыслу, а не по стилю названий.

Контур корпуса — то, что извлекается из нормативных документов:

ТипЧто этоКлючевые связи
regulatorрегулятор: ФСТЭК, ФСБ, Банк Россиивыпускает документ
regulatory_documentнормативный документвыпущен регулятором; основание требования
structural_elementпункт, подпункт, строка таблицывходит в документ; определяет меру
security_measureмера защиты с кодомопределена пунктом; может быть компенсирующей
cii_objectобъект критической информационной инфраструктурык нему применяется требование
threat_sourceисточник угрозы: класс нарушителя, потенциал—

Контур доказательств — то, по чему проверяется соответствие:

ТипЧто этоКлючевые связи
company_documentвнутренний документ организациизакреплён за объектом
security_requirementтребование с идентификаторомосновано на документе; подтверждается доказательством
evidenceдоказательство выполненияподтверждает требование
security_softwareСЗИ и его сертификациязащищает объект

Девять связей: document_issuance (регулятор → документ), document_hierarchy (документ → пункт → подпункт), measure_definition (пункт → мера), applicability_criteria (требование → объект), compensatory_relation (мера → компенсирующая мера), document_assignment (внутренний документ → объект), asset_protection (СЗИ → объект), requirement_basis (требование → нормативный документ), requirement_evidence (доказательство → требование).

Почему не одна большая схема на всё. Контуры наполняются разными источниками и меняются с разной скоростью: корпус — обработкой нормативных документов, доказательства — загрузкой документов организации. Разделение позволяет видеть, где именно не хватает данных, и не смешивать «что требует закон» с «что сделала организация».
11Восемь ошибок новичка
  1. Хранить сущность как строку. Регулятор записан текстом в поле документа. Тогда нельзя спросить «какие документы выпустил ФСТЭК» — придётся искать по подстроке и ошибаться на «ФСТЭК России». Сущность должна быть сущностью.
  2. Дублировать атрибуты по типам без нужды. Отдельные measure_code, measure_title, measure_desc вместо одного типа с тремя атрибутами. Схема распухает, а запросы становятся одинаковыми в трёх вариантах.
  3. Связь без ролей. Пара «источник — цель» без имён ролей не даёт отличить «документ ссылается на документ» от «документ отменяет документ». Через месяц никто не помнит порядок.
  4. Менять схему без новой версии. Правка define поверх работающей базы без записи «что и зачем» — это потерянное решение. Любая правка схемы фиксируется в ADR с датой.
  5. Правило без тестовых данных. Правило, возвращающее пусто, выглядит рабочим. Проверять только на объектах, которые обязаны попасть в вывод.
  6. Ключ из нестабильного признака. Номер документа, который в разных ГОСТах записан по-разному, даёт два объекта вместо одного. Ключ строится из того, что в текстах постоянно.
  7. Смешение стилей в именах. В одной схеме cii-object и cii_object — это два разных типа. Имена в схеме выбираются один раз и одинаково. Честно про нашу схему: в ней это смешение есть — технические атрибуты провенанса названы через дефис (ent-key, source-chunk-id), остальные через подчёркивание (source_origin, struct_index). Работает, но новые имена пишем через подчёркивание, а существующие не переименовываем без миграции: переименование атрибута — это изменение схемы, а не косметика.
  8. Вера в модель вместо схемы. Модель извлечёт «меру» там, где её нет, и пропустит там, где есть. Схема задаёт рамку, а проверка качества — отдельный шаг: сколько объектов получилось, у скольких заполнен код, у скольких провенанс совпадает с текстом.
12Как добавить новый тип: пошагово

Пример задачи. Нужно хранить стандарты (ГОСТ) отдельно от нормативных документов регуляторов, потому что у них есть номер с годом и область применения.

Шаг 1. Проверить, нужен ли новый тип. Если свойства и связи те же — это объект существующего типа с другим doc_type. Новый тип нужен, когда появляются собственные свойства или собственные роли.

Шаг 2. Записать в ADR. Один абзац: зачем тип, чем отличается, какие связи. Решение фиксируется до кода, а не после.

Шаг 3. Описать схему.

define

attribute standard_year, value string;
attribute scope, value string;

entity standard,
  owns ent-key @key,
  owns number,
  owns title,
  owns standard_year,
  owns scope,
  owns source-chunk-id,
  owns source-chunk-ids @card(0..),
  owns source_origin,
  plays requirement_basis:source_document;

Шаг 4. Проверить схему, не трогая рабочую базу. Через редактор онтологии: сначала «Проверить», потом «Применить». Или на отдельной базе скриптом применения схемы.

Шаг 5. Вставить тестовый объект и один запрос, который его находит. Пока объект не находится запросом, тип не считается добавленным.

Шаг 6. Обновить промпт извлечения. Пока промпт не знает про новый тип, модель его не вернёт, и тип останется пустым. Промпт — авторский текст, правка согласуется с владельцем.

Шаг 7. Записать в журнал архитектуры — дата, что добавили, чем проверили.

Порядок нарушать нельзя: схема → проверка → тестовые данные → промпт → прогон. Если сначала запустить прогон, извлечённое просто некуда записать, и работа пройдёт зря.
13Чек-лист перед применением

Проверять по пунктам, каждый — с ответом «да» или «нет»:

  1. У каждой новой сущности есть @key, и ключ строится из стабильного признака.
  2. У каждой новой сущности, которая извлекается из документа, есть source-chunk-id.
  3. Для каждой связи объявлены роли, и у всех участников есть plays этой роли.
  4. Кардинальность ролей соответствует смыслу: где «ровно один» — @card(1..1), где «может не быть» — @card(0..1).
  5. Новые имена не дублируют существующие с другим регистром или стилем.
  6. Схема применена на отдельной базе и загрузилась без ошибок.
  7. Вставлен тестовый объект, и запрос его находит.
  8. Правило (если добавлено) возвращает объект, который обязан попасть в вывод.
  9. Тестовые объекты удалены из рабочей базы.
  10. Запись в ADR и в журнал архитектуры сделана.
Нельзя применять схему, которая ломает существующие данные. Удаление типа или атрибута, который уже используется, — это миграция, а не правка. Порядок: сначала перестать писать, потом перенести данные, потом удалять тип.
