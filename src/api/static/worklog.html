Журнал работ и архитектура

Открытая страница: состояние системы, что сделано и какими числами подтверждено, целевая архитектура и открытые вопросы. Предназначена для внешнего ревью — можно показывать другой модели или человеку без доступа к стенду.

1. Что это за система

KAG — система, которая читает нормативные документы по информационной безопасности, извлекает из них онтологию (требования, меры, структурные элементы, регуляторов) и пишет её в TypeDB с провенансом до фрагмента документа. Вторая задача — разбор документов пользователя: сопоставление их пунктов с требованиями онтологии и подготовка новых версий документов со ссылками на требования.

3. Что сделано (по датам, с числами)

15.11.2026 — подпункты мер отделены от требований

  • Правило: нет глагола требования (должен/обеспечивает/осуществляется/подлежит) и id вида МЕРА-N-а → это описание подпункта меры, а не требование.
  • Bronze пишет такие строки как сырьё, Silver кладёт их в очередь с причиной measure_subitem_not_requirement, Gold не пишет.
  • Замер (прогон d7308e07): 473 требования в Gold, из них подпунктов мер — 0; очередь 176 записей: word 73, bare 47, subitem 38, identical 12, multiple_parents 2, conflicting_measure_refs 2, orphan_submeasure 1, reference_only 1.
  • Конфликты целостности (2) локализованы: сущности записаны, конфликтующие связи сняты, откатов фрагментов нет.

14.11.2026 — ключи и связи

  • Ключ требования — sha256 от нормализованного текста (номер пункта модель пишет только у 10 строк из 508, поэтому номер стал атрибутом).
  • Ключ меры — нормализованный код: АВЗ.1 = АВЗ-1 = авз 1 → авз.1.
  • Связь «мера реализует требование» с номером пункта на связи (point-in-measure): 400 связей на 399 требований.
  • Ссылки вида МЕРА-N разложены: 395 требований из 503 привязаны к мерам, 108 не ссылаются (проверено на 10 образцах — кода меры в тексте нет).
  • Guard'ы: доля пустых фрагментов выше порога → прогон помечается подозрительным; «тихое обеднение» (1–2 объекта на фрагмент) считается отдельно.
  • Три случая тихой потери данных найдены и закрыты: обрезка ответа по max_tokens, мера-заглушка без обязательного атрибута, отказ транзакции, возвращавшийся как «ok».

14.11.2026 — очередь разбора и её страница

  • Страница /queue (только админ): карточки причин с числами, «показано N из M», фильтры, решение двумя нажатиями, без системных диалогов.
  • Очередь прогона заполняется пересчётом Silver по сохранённому прогону — без вызовов модели.

Спайк структуры (в работе)

  • Тексты требований находятся в документе дословно: 523 из 525 (99,6 %).
  • Рядом с кодом меры (≤1500 знаков): 298 из 525 (57 %), медиана 553, p90 1292.
  • Вывод: структура в документе есть (106 строк таблицы мер + 30 номерных заголовков), но брать её надо парсером таблицы, а не поиском кода регуляркой.

4. Целевая архитектура: ядро, домены, выравнивание

Проблема. Схема — монолит под один домен: тип называется security_requirement, роли связей привязаны к этому типу. Требование из другого домена не может участвовать в тех же связях. Доменов станет больше двух.

Решение (путь A, одна база).

  • Ядро — абстрактные типы без доменных имён: document, clause, requirement, control, version, evidence, связь alignment.
  • Домен — префикс в имени типа: sec_requirement, it_requirement, it_control. Связи и роли префикса не несут.
  • Выравнивание — данные: связь alignment(source, target, kind, confidence), маппинги в YAML. Новый домен приносит свои маппинги, ядро не правится.
  • Единые правила ключей для любого домена: документ — домен:издатель|вид|номер; требование — документ#пункт#порядок; контроль — домен:код. Домен входит в ключ, поэтому коды разных доменов не сталкиваются.

Ограничение платформы: базы TypeDB изолированы — кросс-базовых запросов нет. Поэтому «две онтологии» реализуются как два модуля в одной базе, а не как две базы. Второй вариант (две базы + федеративный слой) дороже и нужен только при требовании физической изоляции.

5. Открытые вопросы для внешнего ревью

  1. Ядро/модули/выравнивание в одной базе — достаточно ли этого для 3–5 доменов, или сразу нужен внешний федеративный слой?
  2. Ключ требования документ#пункт#порядок: порядок внутри пункта стабилен? Что делать с требованием, которое после правки документа «сдвинулось» на другую позицию — новый объект или та же сущность с новой редакцией?
  3. Как оценивать качество извлечения требований: precision/recall требуют ручной разметки. Что считать эталоном на 50 требований и кто размечает?
  4. Выравнивание доменов: кто автор маппингов и как хранить их версии (kind + confidence + автор + дата)?
  5. Контур «документ компании → покрытие → новая версия»: достаточно ли связи coverage(clause, requirement) со статусом, или нужна отдельная сущность «оценка соответствия» с обоснованием и цитатой?

6. Известные ограничения

  • Пункт чанка (clause) заполнен у 39 строк из 516 — контекстная проверка ключа пока невозможна; в очереди 47 «номер без контекста» помечены no_clause_yet.
  • Дисперсия извлечения на одном документе: 487–521 требований при одинаковых условиях; одно число для приёмки не годится, нужен интервал.
  • Схема в промпте не подставляется: плейсхолдер {schema_tbox} остаётся литералом (найдено 15.11.2026, решение не принято).
  • Регулярки и словари пока в Python, а не в YAML — это следующий этап расширяемости.
