пересчитывать одно и то же при каждом разговоре. Источник страницы — `/architecture`
(`src/api/static/architecture.html`); этот файл — её письменный журнал.

одна запись в разделе «Журнал изменений» с датой, что изменилось, где проверено. Если страница
ещё не обновлена, запись помечается `[страница не обновлена]`.

## 2. Контуры данных

### 2.1 Загрузка документа

    nginx → api (upload) → redis (очередь) → worker
    worker: парсинг → OCR (служба 41) → таблицы → чанки 1500/225
            → Qdrant (вектор+BM25 payload)          — поиск
            → Neo4j (сущности/связи)                — граф знаний
            → TypeDB (онтология, ADR-007)           — типизированные факты с провенансом

Write в TypeDB выполняется **отдельным контуром**: не под общим шагом графа, у него свой
выключатель. Причина: на стенде `system/graph.skip=true` («ждём локальную модель»), и раньше
онтология из-за этого молча не наполнялась.

### 2.2 Чат

    вопрос → api → гибридный поиск Qdrant (dense 2560 + BM25 → RRF) → реранкер (41)
           → ACL-фильтр по видимым chunk_id
           → Neo4j: связанные сущности
           → TypeDB: дедуктивные факты (violated_documents и др.), тоже через ACL
           → LLM (gigachat-proxy / внешний провайдер) → ответ + источники

### 2.3 Онтология

    схема TypeQL (schema-v2.tql) → БД cybersecurity_ontology_v2
    правила: violated_documents(), violated_certification()
    наполнение: обработка документов + принятие предложений очереди
    очередь предложений: Postgres (ontology_proposals) → при accepted пишется факт в TypeDB

Терминология (по решению владельца): **контур корпуса** — что извлекается из нормативных
документов (regulator, regulatory_document, structural_element, security_measure,
cii_object, threat_source); **контур доказательств** — требования, документы компании,
СЗИ, доказательства.

## 2026-11-07 — Версии документов регулятора (ADR-008, change `2026-11-07-versii-dokumentov-reguljatora`)

Схема `cybersecurity_ontology_v2` пополнилась: entity `document_version` (ent-key = id файла Postgres),
relations `document_version_of` и `supersedes`, атрибуты `effective_from`, `effective_to`,
`version_status`, `version_hash`, `kag_document_id`, `document_key`, `current_version_string`.
Акт (`regulatory_document` / `company_document`) теперь опознаётся `document_key`, редакция — отдельный объект.

Загрузка через сайт получила `version_string`, `effective_from`, `supersedes_id`; для регулятора версия
и дата обязательны (`VERSION_REQUIRED`). Поиск в Qdrant получает `version_status` и по умолчанию
не отдаёт `superseded` (флаг `include_superseded`). `typedb_facts.outdated_references()` находит
требования из утративших силу редакций с соблюдением ACL по чанку.

Проверено: две редакции тестового акта — 2 `document_version`, 1 `supersedes`, повторная обработка
не плодит версии (`skipped: version exists`), тестовые объекты удалены. Тесты: 7 passed.
Открыто: `current_versions()` не подтверждена, статус старой редакции не переписывается атрибутом
(TypeQL delete-синтаксис), файлы схемы в `project_typedb/adr/` не обновлены. Подробности —
`docs/changes/2026-11-07-versii-dokumentov-reguljatora/result.md`.

## 2026-11-11 — Приказ ФСТЭК № 239: подмена глифов в слое PDF и разбор шапки после OCR

Документ `644de44e-6c49-4cc3-a3a9-2aec53e11d1a` (40 стр.) проходил цикл «успешно», но
данные были испорчены: текстовый слой PDF — подмена глифов («ФСТЭК РОССИИ» как
«$ȿȾȿ ȺɅ0ɇȺ3»), кириллицы 0-1%. Следствия: мусор в векторах (по документу нечего
искать), шапка не разбиралась (вид other, нет номера, издателя, даты), в журнале

Причины (три, все исправлены):

## 2026-11-11 — Очередь возможных дублей: человек решает, что это

Точное совпадение байтов (SHA-256) на стенде работает: 350 документов, у всех хеш,

  статус, кто и когда решил);
- при загрузке: то же обозначение (издатель+вид+номер, через `doc_context`) → кандидат
  `key_match`; для новостей — совпадение нормализованного названия склеивается сразу,
  источник дописывается к существующей записи (очередь не забивается копиями из RSS);

- удаление документа чистит его пары в очереди; при чтении висячие пары (документ

## 2026-11-14 (вечер) — запись в TypeDB по новым ключам: ключ требования по хэшу, связь требование→мера

Доведена до базы та часть плана, которая раньше жила только в Silver. Образы
`kre44et/kag-api:2026.11.14.5` и `kre44et/kag-worker:2026.11.14.5` (собран из `work`),
база для проверки — `cybersecurity_ontology_v17` (новая, схема загружена заново).
Проверка — один документ `fb4d9a84-e723-41fa-970d-2ed75683674d` через воркер (321 фрагмент).

**Что в коде.**
- `typedb_writer._collect`: ключ требования перебивается `sha256` от нормализованного текста
  (значение из ответа модели игнорируется — 14.11 в Bronze пришёл старый «kag:<id>|номер»).
- `typedb_writer._collect`: ключ меры считается от НОРМАЛИЗОВАННОГО кода («АВЗ-1» = «АВЗ.1» =
  «авз 1»). Без этого один код ложился разными объектами: 431 мера вместо 113.
- `link_requirements_to_measures`: код меры из `requirement-id` превращается в связь
  `requirement_definition`; мера ищется в пачке или в базе, и если её нет — объект НЕ выдумывается
  (иначе появлялись 241 «мера» из одних ссылок), ссылка считается как неразрешённая.

**Два дефекта, найденных этим прогоном (оба чинили молчаливую потерю данных).**
1. Мера-заглушка создавалась без обязательного `measure_key` (@key, @card(1..1)) — TypeDB
   отклоняла ВСЮ транзакцию фрагмента (CNT5/DVL8), и требования фрагмента исчезали:
   100 фрагментов из 305.
2. `write_facts` возвращает `{"error": ...}` БЕЗ исключения, а `extract_and_store_typedb`
   в этом случае отвечал `status="ok"` — сводка прогона показывала «ошибок 0» при потерянных
   фрагментах. Теперь отказ записи возвращается как `status="error"` и попадает в журнал онтологии.

## 2026-11-14 (поздний вечер) — guard на подозрительный прогон и разбор замечаний ревью

По разбору внешнего ревью закрыто три пункта из четырёх; четвёртый (развилки схемы) — решение владельца.

1. **Guard «подозрительного прогона».** В `document_service._build_typedb_only` после обработки
   считается доля пустых фрагментов. Если она выше порога (`system/extraction.empty_share_max`,
   по умолчанию 0,30), прогон помечается: `logger.error`, запись в журнал онтологии
   (`error_type="suspect_run"`), в `summary` — `suspect=True` и `empty_share`, в `bronze_runs.note`
   — префикс `suspect: пустых N/M`. Причина: 14.11.2026 прогон с 266 пустыми из 321 (83%) прошёл
   как успех, и это выяснилось только по числу сущностей.
2. **Аудит «отказ глотается как ok».** Просмотрены все места `return {"status": "ok"}` и
   `except: pass` в `typedb_writer.py`: остальные четыре `except: pass` безобидны (чтение флага
   записи, сброс драйвера, payload «без размышлений»), опасный путь (отказ транзакции) уже
   возвращает `status="error"`. Больше мест, где потеря данных выдаётся за успех, не найдено.
3. **Сверка чисел между прогонами** записана в `docs/handoff.md`: 508/495 — прогон `f16b25c3`,
   487/475 — `990fa867`; Silver 479 = 475 текстов + 4 разделённые группы, TypeDB 475 = слияние
   одинаковых текстов. Смена базы объясняется другим прогоном модели, а не фильтрацией.
4. **Открытый вопрос по схеме (решает владелец):** 97 ссылок на меры вида `АВЗ.1.1` не имеют
   объекта меры. Варианты: (A) подпункт — отдельная мера (править извлечение), (B) уточнение
   меры `АВЗ.1` (связь/атрибут, промпт не нужен), (C) ссылка на пункт документа, а не на меру.
   До решения промпт не менять — иначе будем извлекать то, что некуда класть.
