# Поставка и дистрибуция KAG

Стратегический документ. Определяет, КАК продукт попадает к заказчику
(в т.ч. в закрытые сети) и как обновляется. Уровень: продуктовый, не про
конкретные команды эксплуатации (те — в `docs/guides/deploy.md`).

Статус: концепция зафиксирована 2026-09-07.

---

## 1. Принципы

1. **Заказчик ничего не собирает.** Никакого `docker build`,
   `pip install`, компиляции, скачивания весов — на стороне заказчика.
   Все тяжёлые и хрупкие операции выполняются нами заранее.
2. **Образ — артефакт поставки.** Готовый immutable-образ с зашитым кодом и
   зависимостями — штатный способ доставки (как бинарник/инсталлятор),
   а не «обход». Он же закрывает проблему блокировок (GitHub release-assets,
   deb.debian.org, плагины Neo4j, веса OCR) — то, что нельзя надёжно скачать
   в момент установки, фиксируется в образе заранее.
3. **Одна команда.** Установка = запуск инсталлера, который сам делает
   preflight, генерирует секреты, разворачивает стек, ждёт готовности и
   печатает доступы.
4. **Один код — разные артефакты.** Две ветки не нужны. Различия между
   «для профи» и «для новичка», между online и air-gapped — это различия
   в АРТЕФАКТЕ и СПОСОБЕ ДОСТАВКИ, а не в кодовой базе.
   Код один; различаются compose-файлы, набор образов и инсталлер.
5. **Версии фиксированы.** Никаких `latest` в поставке. Тег = версия/дата
   (напр. `2026.09.07`). Воспроизводимость и откат.

## 2. Модели поставки

### M1. Online (обычная сеть с доступом к Docker Hub)
- Инсталлер тянет готовые образы из registry (`docker pull`).
- Публичные образы: `kre44et/kag-api|kag-worker|kag-mcp`, `kre44et/dozerdb`
  + инфраструктурные (postgres, redis, qdrant, keycloak, nginx).
- Самый простой путь. Требует доступа к Docker Hub.

### M2. Offline (закрытый контур, air-gapped) — ОСНОВНОЙ для продажи в организации
- Поставляется **офлайн-бандл**: архив с образами + compose + инсталлер + доки.
- Образы переносятся `docker save` → tar, в контуре загружаются `docker load`.
- Интернет не требуется вообще.

### M3. Локальный registry (гибрид, для крупных организаций)
- В контуре один раз поднимается `registry:2` (тем же бандлом).
- Образы загружаются в локальный registry; все машины/стенды тянут из него.
- Обновления централизованны: новый бандл → загрузка в registry → pull.
- Рекомендуется, если инсталляций/стендов больше одного.

## 2a. Топология развёртывания

**All-in-one — РЕШЕНИЕ ПО УМОЛЧАНИЮ** (зафиксировано заказчиком 2026-09).
Один сервер, все сервисы (app + БД) в одном docker compose. Приоритет —
простота установки «одной командой». Это режим для 90% заказчиков, демо и пилота.

**Distributed — опция для крупных организаций.** БД (PostgreSQL, Neo4j,
Qdrant, Redis) на выделенных серверах. Требует: хосты сервисов в `.env`
(не хардкод), инфраструктурные сервисы под compose-profile `infra`
(на сервере приложения не запускаются), проверка доступности внешних БД
в инсталлере. Не делать единственным режимом — усложняет «одну команду».

Важно: «разнести по серверам» касается размещения СУБД, а не хранения данных —
данные всё равно в volumes/bind-директориях того хоста, где запущена СУБД.

## 3. Формат офлайн-бандла (M2)

```
kag-offline-<version>/
├── images/
│   ├── kag-api-<version>.tar        # docker save (gzip)
│   ├── kag-worker-<version>.tar
│   ├── kag-mcp-<version>.tar
│   ├── dozerdb-<version>.tar
│   └── infra-<version>.tar          # postgres, redis, qdrant, keycloak, nginx
├── compose/
│   ├── docker-compose.yml
│   └── docker-compose.offline.yml   # переопределение image → локальные имена
├── installer/
│   └── install.sh                   # load образов + ген .env + up + health
├── docs/                            # install / admin / security
├── SHA256SUMS                       # контрольные суммы ВСЕХ файлов
├── sbom.json                        # состав ПО (SBOM)
└── VERSION                          # версия + дата сборки
```

Требования к бандлу:
- **Контрольные суммы** (SHA256SUMS) — инсталлер проверяет до загрузки.
- **Подпись** (опц. cosign / gpg) — защита от подмены при транспортировке.
- **Версионирование** — имя и VERSION-файл.
- **Размер**: текущие образы api 3.7 GB + worker 3.0 GB + mcp 1.7 GB +
  dozerdb 1.1 GB ≈ 9.5 GB + инфра ≈ **~11 GB** до сжатия, ~5 GB после gzip.
  Оптимизация (см. §7) уменьшает существенно.

## 4. Инсталлер (единая точка входа)

Обязан делать сам, идемпотентно (повторный запуск не ломает установку):

1. **Preflight**: Linux + docker + compose (при отсутствии — поставить,
   с РФ-зеркалом для apt: deb.debian.org недоступен); RAM/CPU/диск;
   свободные порты 80/443; ОС (Debian/RHEL/Astra/РЕД ОС).
2. **Секреты**: сгенерировать ВСЕ пароли разом, записать `.env` целиком
   (правило проекта: пароли генерируются сразу и целиком, потом контейнеры).
3. **Образы**: online — pull; offline — `docker load` из `images/`.
4. **Запуск**: `docker compose up -d`, дождаться health всех сервисов.
5. **Инициализация**: первичная настройка (init-all), создание admin.
6. **Вывод**: креды, URL входа, дальнейшие шаги. Предупреждение про
   self-signed HTTPS.
7. **Откат/обновление**: отдельные команды; бэкап перед обновлением;
   миграции БД применяются автоматически.

---

## 5. Обновления

- **Online**: новый образ → push; на сервере `docker-compose pull && up -d`.
- **Offline**: новый (можно инкрементальный — только изменённые образы)
  бандл → `docker load` → `up -d`.
- **Миграции БД** применяются при старте (механизм миграций в проекте).
- **Перед обновлением** — обязательный бэкап (PostgreSQL + Neo4j + Qdrant +
  данные); откат = предыдущий бандл + restore.
- Данные в volumes/bind-данных обновление НЕ трогает.

---

## 6. Лицензирование (для продажи)

- **Офлайн-ключ**: подписанный файл лицензии, активируется без интернета.
- **Привязка**: к инсталляции (machine-id/домен/кол-во пользователей).
- **Ограничения**: срок, редакция (функции), лимиты.
- Технические меры — вспомогательные; основа — договор и правовые условия.
  Не строить защиту, ломающую эксплуатацию (без «звонков домой» — в закрытой
  сети их быть не может).
- Разделение редакций (напр. Community / Enterprise) делается конфигом/ключом,
  а не отдельной веткой кода.

## 7. Безопасность и соответствие

- **Секреты не в образах** — только генерация при установке (в `.env`).
- **Нет внешних вызовов** (для air-gapped): убраны CDN (граф — локальный
  cytoscape), шрифты/скрипты локальные. Единственный внешний ресурс —
  LLM/embeddings: в закрытом контуре должны быть on-prem (Ollama /
  llama.cpp / GigaChat on-prem / gpt2giga-proxy), иначе продукт бесполезен.
- **SBOM** — состав ПО поставки.
- **Подпись артефактов** — целостность бандла.
- **Минимизация поверхности**: образы без лишних пакетов; опционально
  `read_only`, `cap_drop`, отдельный пользователь (частично уже есть: kag).
- **Чистка репозитория**: в открытых файлах не должно быть паролей/ключей
  (в `PROJECT.md` исторически были sudo-пароль и адреса — проверить и вынести).
- **Российские ОС** для госсектора: Astra Linux, РЕД ОС, ALT — тестировать
  (в т.ч. Podman как альтернативу Docker в защищённых контурах).

## 8. Рекомендации по поставке в закрытые сети (свод)

1. **Образы, не сборка.** Единственно надёжный путь для air-gapped.
2. **Офлайн-бандл** как базовая единица поставки; online — как удобный
   дополнительный канал, не основной.
3. **Локальный registry** при >1 стенде — упрощает обновления.
4. **Инсталлер с preflight и идемпотентностью** — «одна команда».
5. **Фиксированные версии + SHA256SUMS + подпись.**
6. **Автобэкап перед обновлением, откат на предыдущий бандл.**
7. **On-prem LLM/embeddings** обязательны для закрытого контура.
8. **Документация заказчику**: install / admin / security (что и куда
   обращается, какие порты, как обновлять).
9. **Оптимизация размеров образов** (§3) — для передачи бандла.
10. **Лицензия офлайн** — без сетевых проверок.

Технические улучшения, которые стоит сделать до первых продаж:
- **общий базовый образ `kag-base` для api/worker** — сейчас api (3.71 ГБ) и
  worker (3.04 ГБ) собираются независимо и почти дублируют слои (разница:
  api несёт openssh-client+sshpass, worker — нет). Схема: `kag-base` = python +
  apt-пакеты + venv + requirements + Occular + pyctcdecode + Playwright Chromium
  + веса (собирается один раз, ~3.3 ГБ); `kag-api`/`kag-worker` = `FROM kag-base`
  + `COPY src` + свой CMD/healthcheck (тонкие слои ~десятки МБ).
  Экономия ~3 ГБ в registry и при передаче.
- **mcp-server** — его образ (1.67 ГБ) ставит только requirements.txt (без
  OCR/Playwright) и по зависимостям является подмножеством kag-base. Вариант:
  запускать mcp из того же `kag-base`-образа с `command: uvicorn
  src.mcp.server:app --port 8001` → минус целый образ (экономия ещё ~1.7 ГБ,
  итого бандл ~4.4 ГБ вместо ~9.5 ГБ). Решение принимать после проверки, что
  mcp не тянет OCR-импорты при старте (импорты ленивые — проверить).
- multi-arch (amd64 + arm64) — если заказчик может иметь ARM;
- `docker-compose.offline.yml` с локальными именами образов и без pull;
- Podman-совместимость (podman-compose) для защищённых ОС.
- NB: при упаковке нескольких образов в ОДИН `docker save`-архив общие слои
  не дублируются — часть экономии достигается уже этим, но общий base
  выравнивает digest'ы слоёв и в registry/pull.
