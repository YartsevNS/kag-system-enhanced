замером на 41 (20 ядер) и для сравнения не годилась.

**Ключевая находка.** Детектор текста RapidOCR не работает на вырезке одной строки (пусто и без
увеличения, и при ×2..×4) — детектору нужен контекст страницы. То же изображение без детектора

вырезка увеличивается до ~40 px. Без этого перенос ячеек дал бы пустые таблицы.

**Порядок выбора движка в коде:** служба PP-OCRv5 (41) → локальный PP-OCRv5 в контейнере → прежний Occular.
Локальный шаг добавлен специально: он позволяет убрать веса Occular из образа, не оставляя сканы без
распознавания при недоступной службе.

номера пунктов, обозначения документов) и прямо запрещены рассказы про граф/score/confidence,
вступления и заключения («Отличный вопрос», «Обратите внимание», «Подводя итог»), повтор и отчёт
о своих действиях. Ссылки — кратко («по документу «Квитанции.pdf»»), без score. Длину ответа
токенами НЕ нормируем: владелец просил исчерпывающий ответ, режем именно воду.

Замер на 75 вопросах (по одному прогону, глубина 10, отсечение выключено — сравнение с прежним
промптом при той же настройке):

| Промпт | Верных | Отказов | Длина ответа (медиана) | Служебных упоминаний на 75 ответов | Медиана времени |
| :-- | :-- | :-- | :-- | :-- | :-- |
| прежний | 58/75 = 0.773 | 17 | 795 симв. | 637 | 3,7 с |
| новый | 56/75 = 0.747 | 18 | 503 симв. | 9 | 3,4 с |

То есть болтовня убрана (−98,6% служебных упоминаний), средняя длина ответа 822 → 648 символов,
а точность и отказы остались в пределах шума набора (±4–5 вопросов). С доменным отсечением
(как в продукте) новый промпт дал 55/75 = 0.733, медиана ответа 514 символов, медиана времени 3,3 с.

ВАЖНО про замер: метрика «нужный источник упомянут в ответе» на новом промпте показывает 0 из 75 —
это артефакт метрики, а не потеря: она ищет шаблон «документ X.txt», а промпт теперь требует
называть документ коротко («по документу «Квитанции.pdf»»). При смене формата ответа механические
метрики надо перепроверять на ложные срабатывания.

Живой промпт берётся из настроек (привязка функции chat), файл `prompts/chat.txt` — только дефолт,

`scripts/set_chat_prompt.py` (на стенде: 2550 → 3159 символов).

## Живучесть api и стоимость запроса (20.09.2026)

Два захода, оба выросли из практики: сначала api дважды «завис» на живых вопросах, потом встал
вопрос цены запроса (консультация Z.ai/GLM через polza, файл `reports/_scratch/consult_cost_answer.md`).

### Живучесть: почему api переставал отвечать даже на /health

Симптом: контейнер `kag-api` в статусе unhealthy, в журнале последняя строка «Запрос в LLM», CPU 0%,
лечится только перезапуском. Причины оказались ДВЕ и обе в одном обработчике:

1. **Синхронные вызовы внутри асинхронного обработчика.** `kg_service.hybrid_search` (драйвер Neo4j
   синхронный), чтения `get_doc_repo().get_all()` и `document_service.get_document()` шли прямо в
   корутине и блокировали цикл событий — вместе с ним вставал и `/health`. Вызовы модели и
   эмбеддинги при этом были async (`httpx.AsyncClient`) и ни при чём. Исправлено: все три вызова
   переведены в `asyncio.to_thread`. Тест — `tests/test_chat_survivability.py`
   (`test_graph_search_runs_off_event_loop`).
2. **Таймаут был только на попытку.** 120 с на попытку × до четырёх попыток цепочки
   «основной → резерв» = до ~8 минут занятого обработчика на один вопрос. Разделены две величины:
   `llm_timeout` (попытка, по умолчанию **45 с**) и `llm_budget` (вся цепочка, по умолчанию **90 с**),
   обе настраиваются в привязке функции chat. Когда бюджет исчерпан, сервер отвечает честной ошибкой,
   а не держит соединение. Тесты — `test_llm_chain_respects_total_budget`,
   `test_chain_tries_reserve_within_budget`, `test_llm_attempt_timeout_is_configurable`.

### Стоимость: порядок блоков и бюджет истории

Замер: вход — основная статья расхода (на тяжёлом вопросе 7 447 токенов промпта против 829 токенов
ответа, то есть промпт ≈ 90% цены). При этом:

- контекст документов был СКЛЕЕН с системным промптом в одно system-сообщение и стоял ДО истории —
  поэтому кэш префикса (deepseek кэширует длиннейший общий префикс автоматически) не покрывал ни
  промпт, ни историю;
- вся история сессии добавлялась в запрос целиком: клиент присылает всю переписку, сервер ограничений
  не имел — цена вопроса росла с каждым ходом.

Как сделано: порядок сообщений теперь `system(чистый промпт)` → `история` → `system(статистика +
контекст документов + инструкция)` → `user(вопрос)`. То есть стабильное впереди, растущее в середине,
меняющееся — в хвосте. История режется серверным бюджетом (`_trim_history`: 2 500 токенов, последние
3 хода неприкосновенны, длинные старые ответы укорачиваются, а не выбрасываются). Тесты —
`tests/test_chat_cache_and_history.py`.

Эффект измерять по полю `prompt_cache_hit_tokens` из usage (провайдер его отдаёт — проверено живьём:
`prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`, `prompt_tokens_details.cached_tokens`), цель —
попадание выше 80% на втором и последующих запросах сессии. Ожидаемая экономия по разбору: 30–60%
при почти нулевом риске для качества (точность мерить на наборе 75 вопросов тем же способом).

### Что НЕ меняем (по разбору)

Нарезку 1500/225 не трогаем: замер показывает, что нужный факт часто не попадает в топ-10, а мелкие
чанки требуют большей глубины для того же покрытия. Следующая ступень по цене и качеству —
реранкер/гибридный поиск (топ-30 → топ-5–7), это отдельная задача.

Из разбора схемы вышли две практические вещи, обе проверены на стенде.

**Индексы payload.** Фильтры чата ходили по неиндексированным полям: до индекса запрос с фильтром
стоил заметно дороже. Замер (300 запросов напрямую в Qdrant, коллекция 9 929 точек):

| :-- | :-- | :-- | :-- | :-- | :-- | :-- |

| `visibility` | 9 929 | 33,96 мс | 11,69 мс | 44,15 мс | 13,00 мс | 2,9× |

Главная находка: у фильтра по `level` хвост был **выше 100 мс** (p99 104,84) — ровно тот случай,
о котором предупреждал разбор. После индексов хвост 11–14 мс. Индексы применены на стенде
(создаются за 0,3 с, обратимы). Хвосты без «холодного старта»: первые 20 запросов 11,2 мс против
11,8 мс у остальных 980.

**Связь «сущность → фрагменты»** уже есть в графе, отдельное поле не нужно:
`Chunk -MENTIONS-> Entity` (63 093 связи), `Document -HAS_CHUNK-> Chunk` (9 700),
`Section -SECTION_CHUNK-> Chunk` (5 438). То есть «где упоминается сущность» решается обходом
MENTIONS, а `chunk_id` = `Chunk.id` связывает вектор и узел.

**Наблюдаемость.** Нашлось, что метрики в `src/monitoring/prometheus.py` были объявлены, но нигде
не записывались и эндпоинта `/metrics` не существовало — то есть собирать было нечего. Сделано:
`TraceMiddleware` (заголовок `X-Trace-ID`, красивый контекст, метрики HTTP), trace_id в каждой
строке журнала (включая строки из `asyncio.to_thread`), постадийные записи в журнал и метрики
(поиск/граф/таблицы/модель с миллисекундами и токенами), гистограмма
`rag_stage_duration_seconds{stage}`, эндпоинт `/metrics` в формате Prometheus. Полное описание и
примеры запросов в Grafana — `docs/guides/observability.md`; там же честный список того, что ещё
не сделано (сквозной trace через воркер, OTel-спаны, Loki, алерты).

Попутно поймано три дефекта: (1) `/metrics` закрывали сразу два middleware, отдавая страницу входа, —
путь сделан публичным с тестом на оба; (2) в loguru 0.7.3 нет аргумента `patcher` у `add()` — только
через `configure()`; (3) кириллица в `X-Trace-ID` ломает отдачу ответа (заголовки latin-1) —
идентификатор валидируется как ASCII-токен.

## Инцидент 2026-09-13 (сайт лежал): nginx держал старый IP api

`--force-recreate api` меняет IP контейнера, а статический upstream nginx резолвится один
раз при старте -> **502 на весь сайт** до ручного `nginx -s reload`. Починено навсегда:
в `docker/nginx/conf.d/kag.conf` адреса upstream в переменных +
`resolver 127.0.0.11 valid=10s ipv6=off` — nginx перерезолвит сам (проверено: сайт
восстановился за <=3 с без вмешательства). Разбор — `docs/guides/deploy.md`.

Уроки: (1) проверять деплой ЧЕРЕЗ nginx, а не только `localhost:8000` — мои проверки шли
мимо nginx и 502 не видели; (2) `docker network connect` без `--alias api` ломает
DNS-запись -> 502; (3) `nginx -t` перед reload.
