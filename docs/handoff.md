Причина: отсечения по релевантности не было (порог отказа `min_top_score` = 0), поэтому в промпт
И в список источников (а значит и в блок таблиц интерфейса) попадало всё, что вошло в топ-10.

**Масштаб (замер по 75 вопросам):** в среднем 2,4 фрагмента из 10 — из посторонних документов
(~2 852 символа на ответ), 12,8% объёма контекста ниже лучшего на 0,10+, в 21% вопросов таких
фрагментов три и больше (до 46–51% объёма).

**Кривая порога (топ-20, 108 вопросов: 75 Википедии + 33 финкорпуса).** Порог сделан
ОТНОСИТЕЛЬНЫМ (от лучшего score): абсолютный не переносится между доменами — на текстах
посторонний фрагмент отстоит от нужного на ~0,10, на финкорпусе всего на 0,02.

| Отсечение | Википедия: мусора убрано | Финкорпус: мусора убрано | Потеря нужного источника |
| :-- | :-- | :-- | :-- |
| Δ=0,05 | 83% | 26% | 0 из 74 / 0 из 29 |
| Δ=0,10 | 67% | 2% | 0 из 74 / 0 из 29 |
| абсолютный 0,75 | 83% | — | уже 2 из 74 теряются |
| абсолютный 0,85 | 95% | 59% | 3 из 74 теряются (на финкорпусе — 0) |

**Реализация.** `apply_score_gap()` + `resolve_score_gap()` в `chat_service.py`: фрагмент
выбрасывается, если его score ниже лучшего на gap; минимум 3 фрагмента оставляем всегда (короткая
выдача не должна схлопываться). Приоритет значения: запрос → привязка функции → доменный дефолт
(`SCORE_GAP_BY_DOMAIN`: universal 0,08, legal 0,05, infosec/accounting 0,03, medical 0,05) →
встроенный 0,05. Из интерфейса чата пользователь задаёт 0,02–0,20 (нельзя выключить и нельзя
выкрутить в максимум — решение владельца); выключить (0) может только администратор в привязке.
Правки в обоих путях ответа (обычный и потоковый), в `models.ChatRequest`, `routes/chat.py`,
`chat.html` (селектор «Строгость отбора»), `admin.html` (поле порога + пороги по доменам).

ВАЖНО про замер: метрика «нужный источник упомянут в ответе» на новом промпте показывает 0 из 75 —
это артефакт метрики, а не потеря: она ищет шаблон «документ X.txt», а промпт теперь требует
называть документ коротко («по документу «Квитанции.pdf»»). При смене формата ответа механические
метрики надо перепроверять на ложные срабатывания.

Живой промпт берётся из настроек (привязка функции chat), файл `prompts/chat.txt` — только дефолт,

### Живучесть: почему api переставал отвечать даже на /health

Симптом: контейнер `kag-api` в статусе unhealthy, в журнале последняя строка «Запрос в LLM», CPU 0%,
лечится только перезапуском. Причины оказались ДВЕ и обе в одном обработчике:

1. **Синхронные вызовы внутри асинхронного обработчика.** `kg_service.hybrid_search` (драйвер Neo4j
   синхронный), чтения `get_doc_repo().get_all()` и `document_service.get_document()` шли прямо в
   корутине и блокировали цикл событий — вместе с ним вставал и `/health`. Вызовы модели и
   эмбеддинги при этом были async (`httpx.AsyncClient`) и ни при чём. Исправлено: все три вызова
   переведены в `asyncio.to_thread`. Тест — `tests/test_chat_survivability.py`
   (`test_graph_search_runs_off_event_loop`).
2. **Таймаут был только на попытку.** 120 с на попытку × до четырёх попыток цепочки
   «основной → резерв» = до ~8 минут занятого обработчика на один вопрос. Разделены две величины:
   `llm_timeout` (попытка, по умолчанию **45 с**) и `llm_budget` (вся цепочка, по умолчанию **90 с**),
   обе настраиваются в привязке функции chat. Когда бюджет исчерпан, сервер отвечает честной ошибкой,
   а не держит соединение. Тесты — `test_llm_chain_respects_total_budget`,
   `test_chain_tries_reserve_within_budget`, `test_llm_attempt_timeout_is_configurable`.

### Стоимость: порядок блоков и бюджет истории

Замер: вход — основная статья расхода (на тяжёлом вопросе 7 447 токенов промпта против 829 токенов
ответа, то есть промпт ≈ 90% цены). При этом:

- контекст документов был СКЛЕЕН с системным промптом в одно system-сообщение и стоял ДО истории —
  поэтому кэш префикса (deepseek кэширует длиннейший общий префикс автоматически) не покрывал ни
  промпт, ни историю;
- вся история сессии добавлялась в запрос целиком: клиент присылает всю переписку, сервер ограничений
  не имел — цена вопроса росла с каждым ходом.

Как сделано: порядок сообщений теперь `system(чистый промпт)` → `история` → `system(статистика +
контекст документов + инструкция)` → `user(вопрос)`. То есть стабильное впереди, растущее в середине,
меняющееся — в хвосте. История режется серверным бюджетом (`_trim_history`: 2 500 токенов, последние
3 хода неприкосновенны, длинные старые ответы укорачиваются, а не выбрасываются). Тесты —
`tests/test_chat_cache_and_history.py`.

Эффект измерять по полю `prompt_cache_hit_tokens` из usage (провайдер его отдаёт — проверено живьём:
`prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`, `prompt_tokens_details.cached_tokens`), цель —
попадание выше 80% на втором и последующих запросах сессии. Ожидаемая экономия по разбору: 30–60%
при почти нулевом риске для качества (точность мерить на наборе 75 вопросов тем же способом).

## Граф знаний: галочка «не строить» + найденный неполный граф (2026-09-13)

**Замер, из-за которого всё это:** документ «перечень документов по КИИ 2.pdf» (13 чанков)
обрабатывался 147 с, из них **135.7 с — граф**; разбор PDF + векторы — 11.6 с. У документа
на 212 чанков без графа: 21.8 с (parse 9.1, vectorize 10.3, analyze 2.3) — с `graph_skipped`.
Стоимость графа: ~3 с на чанк (2 LLM-вызова на чанк: сущности, затем связи) + дедупликация
сущностей, которая эмбеддит ВЕСЬ граф заново (~1577 имён при 8506 узлах = 197 батчей по 225 мс
≈ 44 с) + пары алиасов по одному запросу на пару.

**Сделано:** `system/graph = {skip}` + `processing_guard.graph_skip_requested()` (fail-open),
конвейер пропускает граф и entity resolution (шаг `graph_skipped` в журнале), API
`GET/POST /api/v1/admin/models/graph-build-config`, в админке секция «🧠 Граф знаний»
(галочка + «Построить граф сейчас»), на «Документах» — кнопка «🧠 Граф» у completed-документа.

**Найдено и исправлено попутно (важно!):** в `rebuild_graph_task` остался старый лимит
`chunks[:10]` — путь «построить позже» давал НЕПОЛНЫЙ граф: у документа в 23 чанка было
10 узлов-чанков (43%), у 212-чанкового было бы 4.7%. В конвейере лимит убрали ранее, здесь
нет. Исправлено (все чанки + отзывчивая остановка + отчёт `chunks_processed`/`chunks_total`),
проверено живьём: 10 → **23** узла, 51 сущность. Образ **2026.09.13.46**.

неполными — по документам, где граф важен, стоит перестроить заново.

**СДЕЛАНО (коммиты 730f6ee + e4e48c2, образ 2026.09.13.48):** дедупликация по эмбеддингам
убрана из конвейера документа; кандидаты формирует ночная задача `resolve_entity_candidates`

## Инцидент 2026-09-13 (сайт лежал): nginx держал старый IP api

`--force-recreate api` меняет IP контейнера, а статический upstream nginx резолвится один
раз при старте -> **502 на весь сайт** до ручного `nginx -s reload`. Починено навсегда:
в `docker/nginx/conf.d/kag.conf` адреса upstream в переменных +
`resolver 127.0.0.11 valid=10s ipv6=off` — nginx перерезолвит сам (проверено: сайт
восстановился за <=3 с без вмешательства). Разбор — `docs/guides/deploy.md`.

Уроки: (1) проверять деплой ЧЕРЕЗ nginx, а не только `localhost:8000` — мои проверки шли
мимо nginx и 502 не видели; (2) `docker network connect` без `--alias api` ломает
DNS-запись -> 502; (3) `nginx -t` перед reload.
