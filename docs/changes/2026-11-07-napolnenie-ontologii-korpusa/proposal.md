# Предложение: наполнение онтологии корпуса

Дата: 2026-11-07
Автор: агент (Hermes), постановка — владелец
Статус: черновик

## Зачем

База `cybersecurity_ontology_v2` на сервере 192.168.50.18 содержит результат обработки одного
файла — ГОСТ-Р-57580.2-2018.pdf (52 чанка): 237 объектов (166 `structural_element`,
37 `security_measure`, 20 `regulatory_document`, 10 `cii_object`, 3 `regulator`,
1 `threat_source`) и 147 связей. Дедуктивные правила `violated_documents()` и
`violated_certification()` на таком объёме не дают полезного результата, чат не получает фактов
из онтологии. Контур TypeDB остаётся демонстрационным.

## Что меняется

- В `cybersecurity_ontology_v2` записываются объекты из всех завершённых нормативных документов
  корпуса (95 уникальных файлов, 6830 чанков).
- Появляется воспроизводимая процедура массового наполнения с отчётом о прогрессе.

## Что НЕ меняется

- Схема `cybersecurity_ontology_v2` (`schema-v2.tql`, 10 сущностей, 9 связей) — без изменений.
- База `cybersecurity_ontology` (старая, с пилотными данными и фикстурами) — не трогаем, остаётся
  точкой отката.
- Промпт извлечения сущностей — авторский, не правим.
- Коллекция Qdrant `kag_documents`, граф в Neo4j — не трогаем.

## Критерий успеха

В `cybersecurity_ontology_v2` не менее 5000 объектов и не менее 3000 связей; повторная обработка
любого документа добавляет 0 объектов; у 100% объектов заполнен `source-chunk-id`.

## Риски

| Риск | Что делаем |
|---|---|
| 6830 вызовов модели, около 3–3,5 часа | запуск в фоне с отчётом прогресса в файл |
| дубли: `r-1323565.1.pdf` загружен 34 раза | дедупликация по хэшу содержимого, не по имени |
| часть `security_measure` с пустым `code` | отдельный замер доли и список таких записей |
| обрыв соединения на середине | идемпотентность по `ent-key`: повтор не дублирует |
| ошибки записи не должны ронять обработку | writer уже изолирует исключения |
