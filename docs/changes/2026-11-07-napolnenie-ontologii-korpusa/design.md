# Решение: наполнение онтологии корпуса

## Подход

Прогон идёт через существующий контур записи (`typedb_writer`), без новых модулей: документ
обрабатывается тем же путём, что и при загрузке — `POST /api/v1/upload/{id}/process?force=true`,
который в воркере вызывает `_build_typedb_only`. Это гарантирует, что наполнение идёт только
flow, а не пилотным скриптом.

Список документов строится отдельным запросом к Postgres: `status='completed'`,
`collection <> 'news'`, дедупликация по хэшу содержимого файла (не по имени). Драйвер обходит
список последовательно и пишет строку прогресса в файл после каждого документа.

Альтернативы, которые отвергли:
- прямой вызов `typedb_writer` из скрипта на чанках из Qdrant — быстрее, но обходит flow и
  противоречит правилу «наполнение только через обработку документа»;
- параллельный запуск всех 95 документов — упирается в модель и мешает работе API.

## Порядок выполнения

1. Снять контрольные счётчики по всем 10 типам в `cybersecurity_ontology_v2`.
2. Собрать список: 95 уникальных документов с хэшами, записать в `/tmp/fill_list.json`.
3. Запустить драйвер в фоне, лог — `/tmp/fill_run.log`, строка на документ с `flush`.
4. Следить по логу: число обработанных, ошибок, добавленных объектов.
5. После завершения — снять счётчики повторно и записать в `result.md`.

## Откат

База `cybersecurity_ontology` (старая) не затрагивается. Если наполнение v2 пойдёт неверно —
`cybersecurity_ontology_v2` пересоздаётся скриптом `project_typedb/pilot/create_v2.py` и
наполняется заново; данные в Postgres, Qdrant и Neo4j не меняются, поэтому потери нет.

## Открытые вопросы

- Доля `security_measure` с пустым `code`: если выше 30%, нужна правка промпта — но это
  авторский текст, решение владельца.
- Нужен ли ночной режим: прогон на 3–3,5 часа может мешать работе с системой днём.
