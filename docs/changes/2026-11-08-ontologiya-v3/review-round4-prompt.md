# Промпт извлечения v3.3: разбор замечаний ревьюера и главная находка

Ревьюер оценивал промпт версии 6 (9 тыс. знаков, TBox вручную). Ниже — статус каждого
замечания по факту, плюс дефект, который нашёлся при проверке и который важнее всех замечаний.

## Главная находка: промпт вообще не доходил до модели

В `src/indexing/entity_extractor.py` стояла страховка: `system_prompt` длиннее 9000 знаков
молча заменялся общим текстом «Ты — эксперт по извлечению…».

    промпт из БД (v3.2)        8 961
    + RESPONSE_FORMAT_RULES      573
    итог                       9 534  > 9 000  → заменялся заглушкой

То есть правила онтологии в извлечении не участвовали, и это не было видно ни в UI, ни в логах.
Именно поэтому разбор «старой версии» описывал промпт, который фактически не работал.

Исправлено: порог 16000 (промпт v3.3 + правила = 5 402, запас трёхкратный), при превышении —
WARNING с длиной, а не молчаливая подмена.

## Статус замечаний по промпту

| Замечание | Статус |
|---|---|
| TBox в промпте дублирует схему → дрейф | **исправлено**: плейсхолдер `{schema_tbox}`, TBox собирается из живой схемы (`ontology_service.tbox_summary`) |
| остался `source_requirement` | **исправлено**: ролей в прозе нет, TBox из базы (проверено: на v3 роли нет) |
| правило 10 — changelog, не инструкция | **убрано** |
| `category` противоречит правилу и схеме | **исправлено**: `category` удалён из схемы v3, остался `cii-category` (целое) |
| примеры без `ent-key` | **исправлено**: добавлен валидный few-shot с `ent-key` и связями |
| `id` в JSON ≠ `ent-key` (два идентификатора) | **исправлено**: правило «id = ent-key», формат `тип:ключ` |
| даты без формата | **исправлено**: ISO 8601, `cii-category` — целое |
| приоритет «нет обязательного → не создавай» vs «опусти поле» | **исправлено**: явное правило 3 сильнее правила 2 |
| «связи N-арные» | **исправлено**: «связи бинарные, кроме certification (3 участника)» |
| `basis_requirement` как обязательный | **исправлено**: в схеме `@card(0..1)`, в промпте «только при явном основании» |
| «если текст утверждает» (расплывчато) | **исправлено**: «нужна утверждающая формулировка» |
| применимость по категории без объекта | **добавлено правило**: объект не выдумывать, категорию оставить в описании |
| дедупликация без состояния графа | **частично**: «если в контексте передан `document_key`» — пайплайн пока его не передаёт |
| few-shot примеров нет | **добавлено**: один пример чанк → JSON |

## Замеры

    шаблон промпта (без TBox)          3 637 знаков   (было 8 961)
    с TBox на базе v3                  5 402           (TBox 1 765)
    с TBox на базе v2 (активна)        6 198           (TBox 2 561 — там ещё measure_definition)
    порог замены                       16 000 (было 9 000)

TBox на v3 содержит `document_has_version`, `document_structure`, `requirement_definition`;
`measure_definition` отсутствует. На активной v2 он пока содержит старые связи — это ещё один
аргумент переключить базу после переписывания writer.

## Что осталось

1. Пайплайн не передаёт известные `document_key` в промпт → дедупликация актов остаётся
   на совести writer (upsert по ключу), а не модели.
2. Пока активна база v2, подставляемый TBox — от v2: правила v3.3 ссылаются на связи,
   которых в v2 нет. Переключение базы — после writer под v3.
3. Удаление `category` из схемы v3 выполнено пересозданием базы (в TypeDB 3.14 снять owns
   у существующего типа нельзя).
