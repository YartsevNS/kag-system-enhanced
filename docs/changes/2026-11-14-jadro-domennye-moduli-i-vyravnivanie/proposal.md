# Предложение: ядро, доменные модули и выравнивание

Дата: 2026-11-15
Автор: помощник (по решению владельца)
Статус: черновик (ждёт утверждения)

## Зачем

Система строилась под один домен: в схеме TypeDB типы называются `security_requirement`,
`security_measure`, `cii_object`, роли связей привязаны к этим конкретным типам. Доменов станет
больше (информационные технологии и далее), а требование из одного домена сейчас не может
участвовать в тех же связях, что требование из другого: это невозможно на уровне модели, а не
«пока не сделали».

Дополнительно требование опознаётся по `sha256(текст)`. Из-за этого нельзя сравнить версии
документа («изменилось ли требование»), а «требование» и «описание подпункта меры» неразличимы
по типу (последнее выяснилось замером: 28–38 строк на документ).

Ограничения платформы проверены по документации: базы TypeDB изолированы (кросс-базовых запросов
нет), `@abstract` в 3.x не навязывает контракт подтипам, но подтипы умеют переопределять
владения и роли (`owns X as Y`, `relates r as s`).

## Что меняется

- Схема: ядро (абстрактные `document`, `clause`, `requirement`, `control`, `version`, `evidence`,
  `alignment`) + доменные модули (`sec_*`, `it_*`) как подтипы ядра. Домен — префикс в имени типа.
- Ключи: единые правила на все домены — документ (`домен:издатель|вид|номер`), узел структуры
  (`документ + structural_path`), требование (`документ + structural_path + порядок`),
  контроль (`домен:код`), редакция (`документ + версия`). Домен входит в ключ.
- Выравнивание: связь `alignment(source, target, kind, confidence)`; маппинги — YAML, грузятся
  в граф. Новый домен приносит свои маппинги, ядро не правится.
- Сборка схемы: `core.tql` + `modules/<домен>.tql`, конкатенация с проверкой дублей имён.
- Контур продукта: документ компании → пункты → покрытие требований → пробелы → новая версия
  документа со ссылками на требования. Одинаков для любого домена.

## Что НЕ меняется

Слои Bronze/Silver/Gold, нормализация, блокировка, дедупликация, guard'ы, локализация конфликтов,
очередь разбора и её страница, правило «детерминированное до модели», промпт извлечения
(версия меняется только отдельным решением). Существующие типы не выбрасываются — становятся
`sec_*` модулем.

## Критерий успеха

1. Запрос по абстрактному `requirement` возвращает требования всех доменов: `sec_requirement`
   и `it_requirement` — в одном результате.
2. Новый домен добавляется файлом `modules/<домен>.tql` + маппингами; ядро и существующие
   запросы не меняются (проверяется тестом: после добавления «пустого» третьего домена
   все прежние проверки зелёные).
3. После миграции данные сохранены: множество смысловых ключей до и после совпадает
   (сверка скриптом, расхождений 0).
4. Добавление требования не требует правки Python: только схема модуля, промпт и маппинги.

## Риски

| Риск | Что делаем |
|---|---|
| TypeDB 3 не навязывает контракт подтипам | обязательность атрибутов проверяем конвейером (guard'ы + integrity), а не схемой |
| Миграция потеряет провенанс | миграция на копии, сверка ключей и провенанса, старые базы не удаляем |
| Два домена в одной базе «перепутаются» | домен входит в ключ и в имя типа; запросы без префикса идут по абстрактному типу осознанно |
| Смена ключей сломает очередь и связи | сначала ядро и `sec_*` в новой базе, проверка на одном документе, затем миграция данных |
