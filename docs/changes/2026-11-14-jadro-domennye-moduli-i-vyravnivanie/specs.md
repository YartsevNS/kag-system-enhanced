# Требования: ядро, доменные модули и выравнивание

Каждое требование проверяемо командой или запросом. Базовый стенд: 192.168.50.18,
база `cybersecurity_ontology_v23` (текущая), новая — `…_v24`.

## R1. Ядро не содержит доменных имён

**Дано:** в текущей схеме есть `security_requirement`, `security_measure`, `cii_object`.
**Когда:** собрана новая схема `core.tql` + `modules/sec.tql`.
**Тогда:** в `core.tql` нет ни одного имени с доменным префиксом; доменные типы — только в модулях.

**Как проверить:** `grep -Ei "sec_|it_|security|cii" src/ontology/core.tql` → пусто.

## R2. Полиморфный запрос по абстрактному типу

**Дано:** в базе v24 есть `sec_requirement` и тестовый `it_requirement` (1 объект).
**Когда:** выполняется `match $r isa requirement;` (абстрактный тип).
**Тогда:** возвращаются оба требования разных доменов.

**Как проверить:** TypeQL-запрос в контейнере kag-api, результат содержит 2 типа объектов.

## R3. Единые правила ключей внутри домена

**Дано:** домен `sec`, документ `fstek|приказ|17`, пункт `7.7.1.5`, требование №3.
**Когда:** записываются документ, узел структуры, требование, контроль и редакция.
**Тогда:** ключи имеют вид: `sec:fstek|приказ|17`, `…#7.7.1.5`, `…#7.7.1.5#3`,
`sec:авз.1`, `…#ред-2`. `ent-key = <тип>:sha1(правило)`.

**Как проверить:** юнит-тест на функцию ключа (по одному примеру на категорию) + запрос
к базе: у 5 случайных требований ключ соответствует регуляркам категории.

## R4. Домен входит в ключ (нет коллизий между доменами)

**Дано:** домены `sec` и `it`; в каждом есть контроль с кодом `1` (условный пример).
**Когда:** создаются оба контроля.
**Тогда:** это два разных объекта; `match $c isa control;` возвращает 2; удаление одного
не затрагивает второй.

**Как проверить:** TypeQL-запрос + проверка ent-key: разные значения.

## R5. Новый домен добавляется без правки ядра и кода

**Дано:** рабочая база v24 с доменами `sec` и `it`.
**Когда:** добавляется `modules/third.tql` с одним типом-подтипом `third_requirement`
и пустыми маппингами; образ пересобирается.
**Тогда:** схема загружается, прежние проверки (R2, R3, очередь, integrity) остаются зелёными;
Python-код не менялся (проверяется `git diff --stat` по `src/**/*.py` → пусто).

**Как проверить:** прогон тестов + `git diff --name-only` по Python-файлам.

## R6. Выравнивание — данные

**Дано:** YAML `config/alignment/sec_it.yaml` с парой «шифрование хранимой информации» ↔
«шифрование данных при хранении», `kind=close`, `confidence=0.8`.
**Когда:** загрузчик маппингов выполняется.
**Тогда:** в графе появляется связь `alignment` между `sec_measure` и `it_control`
с атрибутами kind и confidence; повторная загрузка не создаёт дубль (идемпотентно).

**Как проверить:** TypeQL-запрос связи + повторный запуск загрузчика (число связей не растёт).

## R7. Миграция сохраняет данные и провенанс

**Дано:** база v23: `security_requirement` 473, `security_measure` 113, элементы 192
(прогон d7308e07).
**Когда:** миграция в v24 по новым ключам.
**Тогда:** число объектов по категориям совпадает, множество смысловых ключей совпадает
(расхождений 0), у каждого требования сохранён `source-chunk-id`.

**Как проверить:** скрипт сверки: счётчики по типам + множества ключей + провенанс.

## R8. Контур покрытия не зависит от домена

**Дано:** документ компании (политика) с 5 пунктами; требования домена `sec` и `it`.
**Когда:** запускается анализ покрытия.
**Тогда:** для каждого требования-кандидата создаётся или не создаётся связь покрытия
с указанием пункта документа; результат одинаков по форме для обоих доменов.

**Как проверить:** отчёт по одному документу: пункты, требования, статус покрытия,
для двух доменов — одинаковая структура отчёта.

## Ограничения

- Не удалять старые базы (v23 и ранее) — путь отката.
- Не менять промпт в этой работе: сначала схема и ключи.
- Тип требования остаётся с текстом как атрибутом; текст — не ключ.
- Проверки обязательности атрибутов — в конвейере, не в схеме (ограничение TypeDB 3).
