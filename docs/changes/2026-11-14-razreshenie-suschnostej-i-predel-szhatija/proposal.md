# Предложение: разрешение сущностей и предел сжатия

Дата: 2026-11-14
Автор: помощник (по решению владельца)
Статус: черновик (ждёт утверждения)

## Зачем

Silver-шаг (нормализация и блокировка, `src/indexing/bronze_resolve.py`) сжимает сырьё модели
в 2,9 раза: 2183 строки сущностей → 752 кластера на документе fstek-2014 (прогон `f16b25c3`,
321 фрагмент). Дальше сжимать почти нечего, и это подтверждено замером: у требований 495 разных
текстов на 508 строк, то есть настоящих повторов 13 (около 2,5 %). Остальное — разные требования.

Настоящая проблема не в дедупликации, а в ключе. Модель в поле `requirement-id` пишет номер
пункта только у 10 строк из 508 (2 %). Остальные значения: код меры (`ИАФ.1` — 333 строки,
66 %), слово (`пользователи-1` — 126 строк, 25 %), голое число (`5` — 39 строк, 8 %). Ключ
«документ|номер» на таких данных не работает: под `…|5` лежат 7 записей с разными описаниями,
и слияние по нему склеило бы разные требования. Проверка «валиден ли формат» тоже не спасает:
она оставила бы 10 строк из 508.

Вывод из замера: **идентичность требования задаётся его текстом, а не номером.** Номер (пункт
или код меры) — атрибут и ссылка, а не ключ. Тогда 508 строк дают 495 объектов, а код меры
сохраняется как связь с `security_measure` и не теряется.

## Что меняется

- **Правило 1 — идентичность требования по тексту.** Ключ = нормализованный текст описания
  (NFKC, нижний регистр, сжатие пробелов, снятие краевой пунктуации, первые 300 знаков).
  Дубли по тексту сливаются: 508 → 495 на этом прогоне; `requirement-id` в ключе не участвует.
- **Правило 2 — номер пункта как атрибут с проверкой формата.** Значение `requirement-id`
  проверяется и помечается видом: `clause` (`2.3`, `7.7.1.5`, `2.3-а` — 10 строк),
  `measure_ref` (`ИАФ.1`, `АВЗ.2-1` — 333 строки: это ссылка на меру, не ошибка),
  `bare_number` (39 строк: может быть настоящим пунктом), `word` (126 строк: модель положила
  тему вместо идентификатора). Записи с `bare_number` и `word` НЕ выбрасываются и НЕ сливаются:
  они попадают в очередь разбора с причиной «номер ненадёжен», объект живёт.
- **Правило 3 — меры и conflict guard.** У мер ключ — код (`АВЗ.1`), работает: 367 строк
  → 113 кластеров. Conflict guard: один код с разными названиями меры — конфликт, в очередь;
  названия сравниваются после нормализации.
- **Правило 4 — регулятор и издатель по коду органа.** `issuers.canonical` проверен:
  305 строк регулятора из 305 получают код `fstek`, без кода 0. То есть 305 → 1 кластер
  детерминированно, без fuzzy и без риска склеить разные ведомства.
- **Правило 5 — очередь разбора как диагностика.** Таблица `bronze_queue` с полем `reason`:
  `bare_number`, `word_as_key`, `measure_ref_as_id` (не ошибка, а вид ссылки),
  `empty_description`, `code_name_conflict`. Разбивка по причинам показывает, что чинить:
  извлечение (доминирует `word_as_key`) или типы сущностей (доминирует `measure_ref_as_id`).
- **Пересчёт разрешения на существующем Bronze.** Правила работают по сохранённым прогонам,
  без вызовов модели: новых прогонов и затрат нет.

## Что НЕ меняется

- Схема TypeDB, промпт извлечения (`prompt_version` 13 остаётся), конвейер этапов, лимиты
  и параллельность.
- База `cybersecurity_ontology` (путь отката) и ветка `PREPROD` не трогаются.
- Прогоны Bronze не удаляются: каждый прогон — свой `run_id`, старые строки остаются
  для сравнения.
- Пять документов за один заход не запускаются без отдельного разрешения владельца.

## Критерий успеха

На документе `fb4d9a84-e723-41fa-970d-2ed75683674d` (прогон `f16b25c3`):

1. Требования: 508 строк → 495 объектов (13 дублей по тексту слиты); записей с пустым
   описанием в TypeDB 0 (сейчас 0).
2. Разбивка `requirement-id` по видам зафиксирована числом: `clause` 10, `measure_ref` 333,
   `bare_number` 39, `word` 126; сумма 508.
3. `measure_ref` сохранён как связь с мерой: у требований с кодом меры связь с `security_measure`
   есть, потерянных кодов 0.
4. Меры: 367 строк → 113 кластеров; конфликтов «один код — разные названия» 0 (иначе в очереди).
5. Регулятор: 305 строк → 1 кластер, строк без кода 0.
6. Повторный пересчёт на том же прогоне даёт те же числа; вызовов модели 0.
7. Итог записан в `result.md` с выводом, где именно остановилось сжатие: требования — 2,5 %
   дублей, дальше рост даёт только качество ключа, не слияние.

## Риски

| Риск | Что делаем |
|---|---|
| Модель перефразирует требование, тексты не совпадут | ключ по тексту; перефразировки — отдельный семантический уровень, когда появятся данные |
| Голое число может быть настоящим пунктом документа | не сливаем и не выбрасываем: очередь с причиной `bare_number`, решение человеком |
| `measure_ref` может быть ошибкой типа (мера вместо требования) | сохраняем как атрибут; сомнительные — в очередь с причиной `measure_ref_as_id` |
| Слияние разных ведомств с похожими названиями | слияние только по коду из словаря; fuzzy — только в очередь |
