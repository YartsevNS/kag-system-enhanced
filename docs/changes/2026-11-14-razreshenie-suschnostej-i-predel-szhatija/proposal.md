# Предложение: разрешение сущностей и предел сжатия

Дата: 2026-11-14
Автор: помощник (по решению владельца)
Статус: черновик (ждёт утверждения)

## Зачем

Silver-шаг (нормализация и блокировка, `src/indexing/bronze_resolve.py`) сжимает сырьё модели
в 2,9 раза: 2183 строки сущностей → 752 кластера на документе fstek-2014 (прогон `f16b25c3`,
321 фрагмент). Дальнейшее сжатие упирается не в алгоритм сравнения строк, а в качество ключей:
у требований 450 ключей на 508 строк, из 41 кластера с более чем одной строкой 33 — не дубли,
а коллизия (под ключом «…|5» лежат 7 записей с разными описаниями: шифрование хранимой
информации, управление потоками между компонентами виртуальной инфраструктуры, проверка
вредоносных программ в файлах конфигурации). Среди requirement-id встречаются слова:
«пользователи», «аутентификац».

Причина — потеря контекста при извлечении, а не недостаток дедупликации: модель в части
фрагментов пишет голый номер («5», «6», «7») вместо номера пункта. Если такие записи слить
по ключу, разные требования склеятся в одно и загрязнят онтологию; чистка дороже
предотвращения. Кроме того, пункт чанка (clause) пуст у 468 из 508 строк (92%), поэтому
контекстная проверка ключа сейчас возможна только на 8% данных.

## Что меняется

- **Правило 1a — валидация формата ключа по типу.** Для `security_requirement` допустимы
  `2.3`, `7.7.1.5`, `2.3-а`, «приложение А»; недопустимы голое число, слово, код меры
  (`ИАФ.1`) в типе требования. Невалидные записи — в очередь разбора (таблица в Postgres),
  не в TypeDB и не в мусор.
- **Правило 1b — контекстная сверка ключа с пунктом чанка.** Сначала заполнять пункт
  (clause/structural_path) у чанка и писать его в Bronze; затем проверять, что id требования
  выводится из пункта чанка (пункт `2.3` → id `2.3-а` — валидно; пункт `2.3` → id `5` —
  в очередь).
- **Правило 2a — детерминированный conflict guard.** Для кластеров с более чем одной строкой
  сравнивать структурные идентификаторы внутри описаний (коды мер вида `АВЗ.1`, номера
  пунктов вида `7.7.1.5`). Расходятся — конфликт, в очередь; совпадают — слияние разрешено.
- **Правило 3 — регуляторы и издатели сливаются по коду органа, не по fuzzy.** Проверено
  на словаре `src/indexing/issuers.py`: «ФСТЭК России», «Федеральная служба по техническому
  и экспортному контролю», «…(ФСТЭК России)» → `fstek`; «Минцифры России» и полное
  министерство → `mincifry`. 305 строк регулятора → 1 кластер детерминированно, без риска
  склеить разные ведомства. Fuzzy (порог ≥ 0,9) — только для названий, которых нет в словаре,
  и такие идут в очередь на подтверждение.
- **Пересчёт разрешения на существующем Bronze.** Разрешение пересчитывается по сохранённым
  прогонам, без повторных вызовов модели: Bronze хранит сырьё, поэтому сжатие контента
  не требует новых прогонов и денег.

## Что НЕ меняется

- Схема TypeDB, промпт извлечения (`prompt_version` 13 остаётся), конвейер этапов, лимиты
  и параллельность.
- База `cybersecurity_ontology` (путь отката) и ветка `PREPROD` не трогаются.
- Прогоны Bronze не удаляются: каждый прогон — свой `run_id`, старые строки остаются
  для сравнения.
- Пять документов за один заход не запускаются без отдельного разрешения владельца.

## Критерий успеха

На документе `fb4d9a84-e723-41fa-970d-2ed75683674d` (прогон `f16b25c3`):

1. Кластеров требований с разными описаниями — 0 (сейчас 33); все они в очереди разбора
   с причиной.
2. Записей с невалидным ключом в TypeDB — 0; в очереди разбора видны количества по причинам
   (формат / нет пункта / конфликт описаний).
3. Регулятор: 305 строк → 1 кластер (сейчас 2); проверено, что разные органы не слились
   (сравнение кодов `issuers.canonical`).
4. Повторный пересчёт на том же прогоне даёт те же числа (идемпотентность).

## Риски

| Риск | Что делаем |
|---|---|
| Голое число «5» может быть настоящим пунктом документа | не удаляем и не сливаем: очередь разбора, решение человеком |
| Перефразировки одного требования в двух фрагментах | семантический уровень (порог сходства) — отдельным шагом, когда появятся такие кластеры |
| Слияние разных ведомств с похожими названиями | слияние только по коду из словаря; fuzzy — только в очередь |
| Пустой пункт чанка у 92% строк | сначала заполнение пункта и запись в Bronze, потом контекстная сверка |
