# Требования: разрешение сущностей и предел сжатия

Требование — проверяемое утверждение. Формат «дано / когда / тогда», с конкретными значениями.

Базовый объект для всех требований: документ `fb4d9a84-e723-41fa-970d-2ed75683674d`
(fstek-2014-mery-zashchity-gis.pdf), прогон Bronze `f16b25c3`, 321 фрагмент,
модель deepseek-v4-flash, `prompt_version` 13.

## R1. Требования разрешаются по тексту, а не по номеру

**Дано:** 508 строк `security_requirement`; у них 495 разных нормализованных текстов описания,
13 строк — повторы одного текста; ключ «документ|номер» даёт 450 ключей и 33 кластера-коллизии.
**Когда:** ключ требования строится как нормализованный текст описания (NFKC, нижний регистр,
сжатие пробелов, снятие краевой пунктуации, первые 300 знаков).
**Тогда:** 508 строк → 495 объектов; коллизий «один ключ — разные описания» среди требований 0.

**Как проверить:** пересчёт кластеров по новому ключу: 495 кластеров, кластеров с разными
описаниями 0.

## R2. `requirement-id` сохраняется как атрибут с разбивкой по видам

**Дано:** 508 значений `requirement-id`: `clause` 10 (2.3, 2.3-а, приложение А), `measure_ref` 333
(ИАФ.1, УПД.10-1-а — ссылка на меру), `bare_number` 39 (5, 6, 7), `word` 126 (пользователи-1,
аутентификация-1).
**Когда:** выполняется разметка вида идентификатора.
**Тогда:** каждое значение помечено одним из четырёх видов; сумма 508; ни одна строка не удалена
и не слита из-за вида идентификатора.

**Как проверить:** групповой запрос по виду идентификатора: 10 / 333 / 39 / 126, сумма 508.

## R3. Ссылка на меру не теряется

**Дано:** 333 строки требования несут код меры (`ИАФ.1`, `АВЗ.2-1`).
**Когда:** запись идёт в TypeDB.
**Тогда:** у требования с кодом меры есть связь с `security_measure`; требований с кодом меры
без связи 0.

**Как проверить:** сравнение числа требований с `measure_ref` и числа связей
«требование → мера» по этому прогону.

## R4. Меры: ключ по коду, конфликтов нет

**Дано:** 367 строк `security_measure` → 113 кластеров по коду.
**Когда:** применяется conflict guard: один код, разные названия меры (после нормализации) —
конфликт.
**Тогда:** кластеров мер с расходящимися названиями в TypeDB 0; конфликтующие — в очереди
с причиной `code_name_conflict`.

**Как проверить:** групповой запрос по коду меры: у каждого кода одно нормализованное название
либо запись в очереди.

## R5. Регулятор сводится к одному объекту по коду органа

**Дано:** 305 строк регулятора → 2 кластера: «фстэк россии» (304 строки) и «федеральная служба
по техническому и экспортному контролю (фстэк россии» (1 строка); `issuers.canonical` даёт код
`fstek` для всех 305 строк, строк без кода 0.
**Когда:** ключ регулятора строится из кода органа.
**Тогда:** регулятор — 1 кластер; строк без кода 0; разные ведомства не слиты (у них разные коды:
`fstek`, `mincifry`, `cbr` …).

**Как проверить:** пересчёт кластеров регулятора: 1 кластер; дополнительно — вывод
`issuers.canonical` для контрольных названий, где короткое и полное имя одного органа
дают один код, а разные органы — разные коды.

## R6. Очередь разбора показывает причину и пригодна для решения

**Дано:** записи с ненадёжным номером или конфликтом не должны ни теряться, ни сливаться.
**Когда:** строка попадает в очередь.
**Тогда:** у записи есть `reason` из перечня `bare_number`, `word_as_key`, `measure_ref_as_id`,
`empty_description`, `code_name_conflict`, и она остаётся доступной для решения человеком;
в TypeDB такая запись попадает только после решения, кроме `measure_ref_as_id` (это не ошибка,
а вид ссылки).

**Как проверить:** групповой запрос `reason, count(*)` по очереди; для каждой причины — примеры
по 5 записей.

## R7. Пересчёт идемпотентен и не требует новых прогонов модели

**Дано:** Bronze хранит сырьё прогона `f16b25c3`.
**Когда:** разрешение пересчитывается дважды подряд без нового прогона извлечения.
**Тогда:** оба расчёта дают одинаковые числа кластеров, очереди и принятых объектов;
новых обращений к модели — 0.

**Как проверить:** два запуска подряд, сравнение чисел; счётчик вызовов LLM до и после.

## R8. Результат сжатия измерен и записан

**Дано:** до правил — 2183 строки сущностей → 752 кластера (сжатие 2,9×); требования
508 → 450; меры 367 → 113; элементы 393 → 185; регулятор 305 → 2.
**Когда:** правила R1–R5 применены.
**Тогда:** в журнале и в `result.md` записаны числа до/после по каждому типу и число записей
в очереди по причинам; вывод «предел сжатия» подтверждён или опровергнут этими числами:
у требований 13 дублей (2,5 %), дальше сжатие возможно только за счёт качества ключа.

**Как проверить:** отчёт пересчёта на том же прогоне; сравнение с числами выше.

## Ограничения

- Не трогать базу `cybersecurity_ontology` (путь отката) и ветку `PREPROD`.
- Не удалять строки Bronze и записи очереди: только статусы.
- Не применять fuzzy к структурированным ключам (номера пунктов, коды мер).
- Не запускать повторную обработку документов (5+) без разрешения владельца.
- Промпт не менять в рамках этой работы: сначала разрешение, потом новые версии промпта.
