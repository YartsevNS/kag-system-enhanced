# Факты онтологии по вопросам об организации (P1.8)

## Проблема

Вопрос «Какие требования нарушены на АСУ ТП цеха № 1?» получал ответ «информация не найдена»,
хотя в онтологии факт нарушения существовал (правило `violated_certification()` давало 1).

Причина в фильтре: `query_facts` пересекал факты с чанками, которые вернул векторный поиск.
Политика компании редко попадает в выдачу нормативных вопросов, поэтому её факт отбрасывался.
Права доступа подменялись релевантностью.

Вторая причина: запрос фактов требовал у документа `source_origin`, которого нет у документов,
созданных из метаданных загрузки, — такие факты терялись молча.

Третья: документ компании вообще не появлялся в онтологии, если извлечение не находило в нём
«акта» (политика, инструкция). Без `company_document` правило `violated_documents` не может
сработать.

## Решение

1. `embeddings_service.visible_chunk_ids(...)` — проверка прав на конкретные чанки по ACL
   (visibility / allow_group_ids / allow_user_ids, deny приоритетнее, is_admin — полный доступ).
   Проверяются обе коллекции: основная и новости.
2. `typedb_facts.all_facts()` — все факты без привязки к выдаче поиска; видимость проверяет
   вызывающий код по ACL.
3. `chat_service` — факты фильтруются по `visible_chunk_ids`, а не по `search_results`.
4. `typedb_versions`: документ компании создаётся как `company_document` из метаданных
   загрузки, даже если извлечение не нашло акта.
5. Запрос фактов больше не требует `source_origin`.

## Проверка (стенд 192.168.50.18)

    сертифицированных средств защиты информации…» + пункт 3.1 политики

## Ограничения

- Видимость проверяется по чанку-источнику факта. Если документ удалён из Qdrant, но объекты
  остались в онтологии (техдолг 17), факт не показывается — это верно по правам, но мусор
  в базе остаётся до каскадной чистки.
- При ответе модель пересказывает требование, а не цитирует номер пункта: номер есть в
  контексте, но формулировка «п. 11.1» не обязательна.
