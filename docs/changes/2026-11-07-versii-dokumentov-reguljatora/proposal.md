# Предложение: версии документов регулятора

Дата: 2026-11-07
Автор: владелец (решение) + агент (исполнение)
Статус: выполняется

## Зачем

Новая редакция ГОСТ/приказа/закона приходит отдельным файлом. Сейчас writer создаёт по ней второй
`regulatory_document`, и онтология не знает, какая редакция действует: правило нарушений охватывает
обе, ответ может процитировать отменённое требование. В схеме v2 нет ни версии, ни дат действия
(`version_string` объявлен, но принадлежит только `company_document`).

## Что меняется

- схема `cybersecurity_ontology_v2`: сущность `document_version`, связи `document_version_of`
  и `supersedes`, атрибуты `effective_from`, `effective_to`, `version_status`, `version_hash`,
  `kag_document_id`, `document_key`; у `regulatory_document` — `document_key`, `current_version_string`;
- writer: версия создаётся на первом чанке документа и связывается с актом;
- загрузка через сайт: поля `version_string`, `effective_from`, `supersedes_id`; для `regulator`
  версия и дата обязательны;
- поиск: payload Qdrant получает `document_key`, `version_string`, `effective_from`,
  `version_status`; по умолчанию фильтр `current`;
- правила: `current_versions()`, `outdated_references()`.

## Что НЕ меняется

- ACL: права по-прежнему наследуются от чанка-источника; версия новых прав не вводит;
- Qdrant-коллекции и чанкинг; Neo4j из контура ответа не возвращается;
- старые документы не переобрабатываются массово — версии появятся при следующей обработке;
- структура Postgres не меняется (`document_versions` уже есть), поля загрузки идут в `source_metadata`.

## Критерий успеха

Загружены две редакции одного акта: в `cybersecurity_ontology_v2` один `regulatory_document`
с общим `document_key`, два `document_version`, одна связь `supersedes`, ровно одна версия со
`version_status = "current"`; вопрос чата о действующем требовании отвечает по current-редакции,
а `outdated_references()` возвращает требование из прежней.

## Риски

| Риск | Что делаем |
|---|---|
| старые объекты без версии ломают правила | правила работают и без `document_version` (объект без версии считается действующим), проверяем на текущей базе |
| ключ акта нестабилен (номер с пробелами, «№») | нормализация: тип + номер (или title) в нижнем регистре без пунктуации; ключ пишется в лог при создании |
| дубли версий при переобработке | `ent-key` версии = `kag_document_id`, повторная обработка обновляет ту же версию |
