# Изменения (структура OpenSpec, без CLI)

Методика взята из [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) (MIT): сначала
письменное предложение и проверяемые требования, потом код. Инструмент не внедряем — берём
структуру папок и дисциплину. Причины: CLI требует Node.js 22+ (лишняя зависимость в процессе
разработки), а 80% ценности даёт сам шаблон, а не команды.

## Что где лежит

| Документ | Отвечает на вопрос | Когда меняется |
|---|---|---|
| `docs/changes/<дата>-<название>/` | что делаем сейчас и чем закончилось | в ходе работы |
| `project_typedb/adr/NNN-*.md` | почему система устроена именно так | при смене решения |
| `docs/ARCHITECTURE-JOURNAL.md` | что фактически изменилось в системе | после выката |
| `docs/tech-debt.md` | что отложено и по какому критерию вернёмся | при откладывании |

Правило разделения: **ADR — про «почему навсегда», change — про «что делаем в этот раз»,
журнал — про «что стало по факту».** Одно и то же не дублируется: в change ссылаются на ADR
номером, в журнал попадает только результат.

## Когда заводить папку изменения

Заводить, если выполнено хотя бы одно:
- работа дольше одного дня;
- меняется схема TypeDB, структура таблиц Postgres, контракт API или состав контейнеров;
- затрагивается больше двух модулей.

Не заводить для: правки текста, одного бага в одном файле, изменения настройки. Такие вещи —
только запись в `ARCHITECTURE-JOURNAL.md`.

## Состав папки

    <YYYY-MM-DD>-<короткое-название>/
      proposal.md   зачем это нужно, что меняется, что НЕ меняется, риски
      specs.md      проверяемые требования (сценарии «дано/когда/тогда»)
      design.md     как устроим технически, какие файлы и данные затрагиваем
      tasks.md      чек-лист с критерием готовности у каждого пункта
      result.md     появляется после выполнения: цифры, отклонения от design

`result.md` — ключевой файл для памяти. В нём только проверяемые факты: что запускали, что
вернула команда, что осталось незакрытым.

## Порядок работы

1. Создать папку: `python scripts/new_change.py "название изменения"`.
2. Заполнить `proposal.md` и `specs.md`. Утвердить у владельца.
3. Заполнить `design.md` и `tasks.md`.
4. Выполнять задачи, отмечая `[x]` и записывая замеры.
5. Написать `result.md`, перенести папку в `archive/`, добавить строку в
   `docs/ARCHITECTURE-JOURNAL.md`, при смене решения — обновить ADR.

## Архив

Завершённые изменения: `docs/changes/archive/<YYYY-MM-DD>-<название>/`. Из архива не
удаляется ничего: это история решений и замеров, по ней восстанавливается «почему сделали так».

## Отличие от OpenSpec CLI

| | OpenSpec CLI | у нас |
|---|---|---|
| предложение и требования | `openspec/changes/<name>/` | `docs/changes/<дата>-<name>/` |
| применение | `/opsx:apply` | задачи выполняются обычными инструментами |
| архив | `/opsx:archive` | `git mv` в `archive/` + строка в журнале |
| зависимости | Node.js 22+ | нет |
