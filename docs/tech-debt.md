# Технический долг (список, по решению владельца)

Заполняется по мере того, как задачи осознанно откладываются. Формат: что сделать, зачем, чем рискуем
если не делать, и что нужно для проверки. Список не «на когда-нибудь», а на «когда освободится время» —
каждый пункт уже имеет измерение или понятный критерий готовности.

## Отложено 26.09.2026 (решение владельца: «в техдолг»)

### 1. Ветка main на GitHub отстаёт от PREPROD на 400+ коммитов
**Что:** подтянуть `main` к PREPROD (или переименовать/удалить, если main больше не используется).
**Зачем:** основная ветка по умолчанию уже PREPROD; висящая ветка-предок сбивает с толку при клонировании
и при просмотре истории на GitHub.
**Риск, если не делать:** новый человек (или агент) склонирует main и увидит код полугодовой давности.
**Проверка:** `git rev-list --count origin/main..origin/PREPROD` → 0.

### 2. Скорость реранкера (1,5 с на вопрос) — ищем быстрый вариант
**Что:** замерить `sshalimov04/ru-reranker-edge-150m` (в 3,8 раза легче DiTy, есть fp16-ONNX) и вход
256 токенов вместо 512; при необходимости — статическое int8-квантование с калибровкой.
**Зачем:** владелец принял +1,5 с как допустимое (локальный сервер, позже GPU), но чем меньше, тем лучше:
это время на каждом вопросе.
**Что уже проверено и НЕ помогает:** ONNX fp32 равен torch (1623 мс против 1460 мс на 10 кандидатах),
динамическое int8 ломает порядок (топ-1 уезжает на посторонний фрагмент) — эту вилку закрывать не нужно.
**Проверка:** замер времени на вопрос + сравнение порядка фрагментов с torch-эталоном (скрипты
`scripts/rerank_onnx_export.py`, `scripts/rerank_onnx_check_local.py`), затем quality-замер судьёй.

### 3. Порог отсечения фрагментов перепроверить на новом порядке
**Что:** после включения реранкера подобрать `min_score_gap` заново на том же эталонном наборе.
**Зачем:** cross-encoder разводит оценки заметно шире (отрыв лучшего от второго 16% против 1–6% у
векторного поиска), поэтому старые значения (0,02–0,12) на новой шкале означают другое.
**Риск, если не делать:** отсечение будет либо не работать, либо срезать полезное.
**Проверка:** прогон `scripts/eval_rag_judge.py` по вариантам порога, сравнение при одинаковом k.
