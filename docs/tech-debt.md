# Технический долг (список, по решению владельца)

Заполняется по мере того, как задачи осознанно откладываются. Формат: что сделать, зачем, чем рискуем
если не делать, и что нужно для проверки. Список не «на когда-нибудь», а на «когда освободится время» —
каждый пункт уже имеет измерение или понятный критерий готовности.

## Отложено 26.09.2026 (решение владельца: «в техдолг»)

### 1. Ветка main на GitHub отстаёт от PREPROD на 400+ коммитов
**Что:** подтянуть `main` к PREPROD (или переименовать/удалить, если main больше не используется).
**Зачем:** основная ветка по умолчанию уже PREPROD; висящая ветка-предок сбивает с толку при клонировании
и при просмотре истории на GitHub.
**Риск, если не делать:** новый человек (или агент) склонирует main и увидит код полугодовой давности.
**Проверка:** `git rev-list --count origin/main..origin/PREPROD` → 0.

### 2. Скорость реранкера (1,5 с на вопрос) — ищем быстрый вариант
**Что:** замерить `sshalimov04/ru-reranker-edge-150m` (в 3,8 раза легче DiTy, есть fp16-ONNX) и вход
256 токенов вместо 512; при необходимости — статическое int8-квантование с калибровкой.
**Зачем:** владелец принял +1,5 с как допустимое (локальный сервер, позже GPU), но чем меньше, тем лучше:
это время на каждом вопросе.
**Что уже проверено и НЕ помогает:** ONNX fp32 равен torch (1623 мс против 1460 мс на 10 кандидатах),
динамическое int8 ломает порядок (топ-1 уезжает на посторонний фрагмент) — эту вилку закрывать не нужно.
**Проверка:** замер времени на вопрос + сравнение порядка фрагментов с torch-эталоном (скрипты
`scripts/rerank_onnx_export.py`, `scripts/rerank_onnx_check_local.py`), затем quality-замер судьёй.

### 3. Порог отсечения фрагментов перепроверить на новом порядке
**Что:** после включения реранкера подобрать `min_score_gap` заново на том же эталонном наборе.
**Зачем:** cross-encoder разводит оценки заметно шире (отрыв лучшего от второго 16% против 1–6% у
векторного поиска), поэтому старые значения (0,02–0,12) на новой шкале означают другое.
**Риск, если не делать:** отсечение будет либо не работать, либо срезать полезное.
**Проверка:** прогон `scripts/eval_rag_judge.py` по вариантам порога, сравнение при одинаковом k.

## Отложено 27.09.2026 (решение владельца)

### 6. Свой OCR вместо весов Occular — лицензия весов ограничивает поставку
**Что:** разработать собственные веса OCR (детектор текста, распознаватель, языковая модель) и заменить ими
веса Occular. Код Occular менять не нужно: он под Apache License 2.0.
**Зачем:** веса Occular (детектор, распознаватели svtr_lcnet/svtr_t, языковые модели, модель порядка чтения)
распространяются под **modified AI Pubs OpenRAIL-M**. Свободное использование там разрешено только частным
лицам, исследователям и научным организациям, некоммерческим организациям, самозанятым и малым
организациям (годовая выручка **меньше 20 000 000 ₽ И** штат **меньше 8 человек**). Для поставки продукта в
организации этих условий недостаточно. Исключение: модель определения ориентации страницы
(`orientation_orinet_fp32.onnx`) под Apache 2.0 — её можно использовать свободно.
**Риск, если не делать:** продукт нельзя легально поставлять заказчикам вне «малой организации»: веса вшиты
в образы поставки, и при проверке это первое, что видно. Ситуация усугубляется тем, что весь OCR в системе
сейчас опирается на эти веса.
**Что нужно для проверки:** свои веса (детектор + распознаватель), обученные на нашем корпусе; замер на
эталонном наборе страниц по числу ошибок в словах против текущих весов; лицензия своих весов — Apache 2.0
или собственная. Инструменты замера уже есть: `scripts/occular_full_probe.py`,
`scripts/occular_tables_fill2.py` (текст с координатами, таблицы, время).
**Побочно (на будущее):** тот же вопрос надо задать по другим весам в поставке — эмбеддинги, реранкер,
модель строения таблиц, OCR-веса OCR-контура OCR_OCULAR. Список лицензий стоит свести в один документ
поставки.

### 7. (ПАУЗА) Работа с таблицами приостановлена до выбора рабочего флоу (решение владельца 28.09.2026)

**Решение владельца:** прекращаем разработку по восстановлению/распознаванию таблиц; вернёмся позже, когда будет
выбран рабочий флоу. Это фиксирует текущее состояние, чтобы не потерять наработки.

**Что уже сделано и зафиксировано (значимые результаты):**
- **Служба OCR на 41 работает**: PP-OCRv5 `cyrillic` (RapidOCR/ONNX, CPU) как systemd-служба `kag-ocr.service`,
  порт 8020, автозапуск; накладная — ~3 с (против ~32 с у Occular), строки с рамками, кириллица верная.
  Код в `services/ocr_service/`, ветка `paddle-ocr`.
- **Выбор движка для ТЕКСТА страницы**: PP-OCRv5 cyrillic найден рабочим для текста (чисто), eslav — чуть больше
  чисел, но хуже текст; PP-OCRv6 кириллицу НЕ поддерживает вовсе (проверено ошибкой самой библиотеки +
  подтверждено issue docling #3840).
- **Для ТАБЛИЦ новый OCR пока не лучше**: приёмка по арифметике (кол-во × цена = сумма): Occular — 1 из 21,
  PP-OCRv5 — 0 (таблица собирается, но колонки шапки не определяются из-за искажённой шапки). Детальный разбор
  в `docs/guides/ocr-engine-selection.md`.

**Что осталось на потом (когда вернёмся):**
1. служба OCR сможет использоваться и для таблиц (подключение с переключателем в настройках);
2. общий список: порядок чтения страницы, арифметический валидатор, просмотрщик со слоями — уже начаты,
   см. `docs/guides/document-viewer-and-extraction-plan.md`.

**Сейчас НЕ делаем:** ничего из табличного стека. PREPROD не трогаем; эксперимент — в ветке `paddle-ocr`.
Возврат к прежнему поведению — теги `2026.09.27.19`, метка `stable-occular-2026.09.27`.

### 9. Стратегия таблиц: дорабатывать отраслевой конвейер, а не переносить (решение 03.10.2026)

Выбрана стратегия развития табличного слоя. НЕ переносим чужой конвейер целиком (верхний слой «поля/роли» у всех
custom); дорабатываем блоки, которых у нас нет. Зафиксировано в `docs/guides/ocr-engine-selection.md`, раздел
«Стратегия».

При возврате к таблицам (пауза до выбора флоу в силе) порядок:
1. **DocLayout-YOLO** как детектор таблиц для случая «нет линий» — замена/резерв VL-модели (быстрее и
   детерминированнее; структуру ячеек всё равно даёт SLANet/TableFormer);
2. **Линеаризация таблиц в Qdrant** («наименование: Яблоко, цена: 100») — поверх текущего dense+sparse+RRF и
   точного поиска в Postgres;
3. **Съём OCR ячеек на PP-OCRv5 cyrillic** (у нас уже работает как служба на 41) для повышения точности чисел;
4. Промпт LLM «если вопрос о цифрах — сначала ищи в JSON/структуре, потом формируй ответ».
