# Смена движка OCR: служба PP-OCRv5 вместо Occular

Документ описывает переход текстового распознавания и распознавания ячеек таблиц с Occular (в контейнере)
на службу PP-OCRv5 (RapidOCR/ONNX) на сервере моделей. Переход сделан **переключателем**, а не заменой:
выключенная опция возвращает прежнее поведение, поэтому риск на проде управляем.

## Зачем переходим

| Что | Occular (прежний) | PP-OCRv5 cyrillic (служба) |
|---|---|---|
| Время на накладной (прод, один хост) | 43,9 с | **28,0 с** |
| Контрольные числа накладной | 3 из 7 | **4 из 6** |
| Веса в образе | ~700 МБ (10 файлов) + torch ~0,9 ГБ | ~200 МБ, torch не нужен |
| Лицензия весов | OpenRAIL-M (ограничение по выручке/штату) | Apache-2.0 |

Замер 03.10.2026 — **оба движка на одном хосте**: PP-OCRv5 внутри контейнера api на стенде (не на сервере
моделей), чтобы сравнение было честным. Ранее «3 с против 32 с» — это сравнение разных машин (20 ядер против
нагруженного стенда), так считать нельзя.

## Что важно знать про PP-OCRv5

* PP-OCRv6 для русского **не годится**: кириллицы в нём нет (библиотека прямо отвечает
  `Unsupported rec.lang_type='eslav'`/`'cyrillic'` для v6 small и medium). Русский — только v5:
  языки `cyrillic` и `eslav`, модель mobile, Apache-2.0.
* В RapidOCR 3.x версия и язык задаются **перечислениями** (`OCRVersion.PPOCRV5`, `LangRec.CYRILLIC`),
  строки конструктор не принимает.
* Библиотека **не потокобезопасна**: один движок на процесс, вызовы сериализованы блокировкой.

## Что сделано

1. **Служба на сервере моделей (41)**, юнит `kag-ocr.service`, порт 8020:
   * `GET /health` — состояние и готовность движка;
   * `POST /ocr` — строки страницы: `text`, `quad`, `confidence`, `raw_scale` (формат совпадает с Occular);
   * `POST /cells` — текст вырезанных ячеек: на вход изображение страницы (base64 PNG) и рамки, на выход
     тексты с уверенностью. Вырезки идут **одним запросом**, а не по одной.
2. **Клиент в проекте** — `src/indexing/ocr_client.py`: настройки, проверка доступности с кэшем
   (недоступный сервер не тормозит каждую страницу), разбор ответов. Никогда не бросает исключение.
3. **Коммутатор в конвейере** — `table_strategy.raw_lines_from_engine()`: служба, при недоступности или
   пустом ответе — откат на прежний движок. Распознаватель ячеек `make_cell_recognizer()` тоже сменный.
4. **Настройки в админке** — namespace `ocr`, ключ `settings`:
   `service_enabled` (по умолчанию **false**), `service_url`, `service_timeout_s`.
   Ручки: `GET/POST /api/v1/admin/models/ocr-settings`, состояние службы — `GET /api/v1/admin/models/ocr-service`.

## Ключевая находка: как распознавать ячейки

**Детектору текста нужна страница целиком — на вырезке одной строки он не находит ничего.**
Проверено 03.10.2026 на накладной: вырезка высотой 13–15 px даёт пусто и без увеличения, и при увеличении
×2..×4. Тот же кроп **без детектора** (`Global.use_det: False`) читается: «Универсальный»,
«Исправление №», «15855», «23 июня 2025 г.».

Поэтому `/cells` использует отдельный движок — распознаватель без детектора — и увеличивает вырезку до
~40 px по высоте (предел ×4). Замер на 8 вырезках: **0,25 с**, 6 из 8 с текстом.

## Как включить (на стенде)

```bash
# 1) включить службу
curl -s -X POST http://<стенд>/api/v1/admin/models/ocr-settings \
  -H 'Content-Type: application/json' \
  -d '{"service_enabled": true, "service_url": "http://192.168.50.41:8020"}'

# 2) проверить, что служба видна из контейнера api
curl -s "http://<стенд>/api/v1/admin/models/ocr-service?check=true"

# 3) переобработать документ — в журнале воркера будет причина вида
#    «сетка по линиям: 28 строк × до 20 колонок, качество …, распознавание: служба PP-OCRv5»
```

Выключение (`service_enabled: false`) мгновенно возвращает прежний движок — пересборка не нужна.

## Порядок выбора движка (в коде)

    служба PP-OCRv5 на 41  →  локальный PP-OCRv5 в контейнере  →  прежний Occular (если ещё установлен)

* служба — быстрый путь (движок на 20-ядерной машине);
* локальный PP-OCRv5 — запасной: тот же движок, но в контейнере; нужен, чтобы недоступная служба не
  оставляла сканы без распознавания после удаления весов Occular из образа;
* Occular остаётся третьим шагом только пока он есть в образе.

Распознавание сканов идёт через те же движки: `hybrid_parser` (текст страницы) и `table_strategy`
(строки для таблиц, ячейки). Настройка задаёт только первый шаг — службу.

## Что убрано из образа и что добавлено

`docker/base/Dockerfile`: убраны Occular, `pyctcdecode` и torch (CPU-сборка, ~0,9 ГБ) вместе с
предзагрузкой весов Occular (~700 МБ); добавлен `rapidocr` с прогревом моделей PP-OCRv5 при сборке
(модели кладутся внутрь пакета, поэтому образ работает и без сети). Отдельная тонкость: `rapidocr`
тянет `opencv-python` (не headless) — его надо снять и поставить обратно `opencv-python-headless==4.12.0.88`,
иначе `cv2` падает с `libGL.so.1` (проверено на сервере моделей 03.10.2026).

Откат после выкатки — старыми тегами образов (`kag-base:2026.09.27.4`, `kag-api/kag-worker:2026.09.27.19`),
они остаются на стенде.

## Что осталось (после приёмки)

  «Сложный тест»), сверить таблицы и контрольные числа с прежним результатом.
