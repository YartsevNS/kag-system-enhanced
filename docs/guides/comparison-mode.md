# Сравнительные вопросы (пункт 4): что сделано и почему выключено по замеру

Обновлено 2026-09-13. Образ стенда: **2026.09.13.69**. Коммиты: `c6c4a06` → `ae63567`.

## Что реализовано

Сравнительный режим в чате: для вопроса вида «сравни A и B» собирается структурированный контекст —
на каждую сторону карточка документа (`level=document`) и её фрагменты (фильтр поиска по
`document_id`) с хлебной крошкой раздела, плюс инструкция отвечать двумя блоками («Общее»,
затем «Отличия» с указанием документа и раздела).

Состав: `src/indexing/comparison.py` (определение сравнительного вопроса, разбиение сторон без LLM,
сборка контекста, флаг `config_store chat/comparison`), `chat_service._comparison_context`,
тесты `tests/test_comparison.py` (11 проверок).

## Замер: режим ухудшает покрытие

Метрика — покрытие сравниваемых документов (документ упомянут в ответе или присутствует
в источниках); эталонных ответов для сравнительных вопросов нет, поэтому мерим то, что прямо
отражает цель режима.

| режим | среднее покрытие | полностью покрыты оба документа |
|---|---|---|
| выключено | **0.8750** | 3 из 4 |
| включено | **0.7500** | 2 из 4 |

Ответы при включённом режиме стали короче (например, 2840 символов против 6968 на вопросе
про выработку общего ключа), и один документ из пары терялся. **Режим выключен по замеру.**

## Причина (диагностика по логам)

Маппинг «сторона сравнения → документ» через карточки (`search_documents(..., limit=1)`)
ненадёжен на документах одной серии — их карточки почти неразличимы:

| вопрос | выбранные документы | что ожидалось |
|---|---|---|
| TLS 1.2 против TLS 1.3 | `19cdddfc`, `19cdddfc` — ОБА раза один документ (TLS 1.3) | `5586487b`, `19cdddfc` |
| выработка общего ключа против транспортных контейнеров | `b00668c0`, `18413c28` | `24d001b4`, `18413c28` |
| ГОСТ Р 34.11-2012 против ГОСТ Р 34.13-2015 | `b7324ebf`, `b93f09c5` (это 34.10 и 34.12!) | `d3c3f673`, `1d9dacc7` |

То есть режим не «не помог», а активно мешал: он подставлял неверно выбранные документы
вместо правильных фрагментов, которые обычный поиск уже находил (покрытие без режима 0.875).

## Что делать дальше (гипотеза исправления)

1. **Брать документ стороны из обычного поиска по фрагментам**, а не из карточек: топ-документ
   среди чанков по подзапросу стороны — на серии 34.x чанки различаются (в тексте есть номер
   стандарта), а карточки нет.
2. **Проверять совпадение обозначения**: если в запросе стороны есть обозначение
   («ГОСТ Р 34.11-2012»), требовать его присутствия в названии/файле выбранного документа.
3. **Не сужать контекст**: добавлять блок сравнения к обычным фрагментам, а не заменять их
   (сейчас блок идёт первым, но при неверном маппинге он перетягивает ответ на себя).

Порядок работ: сначала (1) и (2), затем повторный замер на тех же 4 вопросах — без улучшения
покрытия относительно 0.875 включать режим не стоит.

## Инструменты

* `scripts/evaluate_comparisons_template.py` — покрытие сравниваемых документов
  (упомянут в ответе или есть в источниках), печатает ответы целиком для разбора.
* Проверка срабатывания режима — по логу: `docker logs kag-api | grep "сравнительный контекст"`.
  Это обязательный шаг: первый прогон показал 0 срабатываний при включённом флаге (стороны
  делились через `_decompose_query`, у которого порог «вопрос длиннее 60 символов»), второй —
  3 срабатывания с ошибкой ACL-фильтра, и только третий заработал. Без этой проверки «режим
  не помог» и «режим не включался» выглядят одинаково.
* Попутно исправлен реальный баг: `search_documents` использовал `MatchValue(any=...)` вместо
  `MatchAny` — ACL-фильтр карточек падал с `ValidationError` при непустых группах.
