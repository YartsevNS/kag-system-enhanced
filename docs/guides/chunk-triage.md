# Триаж чанков: штампы и дубли не стоят LLM-вызовов

Обновлено 2026-09-13. Модуль: `src/indexing/chunk_triage.py` (тесты: `tests/test_chunk_triage.py`, 9 проверок).
Образ на стенде: `2026.09.13.53`. Коммиты: `ad441aa` → `0c5cee7`.

## Зачем

Извлечение сущностей в граф — 2 LLM-вызова на КАЖДЫЙ чанк (~3 с). Часть чанков служебная:
титульные листы, шапки «РЕКОМЕНДАЦИИ ПО СТАНДАРТИЗАЦИИ», копирайты «© Стандартинформ»,
повторяющиеся блоки внутри одного документа. Платить за них LLM смысла нет.

## Что делает

Два независимых правила, оба до вызова LLM:

1. **Дубли внутри документа** — если чанк почти совпадает с более ранним чанком ТОГО ЖЕ
   документа (косинус ≥ `CHUNK_DUP_SIM` = 0.95), извлекаем один раз, у первого.
2. **Штампы** — если такой же чанк есть ещё минимум в `CHUNK_BOILERPLATE_MIN_DOCS - 1` = 2
   ЧУЖИХ документах (косинус ≥ `CHUNK_BOILERPLATE_SIM` = 0.95), извлечение не нужно вообще.

Результат: списки индексов `kept` / `boilerplate` / `duplicate` + `summary()`. Модуль ничего
не пишет — решение принимает конвейер (`document_service._build`).

Что делает конвейер:
* пропускает LLM-извлечение для `boilerplate` и `duplicate` (узлы чанков всё равно создаются —
  граф структурно полный, цепочка NEXT не рвётся);
* помечает штампы в Neo4j (`Chunk.is_boilerplate = true`) — задел для фильтра в выдаче чата;
* пишет в журнал обработки шаг `graph_triage` с разбивкой (`kept` / `boilerplate` / `duplicate`)
  и временем.

Настройки (`src/config.py`): `GRAPH_TRIAGE_ENABLED` (по умолчанию `true`), `CHUNK_BOILERPLATE_SIM`,
`CHUNK_BOILERPLATE_MIN_DOCS`, `CHUNK_DUP_SIM`, `CHUNK_TRIAGE_NEIGHBORS`.

## Замеры (живые, сервер 18)

| Что | Значение |
|---|---|
| Стоимость триажа | ~12 мс на чанк (ANN-запрос в Qdrant) → 307 мс на 22 чанка, 2.6 с на 212, 6.8 с на 558 |
| Экономия | 2 LLM-вызова (~3 с) на каждый пропущенный чанк |
| Пример (22-чанковый ГОСТ) | `kept 18, штампы 4` — титул, шапка «РЕКОМЕНДАЦИИ ПО СТАНДАРТИЗАЦИИ», «© Стандартинформ», служебная шапка |
| Шаг графа того же документа | **142.9 с → 5.1 с** (тут вместе с убранным дедупом и кэшем LLM) |
| Штампы в корпусе (50 док.) | 91 чанк с маркерами в 30 документах → ~4 % чанков |

Порог 0.95, а не 0.97: проба 14 чанков из 12 документов дала максимум 0.927 (семантически
близкий, но ДРУГОЙ текст), а корпусная проба нашла 397 пар ≥ 0.95 — копии шапок в серии
документов одного ГОСТа. Точность держит второе правило — «минимум 2 чужих документа».

## Три ловушки, из-за которых триаж молча давал ноль

Все три выглядели бы как «в корпусе нет дублей». Поэтому правило: **нулевой результат
обязан быть отличим от «не смог прочитать»**.

1. **Сопоставление векторов.** `point_id = uuid5(chunk_id)` не совпадает у старых чанков:
   в корпусе ДВЕ схемы id (старая `uuid5(document_id-i)` и новая `uuid5(chunk_id)`).
   Было 0 векторов из 558. Теперь сопоставляем по `payload.chunk_id` (есть у всех точек),
   с резервом на `point_id` и `payload.id`; при неполном сопоставлении в `TriageResult.error`
   пишется `vectors_missing: N из M` — это видно в журнале обработки.
2. **Именованные вектора.** Коллекция содержит `dense` (2560) + `sparse`; без `using="dense"`
   каждый ANN-запрос падает с 400 «Vector params for  are not specified in config».
   В логах было 558 ошибок подряд.
3. **`plog` вне области видимости.** Построение графа — отдельный метод
   (`_build_knowledge_graph_async`), имя `plog` конвейера в него не видно → `NameError`,
   шаг `graph_triage` не попадал в журнал, а сообщение в логе врало: «триаж пропущен»,
   хотя триаж сработал (fail-open поймал ошибку уже ПОСЛЕ вычисления). Теперь логгер
   передаётся параметром, а журналирование шага отделено от вычисления.

## Правила на будущее

* Fail-open (при сбое обработать всё) — правильно, но сбой обязан быть ГРОМКИМ: иначе
  «ничего не нашлось» неотличимо от «не смог прочитать». Пишем причину в журнал обработки,
  а не только в общий лог приложения.
* Журналирование результата — отдельно от вычисления: сбой записи шага не должен
  маскировать работу шага.
* После интеграции модуля с внешним API (Qdrant) — сначала дымовой вызов на живых данных,
  потом выводы. Оба сбоя id/вектора нашлись только живым прогоном.
