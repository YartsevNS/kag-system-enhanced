# Обработка документов: загрузка без автозапуска + блокировка

Фича (2026-08-28): загрузка документа через API/UI создаёт файл и миниатюру,
но НЕ запускает обработку автоматически. Обработка (OCR → чанки → векторы → граф)
запускается только кнопкой «Обработать» на странице «Документы»
(POST /api/v1/upload/{id}/process).

## Поведение

1. **Загрузка** (POST /api/v1/upload, /batch, /bulk, TUS) — документ сохраняется,
   статус `pending`, в Celery НЕ ставится. Обработка отложена.
2. **Общая кнопка «Обработать все необработанные»** — под панелью
   «Права доступа к документам» на странице «Документы» (видна, если есть
   необработанные документы пользователя). Ставит в очередь ВСЕ свои
   документы со статусом `pending`/`failed` одним нажатием.
3. **Многопользовательность** — process/process-all обрабатывают ТОЛЬКО
   документы текущего пользователя (`uploaded_by == id`); админ — любые,
   системные документы без владельца — только админу/процедурой web_monitor.
   Чужой пользователь получает **403**
   «Недостаточно прав: можно запускать обработку только своих документов».
4. **Блокировка из админки** — ДВЕ независимые галочки:
   - **«Обработка документов»** (`system`/`processing` = `{blocked, message}`):
     запрещает ЗАПУСК обработки уже загруженных документов.
     При `blocked=true`:
     - кнопка «Обработать» disabled (с подсказкой);
     - POST /{id}/process → **423** «Обработка заблокирована администратором...»;
     - POST /reprocess-pending → **423**;
     - на странице «Документы» — жёлтый баннер «Обработка после загрузки может
       не начаться — в связи с блокировкой на техническое обслуживание...».
   - **«Загрузка документов»** (`system`/`uploads` = `{blocked, message}`,
     с 2026-09-12): запрещает ПОСТУПЛЕНИЕ новых документов из ВСЕХ источников —
     ручную загрузку из UI/API, парсинг сайтов (watched_urls) и RSS.
     При `blocked=true`:
     - POST /api/v1/upload, /batch, /bulk → **423** с кодом `UPLOADS_BLOCKED`;
     - `web_monitor.run_check()` пропускает обход источников целиком
       (в логе: «загрузка документов отключена (...) — проверка источников пропущена»);
     - на странице «Документы» — красный баннер, зона загрузки приглушается,
       попытка загрузки отклоняется с тостом.
   Обе настройки независимы: можно запретить приём новых документов, но
   дообработать уже загруженные (и наоборот).

   Единая точка контроля загрузки — `document_service.upload_document()`
   (через `src/api/services/ingest_guard.py`): туда приходят все пути
   (UI/API, парсер сайтов, RSS), поэтому запрет нельзя обойти новым
   источником. Ошибка чтения настройки запрет НЕ включает — недоступная БД
   не должна блокировать систему сама собой.

## Эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| GET | /api/v1/admin/models/processing-config | {blocked, message} — блокировка ОБРАБОТКИ |
| POST | /api/v1/admin/models/processing-config | сохранить блокировку обработки (admin) |
| GET | /api/v1/admin/models/ingest-config | {blocked, message} — блокировка ЗАГРУЗКИ |
| POST | /api/v1/admin/models/ingest-config | сохранить блокировку загрузки (admin) |
| POST | /api/v1/upload/{id}/process | запустить обработку одного документа (403 чужому, 423 при блокировке) |
| POST | /api/v1/upload/process-all | обработать ВСЕ необработанные документы текущего пользователя (423 при блокировке) |

⚠️ Путь называется `ingest-config`, а НЕ `upload-config`: `/upload-config`
уже занят настройкой разрешённых форматов файлов (GET/POST), поэтому новый
роут там же был бы затенён старым (совпадающий путь + метод — побеждает
зарегистрированный первым).

## Удаление документа — консистентное (2026-08-28)

DELETE /api/v1/upload/{id} удаляет ВСЕ следы документа атомарно:
БД (DocumentRepository) + векторы (Qdrant, filter по document_id) +
граф (Neo4j clear_document) + файл uploads + OCR/Markdown + миниатюру.
Отзыв Celery-задач (revoke) + удаление из кэша.

- delete_document НЕ зависит от кэша: если записи нет в памяти — берёт из БД;
  если и там нет — всё равно чистит Qdrant/Neo4j (осиротевшие данные). Идемпотентно.
- Перед удалением из Qdrant вызывается embeddings_service.initialize() —
  иначе клиент None и векторы остаются (влияют на ответы RAG!).
- Проверка владельца: удалять можно только свои документы (403 чужому,
  401 без токена); админ — любые.
- delDoc в documents.html проверяет ответ и показывает ошибку, если удаление не прошло.

Проверено на проде: загрузка → обработка → Qdrant/БД/файл/миниатюра есть →
DELETE чужим 403 → DELETE владельцем 200 → БД/Qdrant/файл/миниатюра чисто.

## Просмотр документа: текстовый слой PDF (2026-09-12)

PDF в системе НЕ пересобирается: исходный файл сохраняется как есть в
`data/uploads/<document_id>_<имя>.pdf` и отдаётся как есть —
`GET /api/v1/upload/{document_id}/preview` (он же за кнопкой «Скачать»).
Обработка (OCR, парсинг, чанки) файл не перезаписывает, поэтому текстовый слой
исходника сохраняется. Проверка на ec288909: у файла на диске 50 страниц и
119 798 символов текста, у того же PDF из `/preview` — те же 119 798.

Значит «PDF без текстового слоя» — это не про файл, а про отображение.
Просмотрщик (`src/api/static/viewer.html`, pdf.js 3.11.174) раньше рисовал
только канвас: текст нельзя было выделить, скопировать, и его не находил
браузерный Ctrl+F. Теперь страница — это контейнер `.pdf-page` с канвасом и
прозрачным текстовым слоем поверх, построенным по тому же viewport.

Две тонкости этой сборки pdf.js (проверено на стенде с реальным PDF):

- класс `pdfjsLib.TextLayer` в бандле НЕ экспортирован (строка есть, объекта
  нет) — фактически работает откат на `pdfjsLib.renderTextLayer`;
- промис этой задачи ждать нельзя: если он не разрешится, `await` подвесит
  остаток `renderPage` (номера страниц, кнопки). Отрисовку не ждём, ошибки
  только логируем.

Быстрая проверка, что слой есть (эндпоинт требует авторизацию — без токена
вернётся 89 байт JSON с ошибкой `AUTH_*`, и pymupdf скажет «no objects found»):

```
TOKEN=$(curl -s -X POST http://localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d "{\"username\":\"admin\",\"password\":\"$ADMIN_PASSWORD\"}" \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
curl -s -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/upload/<document_id>/preview -o data/_check.pdf
docker exec kag-api python -c "
import pymupdf; d = pymupdf.open('/app/data/_check.pdf')
print(d.page_count, sum(len(p.get_text()) for p in d))"
```

Проверено 2026-09-12 на ec288909: исходник и `/preview` — по 50 страниц и
119 798 символов, текст начинается одинаково.

## Примечания

- Внутренние загрузки (web_monitor → document_service напрямую) НЕ затронуты:
  они обрабатывают сразу, минуя API.
- Админские инструменты (reindex, reprocess-ocr) блокировкой НЕ ограничены —
  блокировка только для пользовательского запуска со страницы «Документы».
