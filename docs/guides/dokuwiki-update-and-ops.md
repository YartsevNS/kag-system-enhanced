# DokuWiki на нашем сервере: обновление и работа (регламент)

Документ написан ДО первого входа на сервер — по официальной документации
([install](https://www.dokuwiki.org/install), [install:upgrade](https://www.dokuwiki.org/install:upgrade),
[requirements](https://www.dokuwiki.org/requirements), [devel:xmlrpc](https://www.dokuwiki.org/devel:xmlrpc)).
После входа сюда добавляются факты нашей установки (версия, PHP, способ установки, плагины) — до этого
шаги считать предварительными.

## 1. Главное свойство DokuWiki, из которого следует порядок работ

Обновление — это **распаковка новой версии ПОВЕРХ старой**. Файлы самой вики перезаписываются, а данные
(`data/`), настройки (`conf/*.local.php`) и плагины/шаблон при этом не теряются: именно поэтому
официальная инструкция советует перезапись, а не «чистую установку с переносом».

Что это значит для нас: обновление безопасно и обратимо, если перед ним снят снимок/бэкап, а настройки
лежат в `*.local.php` (их правит и встроенный менеджер настроек — он так делает сам).

## 2. Что проверить ПЕРЕД обновлением (в этом порядке)

1. **Версия PHP.** Актуальный стабильный релиз требует **PHP 8.2+**; PHP ≤7.4 снят с поддержки. Если вики
   живёт на старом PHP, порядок работ меняется: сначала PHP (и, возможно, ОС), потом вика.
2. **Текущая версия DokuWiki** — файл `VERSION` в каталоге установки; сравнить со свежим релизом.
3. **Способ установки.** Если вики ставилась пакетным менеджером системы — обновлять ТОЛЬКО им
   (`apt`/`dnf`), ручная перезапись сломает учёт пакетов.
4. **Плагины и шаблон.** После смены мажорной версии часть плагинов несовместима; список установленного
   взять из `lib/plugins/` и из менеджера расширений.
5. **Права и владелец** каталогов `data/`, `conf/`, `lib/plugins/` — веб-серверу нужна запись.
6. **Снимок/резервная копия** — обязательна (владелец снимает снимок машины; плюс архив каталога вики).

## 3. Порядок обновления (официальный, адаптированный)

```
# 1) требования
php -v                                   # нужен 8.2+
# 2) резервная копия каталога вики
tar zcpfv dokuwiki-backup-$(date +%F).tar.gz /путь/к/dokuwiki
# 3) прочитать список изменений версии (особые требования: новые каталоги с правами записи и т.п.)
# 4) скачать свежий релиз с официального сайта
# 5) распаковать и наложить поверх (сохраняя права и владельца)
tar zxvf dokuwiki-*.tgz
cp -af dokuwiki-*/ *  /путь/к/dokuwiki/
# 6) проверить права и владельца скопированного
# 7) удалить файлы, которых нет в новой версии
# 8) обновить шаблон и плагины, если нужно
# 9) очистить кэш; при необходимости пересобрать поисковый индекс
```

Откат: развернуть архив из шага 2 (или снимок машины) — данные не теряются, так как обновление их не
касается.

## 4. Проверка ПОСЛЕ обновления

* Открывается главная страница, вход работает, правка страницы сохраняется.
* **Поиск что-то находит** (если нет — пересобрать индекс: это типовая проблема после обновления).
* Панель инструментов редактора на месте (тоже типовая поломка — лечится очисткой кэша браузера и кэша вики).
* Уведомление о доступном обновлении исчезает (может занять до суток).
* В логах веб-сервера и PHP нет предупреждений о правах/отсутствующих каталогах.
* Плагины: каждый из тех, что реально используются, открыть и проверить (несовместимые отключаются).

## 5. Наш раздел: как устроим

* Отдельное пространство имён, например `:kag:` — страницы наших разборов; внутри — разделы по темам
  (`:kag:граф:`, `:kag:ocr:`, `:kag:разметка:`, `:kag:деплой:`) и хронологический журнал сессий.
* Темы выбираем как ОСНОВНУЮ навигацию (по ним ищут), даты — как журнал (по ним вспоминают «когда»).
  Просто «одна страница на сессию» поиск не улучшает: искать будут по теме, а не по дате.
* Каждая страница: дата, коммит, что сделано, почему так, что отвергли, чем проверено. Ссылки на скиллы и
  на разделы проекта — вместо копирования процедур в вики.
* Доступ: редактирование — владелец и агент; чтение — по решению владельца (ACL задаётся по пространству имён).

## 6. Автоматическое наполнение (XML-RPC)

У DokuWiki есть XML-RPC (Wiki RPC 2.0 + собственные методы). Запись страницы — вызов вида
`core.savePage(имя_страницы, текст, комментарий_правки, minor)`; чтение — `core.getPage`. Этого достаточно,
чтобы перенести 165 блоков «вопрос → ответ» из `know.html` и наполнять вики из сессий, не заливая руками.

Условия: на сервере разрешён XML-RPC и есть пользователь с правом записи в наше пространство имён.
Скрипт переноса: `scripts/bakeoff/know_to_dokuwiki.py` (появится после входа и проверки доступа).

### Что из этого следует: обновление упирается в PHP

Текущая версия вики требует PHP 7.4+ и на 7.4 работает штатно. Свежий релиз «Mort» требует **8.2+**.
Значит порядок работ: **сначала PHP, потом сама вики**, и выбор пути по PHP — решение владельца:

* **Путь A (рекомендую): обновить ОС Debian 11 → Debian 12.** В 12-й версии PHP 8.2 «из коробки», и
  заодно возвращаются обновления безопасности: bullseye (11) свою поддержку LTS завершил в августе 2026.
  Цена — полноценный апгрейд дистрибутива на ВМ с 2 ядрами; откат — снимок и архив.
* **Путь B: оставить Debian 11 и подключить сторонний репозиторий PHP (deb.sury.org)**, поставить PHP 8.2
  или 8.3 рядом с 7.4 и переключить nginx на новый сокет. Меньше риска «здесь и сейчас», но ОС остаётся
  без обновлений безопасности, а в системе появляется третий источник пакетов.

После PHP — наложение «Mort» (официальный способ: распаковка поверх, данные и настройки не трогаются),
затем проверка плагинов и шаблона bootstrap3 (он сторонний, от февраля 2024 — совместимость проверять
менеджером расширений), очистка кэша, пересборка поискового индекса и проверка входа/страниц/медиа.

### Особенности перехода на «Mort» (из официального списка изменений)

1. **Минимум PHP 8.2** — причина всей работы.
2. **Полностью переписан полнотекстовый поисковый индекс** → после наложения индекс обязательно
   пересобрать (`php bin/indexer.php -c`), иначе поиск молчит.
3. **У блоков кода/файлов появилась своя кнопка «копировать»**, а плагины, которые делали это раньше,
   «как минимум избыточны, а то и несовместимы». У нас стоят ровно такие: **`copycode`,
   `codebuttonmod1`** — при странном поведении страниц их отключать первыми.
4. Изменён разбор синтаксиса (мелкие правки на страницах возможны), переработаны внутренности
   парсера: плагины, добавляющие свои режимы, могут требовать обновления; часть устаревших функций
   поиска и парсера удалена.
5. Новый параметр `client_ip_header` заменяет старый `realip` — проверить `conf/local.php`, если `realip`
   там задан.
6. Патчи a/b/c — исправления безопасности, поэтому целимся именно в **2026-07-14c**.

### Что доделать при выполнении

1. Точный `fastcgi_pass` из конфига nginx (нужен для переключения FPM на новую версию PHP).
2. Версии плагинов и шаблона — через менеджер расширений (в `plugin.info.txt` версия лежит не там, где я искал).
3. Проверить, что вики открывается на новой версии PHP ДО наложения «Mort» (тогда окно недоступности минимально).
4. Включить XML-RPC и создать пространство имён `:kag:` для нашего раздела.
