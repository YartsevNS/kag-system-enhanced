# Разбор плана «12 этапов» (внешнее предложение) против нашей системы

Дата: 2026-11-13. Источник предложения: чат внешней модели (DeepSeek share of4z8nxgs1q5qvf3vm).
Проверка: по нашему коду и замерам, а не по описанию. Доступ к серверу 192.168.50.18 в момент
разбора пропал (SSH: connection refused), поэтому конфигурация цитируется по логам этой сессии.

## Короткий вывод

Направление верное, три критических замечания по существу верны (нет структурного скелета,
нет отдельного слоя нормализации/разрешения, извлечение и запись смешаны). Но фактические
посылки плана про нашу систему в четырёх местах неверны, а два его «первых шага» нам уже
не нужны и были бы шагом назад.

## Где посылки плана не про нас

| Утверждение плана | Что у нас фактически |
|---|---|
| «чанки по 1500 **токенов**, а контекст эмбеддинга 512 → Qdrant теряет смысл» | чанк — **1500 символов** (LangChain `RecursiveCharacterTextSplitter`, overlap 225; лог: «chunk_size=1500, overlap=225»). Модель — Giga-Embeddings (dim **2048**, контекст 2560). Расхождение «512 vs 1500» относится к базовой GigaChat-модели, а не к нашей |
| «чанки в Qdrant только с текстом и вектором» | payload уже содержит: `document_id`, `chunk_id`, `chunk_type`, `content`, `document_type`, `domain`, `collection`, `created_at`, `file_type`, `allow_user_ids`, `deny_user_ids`, `allow_group_ids`, `deny_group_ids` (проверено выборкой payload) |
| «нужны named vectors для гибрида» | гибрид уже есть: dense + sparse BM25 + RRF; в коллекции два векторных поля |
| «батчинг 100–1000 запросов на транзакцию уберёт необъяснённые накладные» | накладные были не из-за отсутствия батчей: `_read()` открывал новый драйвер TypeDB на **каждый** запрос (43 запроса на фрагмент, ~79 мс на драйвер). После правки запись = **8,5 с на документ** из 321 фрагмента (было 1531 с). Батчинг дал бы единицы процентов |
| «worker берёт чанки из Qdrant» | основной поток чанкует из парсера в памяти; чтение из Qdrant — только для режима «пересобрать онтологию по готовым чанкам» |
| «чанки обрабатывать последовательно, иначе якоря потеряются» | замер 13.11.2026: параллельность 3 → 8,8 мин на документ, 6 → 5,2 мин; выход **не зависит** от параллельности (108/258/151 против 110/271/154 на одном документе; парный замер на СТО БР при 3 и 6 дал одинаковую картину) |

Отдельно: «специализированная модель, которая понимает абзацы» — у нас уже есть слой разделов

`structural_element`. То есть скелет не «отсутствует», он есть, но не в виде полного
structural_path и не в payload.

## Что стоит взять (по приоритету)

**P1. Полный структурный путь в payload (structural_path).** Дешёво: `section_parser` уже знает
разделы, пункт уже в `struct_index`. Нужно: собрать путь «раздел → пункт → подпункт» и положить
в payload `structural_path` + `source_kind`. Даёт фильтры поиска и основу для блокировки.
Цена: день. Эффект: поиск/фильтры + будущая дедупликация.

**P2. Разделение Bronze / Silver / Gold.** Сейчас извлечение сразу пишет в TypeDB, поэтому:
повторная нормализация невозможна без повторного вызова модели, аудит решений негде хранить,
а ошибка извлечения сразу попадает в «золотую» базу. Предложение: сырое извлечение складывать
в отдельную таблицу (Postgres, JSONB: ent_key-кандидат, тип, атрибуты, цитата, chunk_id,
structural_path), затем нормализация/дедуп/линковка — детерминированно, и только потом TypeDB.
Цена: 3–5 дней. Это самый большой архитектурный сдвиг из плана и он обоснован.

**P3. Лестница дедупликации с conflict guard.** Сейчас работает только точное совпадение ключа.
Для корпуса из 86 документов этого мало: разные написания кода (АВЗ.1 / АВЗ-1), разные формы
одной меры. Взять шаги 2–3 (fuzzy внутри блока, эмбеддинги) с запретом слияния при конфликте
атрибутов и с порогами: regulator строже, users мягче. Пограничные — в human-in-the-loop
(у нас уже есть механика очередей и авто-решений с отзывом).

**P4. Проверка омонимии при линковке.** «Проверка» может быть требованием и мерой; сейчас
`ent_key` включает тип, поэтому коллизии типов нет, но линковка по имени без типа опасна.
Взять как правило: имя без ключа → кандидат, а не слияние.

**P5. Метрики качества извлечения и дедупа.** Нужна размеченная выборка: 30–50 фрагментов
с ожидаемыми сущностями/связями, precision/recall по типам. Без этого любые изменения —
вкусовщина (сегодняшний день это показал: вариативность больше эффекта).

## Что не брать сейчас (и почему)

- **Последовательная обработка чанков ради якорей.** Замер против: ×2 времени, выход не растёт.
  Якоря можно передавать и при параллельности (по структурному порядку внутри пачки), если
  понадобятся.
- **Батчинг записи в TypeDB.** После починки драйверов запись 8,5 с на документ — не узкое место.
- **Переход чанкинга на границы пунктов.** Дорого: это переиндексация всего корпуса
  (эмбеддинги + Qdrant + онтология). Делать только если замер покажет, что границы пунктов —
  реальная причина потерь. Сейчас причина потерь другая (см. ниже).
- **Named vectors, payload-поля, идемпотентность** — уже есть.

## Чего в плане нет, а у нас это главная проблема

Стабильность извлечения. Один и тот же документ (СТО БР БФБО, 182 фрагмента) при одном и том же
коде даёт 7 / 4 / 25 элементов и 0–10 требований за прогон; 121–131 фрагмент из 182 возвращают
пустой JSON, при этом ошибок и таймаутов ноль. На табличных документах выход в разы ниже, чем
на прозаических (fstek-2014: 108–110 мер / 258–271 требование стабильно).

План из 12 этапов этого не лечит: он весь про то, что делать с уже извлечёнными фактами. Пока
извлечение нестабильно, ни нормализация, ни дедупликация не дадут предсказуемого результата —
сравнивать нечего.

## Порядок внедрения, который я предлагаю

1. Стабильность извлечения (техдолг п.20): разобрать пустые ответы, проверить подачу таблиц
   в промпт, при необходимости — повтор для пустых фрагментов. Без этого нет смысла в остальном.
2. Bronze-слой и structural_path (P1+P2) — они дают основу для всего остального и не требуют
   переиндексации корпуса.
3. Лестница дедупликации (P3+P4) с аудитом, как в наших авто-решениях.
4. Метрики (P5) — до и после каждого шага.
