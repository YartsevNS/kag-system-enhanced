# Гид: чат с документами

> Актуально на 2026-08-23.

## Архитектура

- **Backend:** `src/api/routes/chat.py`, `src/api/services/chat_service.py`, `src/api/services/chat_storage.py`.
- **Frontend:** `src/api/static/chat.html`.
- **Серверные сессии** (авторизованные): `chat_sessions` / `chat_messages` (SQL, FK users, cascade, проверка владельца).
- **Анонимы:** localStorage fallback (история для LLM из тела запроса).
- **401 для анонимов** на /api/* — by design (security middleware требует JWT).

## Маршрутизация интента

`_detect_meta_intent(query)` в chat_service.py — до RAG:
- **count** («сколько документов») → SQL count, без списка (stats_line).
- **list** («перечисли документы») → SQL список, **limit 25** (для не-админов фильтр по группам).
- **semantic** (всё остальное) → RAG по Qdrant.
- `intent` возвращается в metadata ответа.

**Почему:** deepseek-v4-flash даёт ПУСТОЙ ответ при промпте >~3К токенов (список 60 доков ≈ 3400 токенов) и при max_tokens <500. Фронтенд шлёт max_tokens=2048.

## Анализ домена (Query Routing)

Мелкая модель-классификатор (function_map/query_analysis) определяет домен вопроса ДО основного LLM.

- **Функция:** `query_analysis` в Provider Architecture (админка → Провайдеры → «Анализ запросов»).
- **Провайдер:** llama.cpp (тип `llamacpp`) — http://192.168.50.41:8081 (llama-server, systemd-сервис, MiniCPM5-1B-Q4_K_M, --jinja, 8 потоков).
- **Промпт:** system_prompt функции = пары «вопрос → домен» (few-shot). Дефолт: `prompts/query_analysis.txt`.
- **Код:** `chat_service._detect_query_analysis()` (async) — вызывается в generate_response после `_detect_meta_intent`, до RAG. Парсит домен из ответа модели (приоритет — текст после `</think>`).
- **Результат:** `metadata.domain` в ответе чата (legal/medical/technical/infosec/accounting/universal/...). Если функция не настроена — чат работает как раньше (None, без задержки).
- **Назначение (следующие шаги):** фильтр RAG по document_type, выбор словаря алиасов по domain, схема графа.

**Питфоллы:**
- URL провайдера для OpenAI-совместимых БЕЗ `/v1` (chat_service._call_llm добавляет `/v1/chat/completions` сам). У ollama URL тоже без /v1.
- llama-server (llama.cpp) слушает `0.0.0.0:8081` — иначе с другого хоста недоступен.
- MiniCPM5-1B думает вслух (`<think>...</think>`), итоговый домен — в конце ответа; парсер берёт последнее вхождение после `</think>`.
- httpx 0.28: `resp.text` — свойство (str), не метод: `await resp.text()` даёт `'str' object is not callable` (был баг в _call_llm, исправлен).

## Формат ответа: без markdown-мусора (2026-09-12)

Симптом: в ответах чата видны «**жирный**» и «## Заголовок».

Причины, две и обе разные:

1. модель (deepseek-v4-flash) отвечает в markdown — это привычка модели, а не
   требование нашего промпта. Промпт `prompts/chat.txt` правился (явный раздел
   «ФОРМАТ ОТВЕТА (важно)»: без `**`, без `#`, без ``` и таблиц), но замер на
   3 вопросах после смены промпта дал 54 маркера — инструкцией это не лечится;
2. чат выводил ответ как обычный текст (`escapeHTML`), поэтому разметка
   показывалась символами.

Как сделано: разметку разбирает интерфейс — `formatMessageText()` в
`chat.html`. Сначала экранируется ВЕСЬ ответ, затем по строкам применяется
узкий набор: `#{1,6}` → блок `.msg-h`, `**…**`/`__…__` → `<strong>`,
`*…*` → `<em>`, `` `…` `` → `<code>`, `- `/`* `/`+ ` → `<ul>`, `1)` → `<ol>`,
`---` → `<hr>`. HTML из ответа модели не исполняется (проверено тестом с
`<script>` и `<img onerror>`).

Промпт при этом оставлен «просим без разметки» — это уменьшает мусор, но
полагаться на него нельзя.

Где живёт промпт (обновлено 2026-09-12). Раньше живой промпт брался из файла
репозитория `prompts/chat.txt` (каталог проброшен в контейнеры), а в настройках
(`function_map/<функция>.system_prompt`) было пусто — из-за этого админка
показывала файл как «сохранённый» промпт, а правка из неё молча создавала вторую
версию. Теперь:

- при старте api промпты `prompts/*.txt` засеваются в настройки, если там пусто
  (`provider_service.seed_prompts_from_files()`, вызывается в lifespan; в логах —
  строка «Промпты засеяны из файлов в настройки: …»). Уже отредактированный
  промпт НЕ затирается: файл — версионируемый дефолт, а не источник правды;
- источник виден в ответе API: `prompt_from_settings` (true — используется версия
  из настроек) и `prompt_file` (путь к файлу). В админке то же показано в списке
  функций и в модалке настройки;
- правка из админки действует сразу (проверено: дописанная в промпт инструкция
  появилась в ответе чата, возврат — кнопкой «Взять из файла репозитория»);
- подтянуть файл в редактор без записи:
  `GET /api/v1/admin/models/functions/<функция>/prompt-from-file`; загрузить файл
  в настройки из консоли — `scripts/set_chat_prompt.py prompts/chat.txt`.

Проверка: `scripts/e2e_admin_prompt_edit.py` (Playwright) — весь цикл в браузере.
Формат ответа (без `**` и `##`) проверяет `scripts/e2e_chat_format.py`.

## Отбор фрагментов и глубина контекста: два рычага ответа (2026-09-20)

Коротко: **глубина** решает, сколько фрагментов вообще попросить у поиска, **отбор** — сколько
из них пустить в ответ. Оба параметра настраиваются в привязке функции chat, оба доступны
пользователю в чате (в ограниченном диапазоне) и оба меняются только по замеру.

### Путь фрагмента до ответа

1. поиск (вектор + реранк) возвращает `context_limit` фрагментов — это и есть «глубина»
   (по умолчанию 10, допустимо 3..20);
2. отсечение по релевантности `min_score_gap` выбрасывает фрагменты, которые отстают от
   лучшего больше чем на заданную величину (минимум 3 фрагмента остаются всегда);
3. оставшиеся идут в ТРИ места сразу: в промпт модели, в список источников под ответом
   и в блок таблиц интерфейса. Поэтому отсечение убирает мусор и из ответа, и с экрана.

### Что значит число min_score_gap (легко перепутать!)

Число — это **допустимое отставание от лучшего фрагмента**, а не «строгость». То есть:

| Значение | Что остаётся | Когда уместно |
| :-- | :-- | :-- |
| 0 | всё, что вернул поиск | «выключено», только админ, для отладки |
| 0,02 | только почти неотличимое от лучшего (1–3 фрагмента) | узкий точный вопрос по одному документу |
| 0,03 | самая близкая группа | однородные корпуса: ГОСТы, финансовые обзоры, инструкции |
| 0,05 | близкая группа, чужие документы отрезаны | встроенный дефолт, если домен неизвестен |
| 0,05–0,08 | близкая группа шире | разнородные тексты (статьи, общие документы), universal = 0,08 |
| 0,08–0,12 | заметно больше фрагментов | вопросы, где нужно свести сведения из нескольких документов |
| 0,15 и выше, 0,20 | почти вся выдача | смысла почти нет: мусор возвращается, экономия исчезает |

Правило: **меньше значение = строже отбор**. Первая версия подписей в интерфейсе была
перевёрнута (0,02 называлось «мягко»), поэтому в коде есть тест `test_smaller_gap_is_stricter`.

### Не путать с порогом отказа

- `min_score_gap` (отбор) — сколько фрагментов уходит в ответ: объём, чистота, цена;
- `min_top_score` (отказ) — если ЛУЧШИЙ фрагмент слабее порога, система честно отвечает
  «в загруженных документах информация не найдена» и НЕ вызывает модель. Это про «есть ли
  ответ в корпусе вообще». По умолчанию выключен (0): замер 18.09.2026 показал, что вопрос
  вне корпуса может дать высокий score, и порогом легко наврать.

### Что дал замер (20.09.2026, набор 75 вопросов Википедии + 33 запроса финкорпуса)

Сколько посторонних фрагментов убирает отсечение и не теряем ли нужное:

| Отсечение | Убрано мусора (тексты) | Убрано мусора (финкорпус) | Потерян нужный источник |
| :-- | :-- | :-- | :-- |
| 0,05 | 83% | 26% | 0 из 74 / 0 из 29 |
| 0,10 | 67% | 2% | 0 из 74 / 0 из 29 |
| 0,15 | 41% | 0% | 0 из 74 / 0 из 29 |
| абсолютный 0,75 | 83% | — | уже 2 из 74 (не годится) |
| абсолютный 0,85 | 95% | 59% | 3 из 74 (не годится) |

Почему абсолютный порог не подходит: он не переносится между доменами. На текстах посторонний
фрагмент отстаёт от нужного примерно на 0,10 (его видно), а на финкорпусе — всего на 0,02
(похожие по стилю документы), поэтому там работает только жёсткое отсечение 0,02–0,03.

Что происходит с ответом и деньгами (75 вопросов, глубина 10, по одному прогону):

| Отсечение | Верных ответов | Источников | Контекст | Токенов промпта | Медиана |
| :-- | :-- | :-- | :-- | :-- | :-- |
| выключено | 58/75 = 0,773 | 10,0 | 11 911 симв. | 6 183 | 3,7 с |
| 0,05 | 56/75 = 0,747 | 7,3 | 8 718 симв. | 4 849 (−21,6%) | 3,5 с |
| 0,10 | 55/75 = 0,733 | 8,7 | 10 435 симв. | 5 655 | 3,6 с |

Разница по точности лежит внутри шума набора (±4–5 вопросов), то есть отсечение **точность
не меняет** — оно меняет чистоту ответа и цену. Промпт — это около 90% стоимости запроса,
поэтому −21,6% промпта ≈ −20% к цене вопроса; на вопросах, куда раньше попадал мусор,
экономия доходит до 42% (живой пример: контекст 12 585 → 6 299 символов, промпт
7 447 → 4 325 токенов, источников 10 → 4).

### Что лучше для ответа

- нужен исчерпывающий, но чистый ответ (обычный случай): 0,05–0,08 для текстов, 0,03 для
  однородных корпусов — вся «своя» группа фрагментов остаётся, чужие документы отрезаются;
- нужен максимально дешёвый и узкий ответ: 0,02–0,03 (риск: факт из второго документа
  можно потерять);
- вопрос требует свести несколько документов (сравнение, обзор требований): 0,08–0,12;
- 0 и 0,20+ — крайности без пользы: в первом случае мусор в ответе, во втором — то же самое,
  только выглядит как настройка.

### К чему приводит изменение (диагностика)

- стало больше отказов «информация не найдена» → отсечение слишком жёсткое (или сработал
  `min_top_score`): контекст схлопнулся, модели не хватило материала;
- в ответе появились документы, о которых не спрашивали (и «чужие» таблицы под ответом) →
  отсечение слишком мягкое;
- ответ потерял факт, который в документе есть → проверить, не отсекли ли фрагмент с фактом:
  `reports/_scratch/probe_fact_presence.py` (есть ли факт среди найденных фрагментов) и
  `probe_retrieval_misses.py` (на каком месте документ-источник);
- выросла цена или время → посмотреть объём контекста и токены промпта:
  `reports/_scratch/probe_question.py` (один вопрос целиком) и `compare_gap_runs.py` (сводка
  по проходам).

### Регуляторы в интерфейсе

- в чате: «Контекст» (глубина) и «Отбор фрагментов» (0,02–0,12). Крайние значения пользователю
  недоступны: выключить отсечение (0) или взять почти всю выдачу может только администратор;
- в админке (Модели LLM → функция chat): поле отсечения (0..0,30, 0 = выключено) и отдельные
  поля по доменам (`universal` 0,08, `legal` 0,05, `infosec`/`accounting` 0,03, `medical` 0,05);
- приоритет значения: запрос пользователя → привязка функции → доменный дефолт → встроенный 0,05.

### Промпт чата: исчерпывающе, но без болтовни (2026-09-20)

Симптом: ответ на 2 000+ символов, в котором полезное перемешано со служебной болтовнёй
(«согласно графу знаний, сущность связана с документами», «score 0.85» в каждой ссылке) —
это требование старого промпта, а не поведение модели.

Как сделано: `prompts/chat.txt` переписан — требуется исчерпывающий ответ по существу (все
относящиеся к вопросу числа, даты, номера пунктов, обозначения документов) и прямо запрещены:
рассказы про граф, score и confidence, вступления и заключения («Отличный вопрос», «Обратите
внимание», «Подводя итог»), повтор одной мысли, отчёт о том, что модель собирается сделать.
Ссылки на документы — кратко («по документу «Квитанции.pdf»»), без score и номеров источников:
список источников и так виден под ответом.

Важно: живой промпт берётся из настроек (привязка функции chat), а файл — только дефолт
(см. раздел «Формат ответа» выше): после правки файла нужно загрузить его в настройки —
`scripts/set_chat_prompt.py prompts/chat.txt` (на стенде — с паролем из `.env`).
