# Гид: оценка качества retrieval (поиска)

> Инструмент: `scripts/evaluate_retrieval.py` (только stdlib, без зависимостей).
> Зачем: любое изменение чанкинга, эмбеддингов, нормализации терминов или
> payload-фильтров должно подтверждаться цифрой, а не ощущением.

## Метрики

Для каждого вопроса набор запрашивает у поиска top-K и считает:

| Метрика | Что означает |
|---|---|
| `hit@K` | есть ли хоть один релевантный результат в первых K (0/1) |
| `recall@K` | какая доля релевантных документов попала в первые K |
| `precision@K` | какая доля из первых K оказалась релевантной |
| `mrr` | 1/позиция первого релевантного (0, если не найден) |
| `chunk_recall@K`, `chunk_mrr` | то же, но по конкретным чанкам (если размечены) |

В отчёте — метрики по каждому вопросу и средние по набору.

## Разметка релевантности

Релевантность документная (основной режим): указываете `relevant_document_ids` —
любой чанк из этих документов в топ-K считается попаданием. Если нужна
точность до пункта — дополнительно указываете `relevant_chunk_ids`.

## Пошагово

```bash
# 1. Какие документы есть в системе (для разметки) — нужен запущенный API
python scripts/evaluate_retrieval.py --list-documents

# 2. Создать рабочий набор (он в .gitignore — личные данные не коммитятся)
cp scripts/eval_questions.example.json scripts/eval_questions.json
#    заполнить query + relevant_document_ids по реальным вопросам

# 3. Прогон
python scripts/evaluate_retrieval.py --questions scripts/eval_questions.json

# 4. Сохранить отчёт для сравнения «до/после» изменения
python scripts/evaluate_retrieval.py --output reports/eval_before.json
#    (после правки — eval_after.json, затем сравнить aggregate)
```

На сервере 18 (API слушает 127.0.0.1:8000):

```bash
python3 scripts/evaluate_retrieval.py --url http://localhost:8000 --list-documents
python3 scripts/evaluate_retrieval.py --url http://localhost:8000 \
        --questions scripts/eval_questions.json --output /tmp/eval_after.json
```

Через внешний nginx (если открыт) — `--url https://qd.gostsecret.ru --insecure`.

## Сколько вопросов нужно

Для устойчивой оценки — 50–100 реальных вопросов, покрывающих разные типы:
точный номер ГОСТа, тематический вопрос, вопрос про пункт/требование,
вопрос по нескольким документам. Меньше 20 — метрика шумит.

## Как этим пользоваться

Правило: сначала «до», потом изменение, потом «после». Сравнивать `aggregate`:
если `recall@5` и `mrr` не выросли — изменение не улучшило поиск (даже если
код «красивее»). Регрессия по `hit@1` — повод откатить.

## Что важно при разметке

- Релевантность должна быть объективной: «этот документ действительно отвечает
  на вопрос», а не «в этом документе есть слово из вопроса».
- Один вопрос может иметь 2–5 релевантных документов — так честнее.
- Вопросы формулировать так, как спрашивают пользователи (в т.ч. коротко и
  с аббревиатурами: «ЗИ», «Пдн», «ГИС»), а не языком документа.
