# Синхронный I/O в async-коде: что закрыто и почему остальное не трогаем

Документ отвечает не на вопрос «сколько мест осталось», а на вопрос «почему это не
проблема». Инструмент: `scripts/scan_sync_io.py` (AST-разбор, сопоставление
вызовов по получателю — иначе `app.get`/`status.get` дают более тысячи ложных).

## Общее правило

Одинаковый вызов стоит по-разному в зависимости от места исполнения:

| Где исполняется | Цена блокировки | Что делать |
|---|---|---|
| процесс API (один event loop) | тормозит ВСЕ запросы | чинить |
| воркер Celery (solo-пул) | тормозит только свою задачу, а она и так одна за раз | не трогать |
| синхронный обработчик FastAPI (`def`) | FastAPI сам держит его в пуле потоков | `to_thread` не нужен и вреден |

## Главный SLA (замер, а не обещание)

**`/health` под нагрузкой чата — ≤ 10 мс.** Фактические замеры: 1.4–2.4 мс (запрос
RAG 5 с в фоне), 1.4–2.0 мс (RAG 0.48 с), 2.2–3.1 мс (запрос к Keycloak 0.39 с),
2.2–3.1 мс (работа сторожа типизации). Смысл не в том, что «чат стал быстрее», а в
том, что один работающий пользователь больше не останавливает систему: раньше
синхронный поиск в Qdrant держал event loop, и запросы выстраивались в очередь.

Как проверять (любой из случаев): запустить долгий запрос в фоне и в это время
мерить `/health`:

```bash
( curl -s -o /dev/null -w "долгий запрос: %{time_total}s
" -X POST     localhost:8000/api/v1/chat/search -H "Authorization: Bearer $TOK"     -H "Content-Type: application/json" -d '{"query":"..."}' ) &
sleep 1; for i in 1 2 3 4; do   printf "  /health %s s
" "$(curl -s -o /dev/null -w "%{time_total}" localhost:8000/api/v1/health)"; done; wait
```

## Разобрано построчно: `routes/upload.py` (19 мест)

Каждое место — с решением и цифрой. Обёртки здесь НЕ нужны: либо вызов дешёвый по
замеру, либо тяжёлая часть уже в потоке.

| Строка | Вызов | Решение |
|---|---|---|
| 703 | `extract_dir.mkdir` | один mkdir на запрос (~0.05 мс) |
| 716 / 752 | `zipfile.ZipFile(...)` / `tarfile.open(...)` | конструкторы поверх УЖЕ прочитанных байтов; тяжёлые `infolist`/`getmembers`/`extract` в потоке |
| 739 / 775 | `extracted_path.is_file` | stat локального файла |
| 1015 / 1064 / 1105 / 1303 / 1840 | `repo.get` / `get_dict` | SQL по PK — 1.3 мс (замер) |
| 1133 | `repo.upsert` | запись + commit — 5.0 мс (замер) |
| 1293 / 1357 / 1933 | `config_store.get` | кэш чтения — 0.007 мс |
| 1690 / 2043 / 2049 / 2070 / 2091 | `Path.exists` / `stat` (миниатюра, OCR-md) | один stat (~0.05 мс) |

Закрыто в этой же пачке: **4 × `get_doc_repo().get_all()`** (полное чтение таблицы в
async-роутах `process_all_mine`, `reprocess_pending_documents`, `reanalyze_all_documents`,
`reindex_all_documents`) → в поток. На 47 документах ~10 мс, но растёт линейно, а
роуты админские — тот же класс, что `scroll_points(50000)` в `/chunks`.

## Разобрано построчно: `routes/admin_models.py` (43 места — все обоснованы)

Правок не потребовалось: это административные роуты, и все находки либо уже в потоке,
либо дешёвые по замеру. Формат: место | вызов | замер | решение | почему.

### Группа 1. `config_store.get` — 23 места

Строки: 496, 730, 793, 1425, 1438, 1861, 1877, 1900, 1916, 1959, 1975, 2002, 2024, 2053, 2067, 2091, 2111, 2155, 2178, 2311, 2338, 2395, 2423

- **замер:** ≤ 0.3 мс (кэш чтения 2 с внутри хранилища; до кэша было 10.4 мс);
- **решение:** не оборачивать;
- **почему:** стоимость убрана в самом хранилище (см. выше), поэтому обёртка на 23 места
  была бы чистым churn. Важно: это НЕ то же решение, что «10.4 мс — короткий SELECT» —
  там цифра была снята замером и оказалась в 8 раз хуже ожидания, и лечилось это кэшем,
  а не отказом от обёртки.

### Группа 2. `config_store.set` — 18 мест

Строки: 513, 764, 795, 898, 1215, 1411, 1440, 1886, 1924, 1982, 2037, 2078, 2141, 2163, 2184, 2352, 2437, 2578

- **замер:** 3.8 мс (запись + commit, среднее из 5 на стенде);
- **решение:** не оборачивать;
- **почему:** вызывается по кнопке «Сохранить» в админке (одно действие человека), а не
  на каждый запрос. 3.8 мс на клик ничего не держат: соседние ожидания (перезапуск
  сервиса, ответ провайдера) на порядки больше. Для сравнения — `get` звался на КАЖДЫЙ
  запрос чата (85 мест в карте), `set` — редкое действие.

### Группа 3. `backup_documents` — 2 места

| Строка | Вызов | Замер | Решение | Почему |
|---|---|---|---|---|
| 2800 | `zipfile.ZipFile(tmp, "w", ...)` | конструктор ~0.1 мс | не оборачивать | тяжёлые `zf.write`/`zf.writestr` (по файлу и по разделу) уже через `to_thread`, обход каталога — в `_index_uploads()` через `to_thread`, `config_store.get_all` и `kg_service.list_alias_pairs` тоже |
| 2869 | `os.unlink(tmp_path)` | ~0.05 мс | не оборачивать | ветка ошибки (архив не собран), один unlink |

### Что проверил помимо карты (руками, по коду)

- **httpx в `admin_models.py`** (3 места: 626 `restart_ollama`, 1099 `_provider_balance`,
  1579 `test_provider_connection`) — везде `async with httpx.AsyncClient(...)` и `await`,
  то есть настоящий async-клиент. Скан их показывает как «http» из-за конструктора —
  это не находка.
- **`deploy_action`** — запись файла вложена в `_write_file()` и вызывается через
  `to_thread`; `subprocess.run` тоже уже `await asyncio.to_thread(...)`.
- **`update_worker_resources`** — только `config_store.set` (3.8 мс); применение
  ресурсов идёт при деплое, скрытого docker-вызова там нет.
- **`backup_documents`** — длинный запрос по замыслу (скачивание архива), но event loop
  не держит: всё тяжёлое в потоке.

## Остаток: 166 мест, из них по видам

Первый порядок карты (258 вызовов) разобран и закрыт. Остаток измерен заново после
двух ужесточений скана: (1) вызовы внутри `to_thread(lambda: ...)` больше не находки;
(2) вызовы внутри вложенных синхронных функций, переданных в `to_thread` — тоже
(пример ложной находки: `queue_status` → `_inspect()` → `celery control.inspect`).

| Вид | Мест | Обоснование |
|---|---|---|
| `config_store` (БД) | 85 | теперь 0.007 мс из кэша — блокировки нет |
| `Path`: проверка (`exists`/`is_file`) | 32 | один `stat` локального файла ≈ 0.05 мс |
| БД: репозиторий документов | 18 | чтение по PK 1.3 мс, запись 5 мс — не в горячем пути |
| `Path`: изменение ФС (`mkdir`/`unlink`) | 13 | локальные операции в нечастых роутах |
| криптография | 12 | чистая CPU, без ожидания |
| `open()` | 10 | локальные файлы, TUS/OCR |
| `kg_service` (Neo4j) | 5 | остаток в `/kg`-статусах — к разбору в следующей пачке |
| прочее (архивы, `celery inspect`, urllib) | 11 | часть уже в обёртках, часть — к разбору |

По файлам, крупнейшие: `admin_models.py` 43 (разобран построчно ниже), `upload.py` 19
(разобран построчно выше), `document_service.py` 16 (воркер),
`web_monitor.py` 15 (блокирующий fetch уже в `run_in_executor`), `main.py` 14
(проверки ФС на страницах ≈ 0.05 мс), `routes/knowledge_graph.py` 11.

Честная оговорка: по `admin_models.py` и остатку `upload.py` построчный разбор с
одной строкой обоснования на каждое место ещё не закончен — сейчас обоснование дано
на уровне вида вызова (замер выше). Это следующая пачка работ.

## Как перепроверить

```bash
python scripts/scan_sync_io.py src   # 166 мест (было 258)
```

Скрипт намеренно не знает про «разрешённые» случаи — он показывает все места.
Правило: прежде чем оборачивать, посмотреть, откуда функция вызывается (процесс API
или воркер) и сколько стоит сам вызов (замер, а не догадка).
