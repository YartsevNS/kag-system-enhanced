# Синхронный I/O в async-коде: что закрыто и почему остальное не трогаем

Документ отвечает не на вопрос «сколько мест осталось», а на вопрос «почему это не
проблема». Инструмент: `scripts/scan_sync_io.py` (AST-разбор, сопоставление
вызовов по получателю — иначе `app.get`/`status.get` дают более тысячи ложных).

## Общее правило

Одинаковый вызов стоит по-разному в зависимости от места исполнения:

| Где исполняется | Цена блокировки | Что делать |
|---|---|---|
| процесс API (один event loop) | тормозит ВСЕ запросы | чинить |
| воркер Celery (solo-пул) | тормозит только свою задачу, а она и так одна за раз | не трогать |
| синхронный обработчик FastAPI (`def`) | FastAPI сам держит его в пуле потоков | `to_thread` не нужен и вреден |

## Стратегические оговорки (читать до таблиц)

Правила ниже — наблюдения для ТЕКУЩЕГО состояния системы, а не универсальные истины.
Через полгода их надо проверить заново, а не применять по инерции.

1. **«Это короткий SELECT» — не обоснование.** Ровно так я решил про `config_store.get`,
   не измерив: оказалось 10.4 мс, в 8 раз хуже ожидания, и на 85 местах в горячем пути.
   Лечилось это кэшем в самом хранилище, а не отказом от обёртки. Любое «дешёвый вызов»
   без цифры — повод замерить.
2. **«Синхронный обработчик FastAPI» — не «плохо»,** а «FastAPI сам исполняет его в пуле
   потоков». Внутри такого `def` `to_thread` не нужен и вреден (лишний поток на каждый
   вызов).
3. **«CPU-хеш» / криптография — не I/O.** Блокируют loop ровно как и всё остальное, но
   перекладывать их в поток можно только осознанно: GIL у CPU-работы не освобождается,
   выигрыш близок к нулю, а очередь потоков общая с настоящим I/O.
4. **`to_thread` не ускоряет — он освобождает event loop.** Пул потоков конечен (по
   умолчанию ≤ 40): если БД или сеть деградировали, все потоки уйдут в ожидание, и новые
   запросы будут ждать в очереди пула вместо очереди loop. Симптом сдвигается, не исчезает.
   Лечится это не обёртками, а async-драйвером (asyncpg + SQLAlchemy async) — см. оговорку
   к `config_store.set` в разборе `admin_models.py`.
5. **Одинаковый вызов имеет разную цену по месту исполнения:** процесс API (один event
   loop) — чинить; воркер Celery (solo-пул, последовательная обработка) — синхронный код
   нормален, обёртка добавит оверхед без выигрыша.

## Главный SLA (замер, а не обещание)

**`/health` под нагрузкой чата — ≤ 10 мс.** Фактические замеры: 1.4–2.4 мс (запрос
RAG 5 с в фоне), 1.4–2.0 мс (RAG 0.48 с), 2.2–3.1 мс (запрос к Keycloak 0.39 с),
2.2–3.1 мс (работа сторожа типизации). Смысл не в том, что «чат стал быстрее», а в
том, что один работающий пользователь больше не останавливает систему: раньше
синхронный поиск в Qdrant держал event loop, и запросы выстраивались в очередь.

Как проверять (любой из случаев): запустить долгий запрос в фоне и в это время
мерить `/health`:

```bash
( curl -s -o /dev/null -w "долгий запрос: %{time_total}s
" -X POST     localhost:8000/api/v1/chat/search -H "Authorization: Bearer $TOK"     -H "Content-Type: application/json" -d '{"query":"..."}' ) &
sleep 1; for i in 1 2 3 4; do   printf "  /health %s s
" "$(curl -s -o /dev/null -w "%{time_total}" localhost:8000/api/v1/health)"; done; wait
```

**Замеры:** `get` — 0.001–0.007 мс из кэша чтения (до кэша было 10.4 мс; проверено и на
крупных конфигах, и на отсутствующих ключах — см. ниже). `set` — 3.8 мс (запись + commit,
среднее из 5).

**Почему `get` не оборачиваем:** стоимость убрана в самом хранилище, обёртка на 23 места
была бы чистым churn (плюс 50–100 мкс на вызов — то есть в 10–15 раз дороже самого вызова).
Отдельно: первая формулировка обоснования была «≤ 0.3 мс», и это оказалось **усреднением
промаха с попаданиями**. Проверка границы дала: на маленьких конфигах 0.006 мс, но
ОТСУТСТВУЮЩИЙ ключ (`system/default`, `scaling/default`) читался из БД на каждое обращение
— 1.1 мс, потому что кэшировалось только существующее значение. Добавлен отрицательный кэш:
теперь 0.001–0.002 мс. Так обосновывать (средним по двум разным режимам) — нельзя.

**Почему `set` не оборачиваем — и когда это перестанет быть верным.** Вызов идёт по
действию человека (кнопка «Сохранить»), а не на каждый запрос: `get` звался на КАЖДЫЙ
запрос чата (85 мест в карте), `set` — редкое действие. НО 3.8 мс — это про ТЕКУЩЕЕ
состояние Postgres. Если БД деградирует (медленный commit, таймауты), эти миллисекунды
превратятся в десятки и сотни, и правильное решение будет не «обернуть 18 мест», а перейти
на async-драйвер (asyncpg + SQLAlchemy async). `to_thread` спасает от блокировки event loop,
но не от медленной БД: если пул потоков занят ожиданием SQL, новые запросы всё равно встанут
в очередь. То есть таблица ниже — про сегодняшний день, не универсальное правило.

**Пакетные операции (проверено по коду).** `_restore_namespace()` в restore/migrate —
вложенная синхронная функция, внутри цикл `config_store.set(ns, key, value)` по ключам
namespace, а вызывается она ОДИН раз на namespace через ``await asyncio.to_thread``
(строка 2292). Это правильно: 50 ключей × 3.8 мс = ~190 мс внутри одного потока — loop не
блокируется, растёт только длительность операции. Если 190 мс на namespace когда-нибудь
станет проблемой, известное улучшение — `config_store.set_many(ns, dict)` с одной
транзакцией; тогда обоснование «`set` не оборачиваем» останется валидным, а restore
ускорится. Не срочно.

## Как перепроверить

```bash
python scripts/scan_sync_io.py src   # 166 мест (было 258)
```

Скрипт намеренно не знает про «разрешённые» случаи — он показывает все места.
Правило: прежде чем оборачивать, посмотреть, откуда функция вызывается (процесс API
или воркер) и сколько стоит сам вызов (замер, а не догадка).
