# Админ-API: бэкап, SSH, баланс провайдеров

Заметки по эксплуатации админских эндпоинтов (`/api/v1/admin/models/*`), включая
разбор пунктов внешнего аудита от 2026-09-12/13 (проверено кодом и на стенде 18).

## Бэкап настроек: категории берутся из БД

`GET /api/v1/admin/models/backup` — категории читаются динамически
(`SELECT DISTINCT category FROM system_configs`), как в `/backup-documents`.

Было: список `BACKUP_NAMESPACES` захардкожен и отстал. В бэкап не попадали
`providers` (провайдеры LLM!), `search` (режим поиска), `system` (блокировки
загрузки и обработки), `setup`, `upload_config`, `entity_cache` — при переносе на
другой сервер конфигурация провайдеров терялась.

Сейчас: в бэкапе 9 категорий (проверено) —

```
function_map, kg_config, process_logs, providers, search, setup,
system, upload_config, web_monitor
```

Кэши по умолчанию исключаются (`entity_cache` — эмбеддинги сущностей,
восстанавливать бессмысленно), но включаются параметром `?include_caches=true`.
В ответе есть `categories` и `skipped_caches` — видно, что именно уехало.

Восстановление (`POST /backup-restore`, multipart, поле `file`) формат не меняло:
круг «скачал → залил» проверен на стенде — `restored: 9, errors: []`, значения
`providers`/`search`/`system` после восстановления не изменились.

## SSH: пароли не в командной строке

Было (`restart-ollama` и `ssh_manager.test_connection`): пароль подставлялся
аргументом sshpass (флаг `-p`) → виден в `ps` на хосте; sudo-пароль уходил в
командной строке на удалённой стороне; вызов шёл через `shell=True`.

Стало:

- SSH-пароль — через переменную окружения: `sshpass -e`, `SSHPASS` в `env`
  дочернего процесса (в argv пароля нет);
- sudo-пароль — на stdin (`sudo -S -p ''`), поэтому в `ps` удалённой стороны его
  тоже нет;
- вызовы только списком аргументов, `shell=True` не используется;
- имя systemd-сервиса санитизируется (`_safe_service_name`: только
  `[A-Za-z0-9_.@-]`, иначе `ollama`) — защита от инъекции через настройку.

Тест: `tests/test_admin_audit_fixes.py` — пароль не в argv, `SSHPASS` в env,
sudo-пароль в stdin, инъекции в имени сервиса отсекаются, `shell=True` и
`sshpass -p` в исходниках отсутствуют.

## Баланс провайдеров

Три дублирующих эндпоинта сведены к одной функции `_provider_balance()`:
`/ext-llm/balance` и `/graph/balance` (старые конфигурации) и
`/providers/{id}/balance` (актуальный, его зовёт админка).

DeepSeek: ответ `{is_available, balance_infos: [{currency, total_balance,
granted_balance, topped_up_balance}]}`. Раньше в двух местах из трёх читалось
поле `balance`, которого нет → в интерфейсе было «0.0 токенов» при живом ключе.
Теперь баланс берётся из `balance_infos`, при отрицательной сумме статус
`balance_ok=false` и приписка «(баланс исчерпан)» (у DeepSeek `is_available`
остаётся `true` и при исчерпанном балансе — проверено на живом ключе: −1.18 CNY).

Провайдеры, которые баланс не отдают (gigachat, openai): `balance_ok=null`,
`balance_known=false`, в админке нейтральное «—», а не красная ошибка и не нули.
Ошибки HTTP различаются: 401/403 → «API ключ недействителен», иначе `HTTP <код>`.

## Бэкап с документами: длинные имена файлов (2026-09-13)

`GET /backup-documents` вообще не формировался: отдавал 200 и JSON
`{"status":"error","message":"Ошибка формирования ZIP: [Errno 36] File name too
long: '/app/data/uploads/0e33936d-..._Использование алгоритмов ГОСТ ...'"}`.

Причина: имя собиралось как `f"{doc_id}_{filename}"`, а `filename` в БД — полное
исходное название (до 205 символов). В сумме больше 255 байт (лимит имени в
ext4), и уже `path.exists()` бросал `ENAMETOOLONG` — `pathlib` эту ошибку не
проглатывает (в отличие от `os.path.exists`).

Теперь:

- файлы ищутся по индексу каталога `uploads` (один проход, ключ — `document_id`,
  первые 36 символов до «_») — длинные имена не собираются вообще;
- имя внутри архива обрезается до безопасной длины с сохранением расширения;
- ошибка на отдельном файле не убивает архив: пропуски перечислены в
  `backup_warnings.json` внутри самого архива;
- неудачный ZIP отвечает 500 (раньше браузер сохранял 494-байтный JSON как «zip»).

Проверено на стенде: архив собирается — 51 запись (47 файлов документов +
`documents_meta.json`, `aliases.json`, `config_store.json`, `chat_history.json`),
пропущенных файлов нет, `config_store.json` содержит все категории (в отличие от
`/backup`, здесь кэш `entity_cache` тоже попадает — это полный бэкап).

## restart-ollama: контракт ответа

Страница админки проверяет `result.status` (`success` / `warning`, иначе —
ошибка). При переписывании эндпоинта это поле было потеряно, страница показывала
ошибку при успешном перезапуске. Сейчас возвращаются и старые имена полей
(`systemctl_active`, `http_responding`), и новые (`service_active`,
`api_responding`). Пауза 8 секунд заменена опросом API до ~20 с с выходом сразу
после ответа. Второй SSH-вызов использует `sudo -S` с паролем по stdin: `sudo -n`
без tty ненадёжен (кэш прав может не сработать), из-за чего живой сервис
показывался как неактивный.

Проверено на стенде:

  без токена все отвечают 401/403, не-администратор проходит только на

  health отвечает за 230 мс, ошибок нет: цикл не блокируется.

Известное ограничение: `/deploy` не умеет записывать пустой файл (`file_content`
считается обязательным) — при необходимости снять проверку на пустую строку.

Отложено осознанно (шаг 10 аудита): замена `data: dict` на Pydantic-модели в девяти
эндпоинтах. Причина: интерфейс сохраняет конфиги частичными словарями, и переход
на модели с `exclude_unset` меняет семантику записи (можно затереть поля, которые
UI не отправляет). Делать это нужно по одному эндпоинту вместе с проверкой
соответствующей страницы, иначе есть риск тихой потери настроек.

Остаётся осознанным (не баг): `/deploy` умеет писать файлы в `/app/src`, делать

функционал не нужен на поставке — эндпоинт стоит удалить или ограничить
локальным доступом; решение за владельцем продукта.

## Четвёртый разбор кода (2026-09-13, образ 2026.09.13.10)

Все 15 замечаний подтвердились по коду и исправлены.

Исправления по существу:

- **Обрезка имени в архиве — по байтам, не по символам** (`_truncate_bytes`):
  для CJK 120 символов = 360 байт и снова `Errno 36`. Проверено в контейнере:
  имена из 64, 124 и 204 символов дают запись ~201 байт — в пределах лимита ФС.
  Обе функции (`_truncate_bytes`, `_safe_arcname`) вынесены на уровень модуля:
  вложенные нельзя ни импортировать, ни протестировать.
- **`zf.writestr` в потоке**: сжатие `documents_meta.json`, `chat_history.json`,
  алиасов и настроек шло в основном потоке — теперь через `asyncio.to_thread`.
- **`/backup-restore`**: один поток на namespace (`_restore_ns`) вместо
  `to_thread` на каждый ключ (было 1000 переключений на 1000 ключей).
- **`/deploy`**: `encoding` по умолчанию `utf8` (base64-подобный литерал больше не
  декодируется молча); `auto` декодирует только строки, похожие на base64; пустой
  файл записывается (проверка на `None`, а не на falsy). Проверено живьём:
  литерал `aGVsbG8=` с настройкой по умолчанию сохраняется как текст (8 байт),
  с явным `base64` — как `hello` (5 байт), пустая строка — 0 байт.
- **`/backup`**: `_all_config_categories` возвращает `None` при ошибке БД и `[]`
  при пустой таблице — 503 теперь только при реальной ошибке, а не на свежей
  установке. В `/backup-documents` при недоступной БД пишется маркер ошибки,
  а не пустой `config_store.json`.
- **`restart-ollama`** при исключении отдаёт JSON `{status: error, message}` —
  страница админки показывает текст, а не «❌ undefined» (проверено: HTTP 200,
  `status=warning` при недоступном хосте).
- Мелочи: `import traceback` в шапке; дубли `from pydantic import BaseModel` и
  `Optional as Opt` убраны; инициализация настроек при старте логирует сбой
  вместо молчаливого `pass`; `_graph_model_config` объявлена до загрузчика;
  worker считается по compose-метке, а не по подстроке в имени.
