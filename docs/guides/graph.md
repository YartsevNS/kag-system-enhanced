# Гид: граф знаний (Neo4j)

> Актуально на 2026-08-23. ⚠️ ЕСТЬ ОТКРЫТАЯ ПРОБЛЕМА: LLM возвращает пустые ответы при извлечении сущностей.

## Текущее состояние

- **Neo4j Community** (не Enterprise): NODE KEY / composite constraints НЕ доступны → используем MERGE + отдельные индексы.
- Схема: `Document {id, filename}`, `Chunk {id, chunk_seq, text_preview}`, `Entity {name, type, source_docs}`.
- Связи: `(:Document)-[:HAS_CHUNK]->(:Chunk)`, `(:Chunk)-[:MENTIONS]->(:Entity)`, `(:Entity)-[:RELATED_TO]->(:Entity)`.
- Векторов в графе НЕТ — только текст-превью (первые ~500 символов).

## Как строится граф

`_build_knowledge_graph_async` в `src/api/services/document_service.py`:
1. Создаёт узел Document.
2. Обрабатывает **первые 10 чанков** (chunks[:10]):
   - создаёт узел Chunk (MERGE),
   - LLM-извлечение сущностей (`entity_extractor.extract_and_store`) — один промпт (core/relations/extended объединены, коммит df35877).

Таймауты (страховка от зависания):
- Neo4j-операция: 20 сек (to_thread + wait_for)
- Извлечение на чанк: 60 сек
- Весь граф: 300 сек — при превышении граф ПРОПУСКАЕТСЯ, документ завершается (граф вторичен).

## ⚠️ Проблема с пустыми ответами LLM — ИСПРАВЛЕНА (2026-08-23)

**Симптом:** `Пустой ответ LLM для chunk_00001 (pass=extract):` для всех чанков; граф ~70 сек/документ впустую; Entity не создавались.

**Причина:** `function_map:graph` → `deepseek-v4-flash` — **reasoning-модель**. Сначала генерирует длинный `reasoning_content`, потом `content`. `max_tokens=800` (жёстко в `_call_llm`) — суммарный лимит, модель «думала» до исчерпания, content оставался пустым.

**Решение:** в `_call_llm` для deepseek/openai/openrouter добавлен `payload["thinking"] = {"type": "disabled"}` (коммит 4dcdc4d).

**Результат:** content_len=1211, reasoning=0; граф 25.4 сек вместо 71; сущности извлекаются.

**Диагностика (если снова пусто):** прямой вызов с полным промптом:
```python
# проверить reasoning_content и content
data = await resp.json()
msg = data['choices'][0]['message']
print(len(msg.get('content','')), len(msg.get('reasoning_content','')))
```

## Очистка при переиндексации

- `process_document(force=True)` вызывает `kg_service.clear_document(document_id)` ПЕРЕД переобработкой:
  - удаляет Document и его Chunk (DETACH DELETE),
  - убирает document_id из source_docs сущностей,
  - удаляет осиротевшие сущности (без MENTIONS).

## Визуализация /kg: имена узлов и фрагменты по клику (2026-09-12)

Что было не так: обход подграфа отдавал узлы Document и Chunk как есть, а у них
нет свойства `name` — имя падало на `id`, и в графе висели «b93f09…». По клику
было видно только имя и кнопку «+ соседи»: ни текста фрагмента, ни перехода к
файлу. Плюс в имени файла оставался префикс хранения (`<document_id>_`).

Что теперь отдаёт `GET /api/v1/kg/graph/{сущность}?depth=N`:

- у каждого узла `key` (уникальный: `e:<имя>`, `d:<document_id>`, `c:<chunk_id>`),
  `name` (человекочитаемое), `kind` (`entity` | `document` | `chunk`) и
  привязка: `document_id`, `chunk_seq`, `filename`;
- имена: сущность — как есть; документ — имя файла; чанк — «<файл> · фрагмент N»
  (имя файла берётся у родителя одним доп. запросом, у Chunk его нет);
- `display_filename()` (`src/indexing/ids.py`) снимает префикс хранения
  `<document_id>_` — в хранилище имя не меняется, только на выдаче;

Новые эндпоинты (нужны панели по клику):

- `GET /api/v1/kg/entity/{сущность}/chunks?limit=8` — фрагменты, где встречается
  сущность: документ, номер фрагмента, превью (из графа) и **номер страницы с
  полным текстом из Qdrant** (в графе страницы нет);
- `GET /api/v1/kg/chunk/{chunk_id}` — один фрагмент целиком.

Питфолл страницы: в payload Qdrant страница лежит в `metadata.pages` — это СПИСОК
(например `[68]`), а не `page`/`page_number`. Хелпер `_page_of()` смотрит все три
варианта и для диапазона отдаёт «1-2» (просмотрщик понимает `?page=`).

В интерфейсе (`kg.html`) по клику на узел: сущность → её фрагменты с текстом и
кнопками «открыть на странице» (`/viewer?id=…&page=…`) и «все чанки документа»
(`/chunks?doc_id=…`); чанк → его текст и переход к документу; документ → файл и
чанки. Узлы в Cytoscape различаются по `key`, а не по имени (иначе документ и
чанк с одинаковым именем склеивались).

Проверка: `scripts/e2e_kg_viz.py` (Playwright) — открывает /kg, строит граф,
кликает узел, проверяет наличие фрагментов, кнопок и отсутствие имён с сырым id.
Живые цифры: сущность «Банк России» → 46 узлов (25 фрагментов), 6 фрагментов в
панели, «press.pdf · фрагмент 20, стр. 13», имён с сырым id — 0.

## Поиск фрагментов по тексту (совпадения + соседи) — 2026-09-12

Второй режим визуализации, кроме «граф по документу»: искать не документ целиком,
а НУЖНЫЕ фрагменты и добирать к ним соседние. Логика:

1. поиск по графу (Neo4j) по тексту чанков: полнотекстовый индекс
   `chunk_text_fulltext` по `Chunk.text` создаётся автоматически
   (`CREATE FULLTEXT INDEX … IF NOT EXISTS`); если индекс недоступен — откат на
   `CONTAINS` со обязательным наличием ВСЕХ термов;
2. к каждому совпадению добавляются соседи по `chunk_seq` в пределах того же
   документа: радиус = уровень, выбранный на странице (`1 уровень` → ±1);
3. в выборку попадают сущности этих фрагментов и связи: документ→фрагмент
   (`HAS_CHUNK`), фрагмент→сосед (`NEXT`, только реально соседние), фрагмент→
   сущность (`MENTIONS`). Найденные фрагменты помечены `matched` и подсвечены.

Роут: `GET /api/v1/kg/search-chunks?q=&doc_id=&level=&limit=` (doc_id — искать
внутри одного файла). Живые замеры: «ГОСТ Р 34.10» (уровень 1) — 20 совпадений,
141 фрагмент в выборке, 6 документов, 143 сущности, связей NEXT 121; «цифровой
рубль» (уровень 2) — 14 совпадений, 61 фрагмент, 2 документа.

Питфоллы:

- Lucene ломается на точках и дефисах («ГОСТ Р 34.10»): термы чистятся и
  склеиваются через AND — иначе поиск падает на разборе запроса;
- признак `matched` нужно переносить в данные узла Cytoscape, иначе подсветки нет
  (сервер отдаёт поле, но `addGraphData` его не копирует).

## Что лежит в графе (проверено 2026-09-12)

`MATCH (c:Chunk) RETURN count(c), count(c.text), sum(size(c.text))` →
3495 чанков, у ВСЕХ есть `c.text`, суммарно ~4.7 МБ текста. Сущностей 8381,
связей `MENTIONS` 19058. Самые крупные документы по числу фрагментов: 718, 558,
308, 295, 285. То есть в графе есть всё; лимиты 150/120 в подграфе документа —
это только размер того, что уходит в браузер (Cytoscape с cose на большом графе
подвешивает страницу), а не ограничение хранения.

## Полезные запросы Neo4j

```cypher
// Сущности по типу
MATCH (e:Entity) RETURN e.type, count(*) ORDER BY count(*) DESC LIMIT 20;
// Документы без чанков
MATCH (d:Document) WHERE NOT (d)-[:HAS_CHUNK]->() RETURN d.id, d.filename;
// Связи между сущностями
MATCH (a:Entity)-[r:RELATED_TO]->(b:Entity) RETURN a.name, r.type, b.name LIMIT 50;
```
