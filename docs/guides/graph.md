# Гид: граф знаний (Neo4j)

> Актуально на 2026-08-23. ⚠️ ЕСТЬ ОТКРЫТАЯ ПРОБЛЕМА: LLM возвращает пустые ответы при извлечении сущностей.

## Текущее состояние

- **Neo4j Community** (не Enterprise): NODE KEY / composite constraints НЕ доступны → используем MERGE + отдельные индексы.
- Схема: `Document {id, filename}`, `Chunk {id, chunk_seq, text_preview}`, `Entity {name, type, source_docs}`.
- Связи: `(:Document)-[:HAS_CHUNK]->(:Chunk)`, `(:Chunk)-[:MENTIONS]->(:Entity)`, `(:Entity)-[:RELATED_TO]->(:Entity)`.
- Векторов в графе НЕТ — только текст-превью (первые ~500 символов).

## Как строится граф

`_build_knowledge_graph_async` в `src/api/services/document_service.py`:
1. Создаёт узел Document.
2. Обрабатывает **первые 10 чанков** (chunks[:10]):
   - создаёт узел Chunk (MERGE),
   - LLM-извлечение сущностей (`entity_extractor.extract_and_store`) — один промпт (core/relations/extended объединены, коммит df35877).

Таймауты (страховка от зависания):
- Neo4j-операция: 20 сек (to_thread + wait_for)
- Извлечение на чанк: 60 сек
- Весь граф: 300 сек — при превышении граф ПРОПУСКАЕТСЯ, документ завершается (граф вторичен).

## ⚠️ Проблема с пустыми ответами LLM — ИСПРАВЛЕНА (2026-08-23)

**Симптом:** `Пустой ответ LLM для chunk_00001 (pass=extract):` для всех чанков; граф ~70 сек/документ впустую; Entity не создавались.

**Причина:** `function_map:graph` → `deepseek-v4-flash` — **reasoning-модель**. Сначала генерирует длинный `reasoning_content`, потом `content`. `max_tokens=800` (жёстко в `_call_llm`) — суммарный лимит, модель «думала» до исчерпания, content оставался пустым.

**Решение:** в `_call_llm` для deepseek/openai/openrouter добавлен `payload["thinking"] = {"type": "disabled"}` (коммит 4dcdc4d).

**Результат:** content_len=1211, reasoning=0; граф 25.4 сек вместо 71; сущности извлекаются.

**Диагностика (если снова пусто):** прямой вызов с полным промптом:
```python
# проверить reasoning_content и content
data = await resp.json()
msg = data['choices'][0]['message']
print(len(msg.get('content','')), len(msg.get('reasoning_content','')))
```

## Очистка при переиндексации

- `process_document(force=True)` вызывает `kg_service.clear_document(document_id)` ПЕРЕД переобработкой:
  - удаляет Document и его Chunk (DETACH DELETE),

  - удаляет осиротевшие сущности (без MENTIONS).

## Визуализация /kg: имена узлов и фрагменты по клику (2026-09-12)

Что было не так: обход подграфа отдавал узлы Document и Chunk как есть, а у них
нет свойства `name` — имя падало на `id`, и в графе висели «b93f09…». По клику
было видно только имя и кнопку «+ соседи»: ни текста фрагмента, ни перехода к
файлу. Плюс в имени файла оставался префикс хранения (`<document_id>_`).

Что теперь отдаёт `GET /api/v1/kg/graph/{сущность}?depth=N`:

- у каждого узла `key` (уникальный: `e:<имя>`, `d:<document_id>`, `c:<chunk_id>`),
  `name` (человекочитаемое), `kind` (`entity` | `document` | `chunk`) и
  привязка: `document_id`, `chunk_seq`, `filename`;
- имена: сущность — как есть; документ — имя файла; чанк — «<файл> · фрагмент N»
  (имя файла берётся у родителя одним доп. запросом, у Chunk его нет);
- `display_filename()` (`src/indexing/ids.py`) снимает префикс хранения
  `<document_id>_` — в хранилище имя не меняется, только на выдаче;

Новые эндпоинты (нужны панели по клику):

- `GET /api/v1/kg/entity/{сущность}/chunks?limit=8` — фрагменты, где встречается
  сущность: документ, номер фрагмента, превью (из графа) и **номер страницы с
  полным текстом из Qdrant** (в графе страницы нет);
- `GET /api/v1/kg/chunk/{chunk_id}` — один фрагмент целиком.

Питфолл страницы: в payload Qdrant страница лежит в `metadata.pages` — это СПИСОК
(например `[68]`), а не `page`/`page_number`. Хелпер `_page_of()` смотрит все три
варианта и для диапазона отдаёт «1-2» (просмотрщик понимает `?page=`).

В интерфейсе (`kg.html`) по клику на узел: сущность → её фрагменты с текстом и
кнопками «открыть на странице» (`/viewer?id=…&page=…`) и «все чанки документа»
(`/chunks?doc_id=…`); чанк → его текст и переход к документу; документ → файл и
чанки. Узлы в Cytoscape различаются по `key`, а не по имени (иначе документ и
чанк с одинаковым именем склеивались).

Проверка: `scripts/e2e_kg_viz.py` (Playwright) — открывает /kg, строит граф,
кликает узел, проверяет наличие фрагментов, кнопок и отсутствие имён с сырым id.
Живые цифры: сущность «Банк России» → 46 узлов (25 фрагментов), 6 фрагментов в
панели, «press.pdf · фрагмент 20, стр. 13», имён с сырым id — 0.

## Поиск фрагментов по тексту (совпадения + соседи) — 2026-09-12

Второй режим визуализации, кроме «граф по документу»: искать не документ целиком,
а НУЖНЫЕ фрагменты и добирать к ним соседние. Логика:

1. поиск по графу (Neo4j) по тексту чанков: полнотекстовый индекс
   `chunk_text_fulltext` по `Chunk.text` создаётся автоматически
   (`CREATE FULLTEXT INDEX … IF NOT EXISTS`); если индекс недоступен — откат на
   `CONTAINS` со обязательным наличием ВСЕХ термов;
2. к каждому совпадению добавляются соседи по `chunk_seq` в пределах того же
   документа: радиус = уровень, выбранный на странице (`1 уровень` → ±1);
3. в выборку попадают сущности этих фрагментов и связи: документ→фрагмент
   (`HAS_CHUNK`), фрагмент→сосед (`NEXT`, только реально соседние), фрагмент→
   сущность (`MENTIONS`). Найденные фрагменты помечены `matched` и подсвечены.

Роут: `GET /api/v1/kg/search-chunks?q=&doc_id=&level=&limit=` (doc_id — искать
внутри одного файла). Живые замеры: «ГОСТ Р 34.10» (уровень 1) — 20 совпадений,
141 фрагмент в выборке, 6 документов, 143 сущности, связей NEXT 121; «цифровой
рубль» (уровень 2) — 14 совпадений, 61 фрагмент, 2 документа.

Питфоллы:

- Lucene ломается на точках и дефисах («ГОСТ Р 34.10»): термы чистятся и
  склеиваются через AND — иначе поиск падает на разборе запроса;
- признак `matched` нужно переносить в данные узла Cytoscape, иначе подсветки нет
  (сервер отдаёт поле, но `addGraphData` его не копирует).

## Переход от фрагмента к странице документа (2026-09-18)

Жалоба: в /kg поиск по сущности показывает соседние фрагменты и документы, но
нажатие на страницу ничего не открывает, а фрагменты идут по порядку — не видно,
в котором из них найдена информация.

Что было не так (три причины, все подтверждены по коду):

1. **Страницы у узлов графа не было вообще.** Номер страницы живёт только в payload
   Qdrant (в Neo4j его нет), а `search_chunks` и `get_document_graph` не отдавали даже
   id точки Qdrant — добрать страницу было нечем. Поэтому узел-документ открывался
   с первой страницы, а узел-фрагмент — без страницы.
2. **Переход шёл через `window.open`.** Кнопка «открыть на странице» вызывала
   `window.open`, который глушится блокировщиком всплывающих окон — «нажимаю, ничего
   не открывается».
3. **В панели не было признака совпадения.** Фрагменты шли по `chunk_seq` и выглядели
   одинаково: какой из них содержит искомое, видно не было.

Что сделано:

- **Бэкенд.** Узлы-фрагменты несут `qdrant_point_id` (`kg_service.search_chunks`,
  `get_document_graph` — в Cypher добавлен `coalesce(c.qdrant_point_id, '') AS pid`).
  Роут графа обогащает узлы полем `page`: хелпер `_attach_pages()` собирает id точек
  и читает payload'ы ОДНИМ запросом (`embeddings_service.get_points_payload`),
  ошибка Qdrant граф не ломает — у узла просто не будет `page`. Вызывается в
  `/graph/{сущность}`, `/search-chunks` и `/document/{id}/graph`.
- **/kg.** Переход к файлу — настоящая ссылка (`<a target="_blank">`), а не
  `window.open`; в ссылке и номер страницы, и термины запроса (`&page=`, `&q=`).
  Узел-документ открывается на странице первого найденного фрагмента
  (`firstDocPage()` — сначала совпадения, диапазон «12-14» → 12). В панели сущности
  фрагменты-совпадения идут первыми и помечены бейджем, термины подсвечены в тексте
  (`markTerms()` — сначала экранирование, потом `<mark>`).
- **Просмотрщик.** Параметр `q` подсвечивает термины в текстовом слое страницы и
  пишет над страницей, что совпадения найдены (или что на этой странице их не видно —
  значит, фрагмент на соседней). Подсветка НЕ блокирует рендер: текстовый слой
  дорисовывается асинхронно, спаны ждём через `setTimeout` (await здесь вешает вьюер).

Как проверять живьём (после выкатки образа api):

1. Режим «сущность», например «Банк России», уровень 2 → клик по кружочку-сущности.
2. В панели — список фрагментов; у каждого кнопка «открыть на странице N». Переход
   открывает просмотрщик на этой странице, термины подсвечены жёлтым, над страницей
   подпись про совпадения.
3. Режим «текст»: запрос вроде «пентест» → клик по фрагменту с оранжевой обводкой →
   в панели бейдж «совпадение по запросу», термины подсвечены, ссылка ведёт на его
   страницу. Соседние фрагменты помечены «соседний фрагмент».
4. Клик по кружочку-документа → «открыть на странице N» ведёт на страницу первого
   найденного фрагмента, а не на первую страницу файла.

Питфоллы:

- `window.open` в панели не работает (блокировка всплывающих окон) — только ссылки;
- подсветка идёт ПОСЛЕ экранирования текста, иначе HTML из фрагмента исполнится;
- `renderTextLayer` в нашем бандле pdf.js не экспортирует `TextLayer` и не отдаёт
  готовый промис — подсветку вызывать после проверки, что в слое есть спаны;
- если у фрагмента нет `page` (точка потеряна при переиндексации) — ссылка ведёт на
  документ без страницы; это ожидаемое поведение, а не ошибка.

Было: три поля ввода и шесть кнопок в одну строку («Показать граф», «Граф по

## Доменная схема сущностей: где живёт состояние (2026-09-13, образ 2026.09.13.17)

Симптом: в админке выбираешь пресет доменной схемы (universal / infosec / legal …),
интерфейс подтверждает, но после перезапуска api схема снова «universal», а
извлечение сущностей в worker'е идёт по универсальной схеме — выбранный пресет
на пайплайн не влияет вообще.

Причина: схема и пресет жили ТОЛЬКО в памяти процесса. В config_store писали
(`kg_config:active_preset`, `kg_config:domain_schema`), но не читали нигде: при
старте экстрактор брал `DOMAIN_SCHEMA = SCHEMA_PRESETS["universal"]`. Worker —
отдельный процесс, он переключение в api не видел в принципе, а извлечение
сущностей идёт именно там.

Как сделано теперь:

- единый ключ настроек `kg_config:domain_schema_active` =
  `{"mode": "preset"|"manual", "preset": имя_или_None, "schema": {...}}` —
  единственный источник правды;
- `EntityExtractor.apply_stored_domain_schema()` применяет его в процессе и
  возвращает режим (`preset:<имя>` | `manual` | `default`); вызывается
  при старте api (`main.py` lifespan), в задаче `process_document` (worker) и на
  чтение `GET /api/v1/kg/domain-schema` — интерфейс всегда показывает состояние
  из настроек, а не из памяти;
- ручная схема помечает пресет как «manual» (`set_domain_schema(..., mark_manual=True)`),
  иначе интерфейс продолжал бы подсвечивать пресет, которого уже нет;
- сбой чтения настроек — fail-open: применяется текущая схема, в лог идёт warning.

Проверка (обязательно с рестартом — иначе баг не виден):
переключить пресет → `docker restart kag-api` → `GET /domain-schema` должен
показать тот же пресет и то же число типов; затем в контейнере worker'а
`entity_extractor.apply_stored_domain_schema()` должен вернуть `preset:<имя>`.

Заодно по тому же обзору: лимиты подграфа документа клампятся (1..500, как в
остальных пяти эндпоинтах), `/type-watchdog/status` считает одним проходом,
`q_lower` в `/hybrid-search` вынесен из цикла, убран неиспользуемый параметр в
`/stats`, `EmbeddingsService.is_initialized()` заменяет обращение роутов к
приватному `_embedding_client`, в `/cypher` добавлен аудит-лог
(`user=… limit=… rows=… query='…'[:200]`).
