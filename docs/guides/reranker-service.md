# Реранкер: подключаемый, отключаемый, модель на отдельном сервере

Решение владельца (26.09.2026): реранкер должен быть **подключаемым и отключаемым в админке**, а
модель, которую он использует, — **храниться на сервере моделей (41)** и выключаться, когда не нужна.
Это не «фича на вырост»: без переключателя нельзя ни измерить пользу на своём трафике, ни быстро
откатиться, если реранкер начнёт тормозить ответы.

## Почему так, а не «модель внутри api»

Замер 26.09.2026 (14 вопросов, 10 кандидатов на вопрос, CPU):

| Модель | Смена топ-1 | Время на вопрос (20 ядер) | Отрыв лучшего от второго |
| :-- | :-- | :-- | :-- |
| `DiTy/cross-encoder-russian-msmarco` (200M) | 11/14 | 1,46 с | 16,2% |
| `sshalimov04/ru-reranker-edge-150m` (150M, есть ONNX) | 10/14 | 3,03 с | 31,2% |
| `BAAI/bge-reranker-v2-m3` (568M) | 12/14 | 6,59 с | 2,5% |
| векторный поиск (как сейчас) | — | 0 с | 1–6% |

На стенде 4 ядра — там те же модели дают в разы больше времени (DiTy на ноутбуке: 8,7 с против 1,5 с
на 41). Поэтому: модель живёт рядом с другими моделями на 41, а стенд обращается к ней по HTTP.

Отдельно видно, что **все** проверенные cross-encoder'ы реально меняют порядок (10–12 из 14), в отличие
от установленного сейчас flashrank с `ms-marco-MultiBERT-L-12` (0% изменений — он не делал ничего).

## Три состояния, которые переключает админ

| Состояние | Что происходит | Когда нужно |
| :-- | :-- | :-- |
| `выключен` | Порядок — как отдал векторный поиск (сегодняшнее поведение) | Дефолт. Экономит время ответа |
| `flashrank` | Локальный cross-encoder внутри api (текущая реализация) | Если нужен реранк без внешнего сервиса (закрытый контур, один сервер) |
| `сервис` | HTTP-вызов cross-encoder'а на сервере моделей (41) | Прод: быстрая модель без нагрузки на стенд |

## Конфиг (`reranker/config` в config_store, ключи)

| Ключ | Смысл | Дефолт |
| :-- | :-- | :-- |
| `enabled` | Главный тумблер | `false` |
| `backend` | `none` / `flashrank` / `service` | `none` |
| `model` | Имя модели (для flashrank — из его списка, для сервиса — что загружено на 41) | `DiTy/cross-encoder-russian-msmarco` |
| `endpoint` | Адрес сервиса | `http://192.168.50.41:8010` |
| `timeout_ms` | Жёсткий таймаут вызова | `1500` |
| `top_k` | Сколько фрагментов оставлять после реранка | `5` |
| `keep_dense_on_error` | При ошибке/таймауте оставить исходный порядок | `true` |
| `min_fragments` | Не реранкать, если кандидатов меньше | `4` |

Правило: **значение по умолчанию — выключено**. Реранкер включается осознанно, после того как на
эталонном наборе видно, что он улучшает `context_precision` и не роняет `context_recall`.

## Карточка в админке (обязательна, по правилу «фича с вкл/выкл имеет карточку»)

Содержимое карточки «Реранкер»:

1. Тумблер `Включён` + выбор `backend` (нет / flashrank / сервис) + выбор модели.
2. Адрес сервиса и таймаут — только для backend=`сервис`.
3. Кнопка **«Проверить связь»**: дергает `/health` сервиса и показывает «готов, модель X» либо
   «не готов: причина». Без этой кнопки админ не понимает, почему реранк не работает.
4. Строка состояния: включён/выключен, модель, последний вызов (мс), доля смены топ-1, число
   таймаутов и ошибок за час.
5. Короткий текст «что это и почему так»: «Реранкер переставляет уже найденные фрагменты, чтобы в
   промпт попало самое релевантное. Выключен по умолчанию: он добавляет время к каждому вопросу.
   Включать после проверки на эталонном наборе».

## Живучесть (без этого включать нельзя)

* Таймаут на вызов — жёсткий (`timeout_ms`), при выходе за него порядок остаётся векторным.
* Сервис недоступен — чат работает как раньше; ошибка считается в метрику, а не в лог-простыню.
* «Защёлка» на неудачу: после N подряд ошибок реранкер автоматически считается выключенным на
  5 минут (иначе каждый вопрос будет ждать таймаут).
* Метрики: `rag_reranker_runs_total`, `rag_reranker_changed_top1_total` (уже есть), добавляем
  `rag_reranker_errors_total{reason="timeout|http|not_ready"}` и `rag_reranker_duration_seconds`.
* Проверка `ready`: запросы не идут, пока `/health` не подтвердит, что модель загружена.

## Развёртывание сервиса на сервере моделей

    ~/kag-eval/venv                     — окружение (torch CPU, sentence-transformers, fastapi, uvicorn)
    ~/kag-eval/models                   — HF_HOME: веса моделей (переживают перезапуск, для закрытого контура кладутся файлами)
    ~/kag-eval/rerank_service/app.py    — сервис (контракт: GET /health, POST /rerank)
    systemd-юнит (system или --user с linger) — автозапуск и перезапуск при падении

Проверка: `curl http://192.168.50.41:8010/health` → `{"ready":true,"model":"..."}`.

## Что решает замер (и чего пока не хватает)

Перед включением нужен ответ по числам: растёт ли `context_precision` после реранка и не падает ли
`context_recall`. Считает судья на эталонном наборе (14 вопросов) — прогоны идут: топ-5 по векторному
score против топ-5 после каждой из трёх моделей. Если прироста нет — реранкер остаётся выключенным,
и это тоже результат: значит, узкое место не в порядке фрагментов.

Второе: **после реранкера порог отсечения нужно подбирать заново.** Сейчас `min_score_gap` почти
бесполезен, потому что векторные оценки выдачи лежат в полосе 1–6%; cross-encoder разводит их на
16–31%, и старые значения (0,02–0,12) окажутся в другом месте шкалы.
