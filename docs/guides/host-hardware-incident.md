## Доказательства (что именно проверено)

- В журнале предыдущих загрузок НЕТ: `Reached target Shutdown`, паники, OOM-kill, `hung task`,
  ошибок ввода-вывода, сбросов ATA/NVMe, задач `reboot/shutdown` в журнале задач PVE.
  Журнал просто обрывается → жёсткий сброс/зависание, а не выключение.
- В PVE взведён `softdog` (`soft_margin=60`) через `watchdog-mux`: зависание дольше 60 с
  приводит к аппаратному сбросу, и никаких следов в журнале не остаётся. Это объясняет
  «пустой» журнал.
- Внутри ВМ 107 перегрузки не было: занято 2,5–2,8 ГБ из 20, контейнеры 130–240 МБ.
- На хосте: 125 ГиБ RAM, Xeon E5-2682 v4 (32 потока), плата BKHD-2011-MATX, PVE 9.2.4,
  ядро 7.0.14-4-pve, BMC/IPMI нет (SEL не прочитать).

## Аппаратные улики

  Счётчики EDAC по памяти (mc0/mc1, ce/ue) нулевые → не планка DIMM, скорее PCIe/накопитель.
- SATA-диски чистые: Kingston SA400 ×2 (в т.ч. `data`, где лежит ВМ 107), SanDisk, Seagate —

## Исключено

- Память хоста не переполнялась (занято 12 из 125 ГиБ), OOM в журнале нет.
- Диск ВМ 107 здоров, I/O-ошибок по нему в журнале нет.
- Нагрузка на стенд (замеры Qdrant/чаты) могла быть триггером утром, но последние падения
  (16:55 → 16:56, 25 секунд жизни; и далее) шли при выключенном стенде и без моих прогонов.
- Задач выключения узла из панели/API в журнале задач нет.

## Гипотезы (по убыванию правдоподобия)

1. Деградировавший NVMe (или его слот/шлейф) роняет ввод-вывод хоста, зависание > 60 с →
   softdog сбрасывает машину. Косвенно: падения начинаются при обращении к дискам, статус
   диска FAILED.
2. Питание/материнская плата (BKHD-2011-MATX, бюджетная плата под E5 v4): просадка под
   нагрузкой, MCE в журнале.
3. Перегрев/вентиляция CPU (предупреждений в журнале нет, но и термодатчиков BMC нет).

## Отдельный инцидент того же дня: пропал реестр документов (ВОССТАНОВЛЕНО)

удалялось: в журналах api и в аудите нет ни одного удаления, а штатное удаление документа чистит

Что сделано (19.09, вечер):

1. Дамп текущей базы перед правкой: `backup_20260919/kag_before_restore.sql` (75 МБ).
2. Разобран старый дамп `backup_20260829/kag.sql` → 68 строк `documents` с хешами и авторами
   (`reports/_scratch/restore/parse_dump_docs.py`, запускается `python3` на стенде).
3. Реестр собран заново: `reports/_scratch/restore/restore_documents.py` — запускается ВНУТРИ
   контейнера `kag-api`. Источники: карточки Qdrant (id, title, type, domain, summary, topics,
   права), файлы `/app/data/uploads` (имя = `{doc_id}_{исходное имя}` → `filename`, размер,
   sha256), дамп 29.08 (mime, автор, дата, версия). `chunks_count` считается по точкам Qdrant.
4. Проверено: 81 строка, все `completed`, сумма `chunks_count` = 4944 (совпадает с Qdrant),
   домены infosec 53 / accounting 24 / legal 4; `/upload/list` → 81 документ;
   `/upload/{id}/details` и `/upload/{id}/preview` → 200 для всех 81 (превью отдаёт реальные
   байты PDF); скан сирот → **0**; чат отвечает (проверено вопросом про макропруденциальные
   надбавки — 3898 симв.).
5. Автора документа брать из старого дампа нельзя: тех `uploaded_by` больше нет среди `users`
   (FK `documents_uploaded_by_fkey`) — все 81 записаны на `admin`.

### Вероятная причина потери (требует решения)

`src/api/services/document_service.py:141` — `_cleanup_stale_records()` вызывается на старте и
удаляет из БД записи, для которых нет файла на диске (сверка по первым 36 символам имени файла).
Если каталог `/app/data/uploads` в этот момент недоступен (не смонтирован, только монтируется
после старта контейнера), метод уходит в fallback `/tmp/kag_uploads` (строка 126) — и тогда
`existing` пустой, то есть удаляются ВСЕ документы. Это ровно наблюдаемая картина: строки в БД
исчезли, векторы и файлы целы, удалений через API нет. Логи за те загрузки не сохранились
(docker logs хранит только последние), поэтому доказать нечем — но защита нужна:

- не удалять ничего, если каталог uploads пуст или недоступен (пропустить очистку);
- писать об очистке в WARNING с количеством, а не молча в INFO;
- не удалять больше, чем N записей за раз, без явного подтверждения.

Второй фактор риска: диск ВМ 107 был подключён как `cache=writeback` — при жёстком сбросе хоста
подтверждённые гостём записи могут не дойти до диска. **СДЕЛАНО 19.09:** ВМ остановлена штатно и
переключена на `cache=none` (`scsi0: data:107/vm-107-disk-0.qcow2,cache=none,iothread=1`);
после запуска проверено: ядро 6.1.0-53, 11 контейнеров healthy, api 200, 81 документ, чат отвечает.

Осталось доделать 14 пакетов в половинчатом состоянии (`iU`/`iF`): `openssh-server`,

Порядок завершения (когда хост проживёт хотя бы 10 минут):

```bash
bash /home/yartsevn/upd2.sh            # apt-get -f install, dpkg --configure -a, full-upgrade
                                        # лог: /home/yartsevn/upd2.log (переживает перезагрузку)
sudo systemctl reboot                   # затем проверка: контейнеры healthy, api health, сайт через nginx
```

В скрипте учтено: `apt-get -f install` первым шагом отказывается работать, пока не выполнен
`dpkg --configure -a` — поэтому он идёт вторым, а не первым.

Права на стенде: `yartsevn` получил через `/etc/sudoers.d/hermes-agent` sudo без пароля на
`/usr/bin/{apt-get,apt,dpkg,docker,docker-compose,systemctl}` и `/usr/sbin/{reboot,shutdown}`
(откат: `rm /etc/sudoers.d/hermes-agent`). Это фактически полный root — правило осознанное.

## Docker: что «обновить докер» значит здесь

На 18 стоят пакеты Debian: `docker.io 20.10.24+dfsg1` и `docker-compose 1.29.2`. В репозитории
bookworm доступны только ревизии 20.10 — «обновление» здесь ограничено ими. Переезд на
официальный `docker-ce` (28.x) — отдельное изменение: деплой проекта ходит через
`docker-compose` v1, а в compose v2 другая команда (`docker compose`), то есть требуется правка
скриптов и проверка на стенде. Делать это до стабилизации железа смысла нет.
