# Поэтапное развёртывание KAG: визард установки (default / advanced)

Замысел владельца (26.09.2026): система — это не только код, но и проработанный набор элементов
развёртывания; часть решений нельзя предусмотреть на старте, и по мере реализации понятно, что
параметры нужно выбирать **в процессе установки**, а не зашивать в момент «старта». Отсюда —
поэтапное развёртывание: установщик предлагает выбор параметров в двух режимах, **default** и
**advanced**, и разворачивает систему по выбранному набору. Ключевые вопросы, которые он задаёт:
api-ключ модели, ключ для обработки документов (эмбеддинги) и ключи дополнительных процессов.

Статус: архитектурный долг, не в работе. Правило: не строить визард, пока не будет 2–3 успешных
инсталляций — иначе автоматизируем то, что ещё не устоялось. Сначала оценка качества и A/B на
тумблерах, потом визард.

## Почему это про KAG особенно важно

В обычном сервисе установка — это «порт, пароль, путь к данным». В нашей системе внешних
зависимостей в разы больше, и у каждой есть выбор «качество против цены против приватности»:

| Компонент | Варианты | Чем платим |
| :-- | :-- | :-- |
| Генерация (чат) | локальная (Ollama/llama.cpp), DeepSeek, GigaChat, polza | локально — бесплатно и приватно, но медленно; API — быстро, но платно |
| Эмбеддинги | GigaChat EmbeddingsGigaR, локальные BGE/e5 | качество против облака и лицензии |
| Извлечение таблиц | pdfplumber, наш строчный слой | точность против объёма работы |
| Реранкер | flashrank локально / внешний | задержка против точности (у нас выключен по замеру) |
| Судья (оценка) | платный отдельным ключом / локальная модель | 2,4 ₽ против 20 минут ожидания |
| Граф | Neo4j (есть) / без графа | функции против ресурсов |
| Хранилища | Qdrant, Postgres, Redis — как есть | — |
| SSO | Keycloak (есть) / локальные пользователи | интеграция против простоты |
| Наблюдаемость | профиль `monitoring` (Prometheus/Grafana/алерты) / без него | ресурсы против видимости |

Пользователь, который ставит систему впервые, этих компромиссов не знает: он хочет «просто
запустить». Опытный инженер хочет контролировать каждый шаг. Отсюда два режима.

## Режимы

**Default** (5 вопросов, всё остальное — по нашим рабочим значениям):

1. Каталог данных (по умолчанию `/opt/kag/data`).
2. Модель генерации: локальная (бесплатно, медленно) или API (быстро, платно) — и ключ.
3. Эмбеддинги: ключ GigaChat (проверяется сразу тестовым запросом).
4. Граф: Neo4j включить? (по умолчанию да).
5. Наблюдаемость: профиль `monitoring` включить? (по умолчанию да).

**Advanced** — по разделам: генерация (+ резервный провайдер), эмбеддинги, извлечение таблиц,
реранкер, судья для оценки (отдельным ключом и **другой моделью**, чем генерация), хранилища,
ACL/SSO, наблюдаемость, лимиты (глубина контекста, отбор фрагментов, таймауты модели).

## Требования к визарду (и почему именно такие)

1. **Идемпотентность.** Повторный запуск не ломает систему: если `.env` есть — предложить
   обновить или пропустить, а не перезаписывать молча.
2. **Проверка ключей на входе.** Ключ проверяется тестовым запросом сразу, а не через три дня при
   первом реальном вопросе. Для ключа судьи проверка — один дешёвый вызов с ответом в одно слово.
3. **Секреты только в `.env`** (chmod 600, в `.gitignore`), никогда в `config_store` и никогда в git.
   В отчётах и в UI — маска.
4. **Отчёт о развёртывании** (`DEPLOYMENT.md`): какие компоненты, модели, адреса, какие ключи
   (замаскированы). Это audit-trail установки.
5. **Проверка каждого шага** — тест-стражи, как в коде: после настройки компонента проверяем
   живость (health, скрейп метрик, наличие правил алертов, список коллекций Qdrant).
6. **Проверка прав каталогов монтирования.** Прямо из нашей практики: каталоги, которые Docker
   создаёт от root (например `docker/prometheus/rules`), не дают git положить файлы, и правила
   алертов молча не загружаются. Визард обязан проверять владельца и права и чинить их.
7. **Проверка форматов конфигов, которые никто не читает глазами**: манифест провижининга Grafana
   должен быть в подкаталоге, дашборд — в «голом» формате, `rule_files` — существующий путь.
   Каждая такая проверка появилась у нас после реального отказа.

## Связь с текущей болью

Три находки одного дня (26.09.2026) — это одна болезнь: расхождение между репозиторием и тем, что
реально работает в контейнерах (`config drift`).

| Находка | Как ловил бы её визард |
| :-- | :-- |
| Каталог `docker/prometheus/rules` принадлежал root, git туда не писал | Шаг «правила алертов»: проверка владельца каталога и наличия файла внутри контейнера |
| Дашборды Grafana были в формате HTTP API, а не файлового провижининга | Шаг «наблюдаемость»: проверка, что Grafana видит N дашбордов, а не 0 |
| `/metrics` закрывали два middleware, метрики никто не писал | Шаг «живость»: скрейп `/metrics` и проверка, что серии непустые |
