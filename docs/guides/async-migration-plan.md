# Переход на асинхронные варианты работы: план и обоснование (2026-09-20)

Документ отвечает на вопрос «нужен ли проекту переход на async и где именно он даёт преимущество».
Всё, что здесь есть, опирается на факты из кода и замеры на стенде, а не на общее «async быстрее».

## Что случилось на практике (почему тема вообще возникла)

Две реальные аварии на стенде, обе — из-за синхронного ввода-вывода в асинхронном обработчике:

1. `kg_service.hybrid_search` (драйвер Neo4j **синхронный**), чтения `get_doc_repo().get_all()` и
   `document_service.get_document()` вызывались прямо в корутине чата. Пока они ждали ответа,
   цикл событий был заблокирован — вместе с ним вставал `/health`, контейнер уходил в `unhealthy`
   и лечился только перезапуском. Диагностический признак: CPU 0% и последняя строка журнала
   «Запрос в LLM».
2. Таймаут был только на одну попытку вызова модели (120 с), а попыток в цепочке
   «основной → резерв» до четырёх → до ~8 минут занятого обработчика на один вопрос.

Что уже сделано (этап 0, в ветке TABLES):
синхронные вызовы горячего пути чата обёрнуты в `asyncio.to_thread`; таймаут попытки 45 с, общий
бюджет на цепочку 90 с (`llm_timeout`, `llm_budget` в привязке функции chat), при исчерпании —
понятное сообщение клиенту. Тесты: `tests/test_chat_survivability.py`.

## Масштаб: сколько ещё синхронного в async

Сканер `scripts/scan_sync_io.py src`: **179 мест** (153 уникальных) с синхронным I/O внутри
async-функций. По видам вызовов:

| Вид | Мест | Комментарий |
| :-- | :-- | :-- |
| `config_store` (чтение настроек из БД) | 97 | есть TTL-кэш 2 с, поэтому в БД идут не все |
| проверки путей/файлов (`Path.exists`, `stat`) | 27 | микросекунды, переводить незачем |
| репозиторий документов (БД) | 16 | часть уже обёрнута в `to_thread` на горячем пути |
| остальное (граф, загрузка, админка) | ~39 | смотреть по одному |

Доступные асинхронные варианты в текущих зависимостях: `neo4j 5.27` → `AsyncGraphDatabase`;
`qdrant-client 1.12` → `AsyncQdrantClient`; `SQLAlchemy 2.0.54` → async-движок (нужен async-драйвер
Postgres, сейчас стоит `psycopg2-binary`); `httpx 0.28` async уже используется; `redis 5.2` — есть
async-клиент.

## План по этапам (по возрастанию цены, с ожидаемым эффектом)

### Этап 1. Не async, а убрать лишние вызовы (дешевле всего)

- `config_store`: TTL 2 с → для редко меняющихся ключей (промпты, привязки моделей) поднять и
  инвалидировать по записи (механизм `_cache_del` уже есть);
- на горячем пути не перечитывать настройки для каждого запроса (кэш привязок у `provider_service`
  уже с TTL 30 с — использовать его, а не ходить в БД).

Ожидание: снимает большую часть из 97 потенциальных блокировок. Цена — 1–2 дня, риск низкий.

### Этап 2. Neo4j на async-драйвер (`AsyncGraphDatabase`)

Графовый сервис: 2521 строка, 59 функций, единый синхронный драйвер (`GraphDatabase.driver`).
Начинать с горячего пути — `hybrid_search`, который сейчас обёрнут в `to_thread`.
Что меняется: async-сессии и транзакции (`await session.run`, `async for record in result`),
async-итерация результатов, `await driver.verify_connectivity()`.

Ожидание: поиск по графу перестаёт занимать поток; при 10–50 одновременных чатах запросы не
конкурируют за пул потоков. Цена — 3–5 дней (постепенно, метод за методом), риск средний.

### Этап 3. Qdrant на `AsyncQdrantClient`

Заменить синхронный клиент в поиске и записи (`indexing/embeddings_service.py`), убрать
`to_thread`-обёртки вокруг поиска/upsert; отдельно посмотреть `orphan_service`, `qdrant_monitor`.
Поиск — самый частый внешний вызов после модели, поэтому выгода тут наибольшая по частоте.

Ожидание: минус потоки на каждом поиске. Цена — 1–2 дня, риск низкий-средний (API почти
симметричен, но запись/скролл нужно проверять отдельно).

### Этап 4. Postgres на async (`asyncpg`/`psycopg3` async + SQLAlchemy async)

Нужен новый драйвер, async-движок, async-сессии, аккуратность с миграциями; Celery-воркер
оставляем синхронным (там async ничего не даёт). Делать **только если после этапов 1–3 останутся
измеримые блокировки** (мерить, а не предполагать): большинство чтений настроек к тому моменту
будет кэшировано, поэтому эффект умеренный, а цена — неделя и выше.

## Где async НЕ даст выигрыша (чтобы не тратить силы)

- CPU-тяжёлые задачи: реранкер, OCR, парсинг документов — им нужен поток или процесс, async
  не ускоряет вычисления;
- Celery-воркер: отдельный процесс, внутри него async не нужен. Для скорости обработки корпуса
  правильнее масштабировать воркеры (несколько процессов/очередей), а не переписывать на async;
- низкочастотные вызовы (статусы, настройки админки): дешевле обернуть в `to_thread`, чем
  переписывать на async-драйверы.

## Как измерять выигрыш (иначе это вера, а не инженерия)

1. До и после этапа снимать одинаковый набор: латентность чата под нагрузкой (медиана и 95-й
   перцентиль при 10–20 одновременных запросах), число блокировок цикла событий (инструментировать
   обёртку: сколько миллисекунд суммарно уходит в синхронные вызовы на 100 запросов), утилизация
   пула потоков (`asyncio` default executor), доступность `/health` во время нагрузки.
2. Порог пользы: блокировки цикла сократились, а латентность/точность не ухудшились; иначе откат.
3. Точность мерить тем же способом, что и раньше: набор 75 вопросов, механическая проверка +
   судья (см. `rag-answer-quality-eval`), правило «меньше 4–5 вопросов — шум».

## Что предлагается сделать в первую очередь

Порядок: **этап 1 → этап 3 → этап 2 → этап 4** (сначала убрать вызовы и перевести самый частый
внешний вызов, затем граф, и только по замеру — Postgres). Проверка плана на стороне консультанта:
`reports/_scratch/consult_async_answer.md` (Z.ai/GLM через polza), решение владельца — по итогам.
