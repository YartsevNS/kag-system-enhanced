# Замена OCR: выбранный движок, замеры и что осталось (ветка `paddle-ocr`)

Дата: 28.09.2026. Основание: сравнительный прогон трёх движков на реальной накладной (последовательно, по одному
движку за раз, сервер 41), скрипт — `scripts/ocr_bakeoff.py`.

## Победитель: PP-OCRv5 с распознавателем `eslav` (RapidOCR, ONNX, CPU)

Лицензия Apache 2.0 у кода и весов — это снимает прежний блокер (у Occular веса под OpenRAIL-M с ограничением
по выручке). Русский читается верно, скорость в разы выше.

**Точный рецепт запуска** (подобран перебором — строки не принимаются, нужны перечисления):

```python
from rapidocr import RapidOCR
from rapidocr.utils.typings import LangRec, OCRVersion, ModelType

engine = RapidOCR(params={
    "Rec.ocr_version": OCRVersion.PPOCRV5,   # именно PP-OCRv5
    "Rec.lang_type": LangRec.ESLAV,          # восточнославянские: русский, украинский, белорусский, болгарский
    "Rec.model_type": ModelType.MOBILE,
})
out = engine(image)          # в RapidOCR 3.x это единый объект, текст в .txts (не пара result/elapsed)
```

Почему нельзя «по умолчанию»: RapidOCR 3.9 ставит распознаватель **PP-OCRv6 small**, а PP-OCRv6 кириллицу не
поддерживает вовсе (латиница, китайский, японский). На попытку включить `eslav` для v6 он отвечает
`Unsupported rec.lang_type='eslav' for PP-OCRv6 small model`; по умолчанию русский читается похожими латинскими
буквами («Y Vicnpasnerse Ne 15855 0T 23 wown 2025 r.»), и цифры выживают случайно.

## Почему RussianDocsOCR отклонён для этой задачи

Проект хороший и с чистой лицензией (MIT и на код, и на веса, 215 МБ), но это конвейер для документов,
удостоверяющих личность (паспорт, права, СНИЛС, загранпаспорт). На счёте-фактуре он останавливается до OCR: в
отчёте `DocType: NONE`, `Quality.DocConf -1.86`, `OCR: None`, поля пустые. Для нашего корпуса (накладные, УПД,
ГОСТы) он не подходит. Остаётся как эталон структуры результата (у него есть `doctype`, `quality`, `angle`,
`field_quads`, выпрямленное изображение) — полезно, когда будем выводить наложения в просмотрщике.

## Стратегия: отраслевой конвейер для таблиц (2026-10-03)

Индустрия сошлась на 4-этапном конвейере для документов/таблиц, и **на 80% он уже есть у нас**:

| Этап | Отрасль (продукты) | У нас уже | Доработать |
|---|---|---|---|
| 1. Детекция макета | DocLayout-YOLO / TATR / PaddleOCR layout | сетка по линиям (бланки), VL-модель (таблицы без линий) | **DocLayout-YOLO** как альтернатива VL — там, где нет линий; кроп таблицы по bbox |
| 2. Структура таблицы (TSR) | Docling TableFormer / SLANet (wired+wireless) / RapidTable | своя сетка (wired), Occular TableRecognizer | RapidTable/SLANeXt как резерв для wireless; структура в HTML/JSON |
| 3. OCR в ячейках | PaddleOCR/RapidOCR cyrillic, Occular | Occular (ячейки), PP-OCRv5 cyrillic (страница) | **съём OCR ячеек на PP-OCRv5** для повышения точности чисел |
| 4. Двойное хранение | JSONB в Postgres + линеаризованный текст в Qdrant | Qdrant+Postgres+точный поиск, провенанс уже есть | **линеаризация** строк таблиц для Qdrant: «наименование: Яблоко, цена: 100»; промпт «ищи в JSON, потом отвечай» |

Ключевые решения:

1. **НЕ переносим чужой конвейер целиком.** Верхний слой «поля/роли колонок» у всех custom и у всех свой; у нас он уже написан (deterministic detect_columns + table_validate). Адаптировать надо блоки, а не проект.
2. **DocLayout-YOLO** — реальный кандидат на замену VL-модели для **таблиц без линий** (сейчас ~20-150 с на страницу у Qwen2-VL; YOLO быстрее и детерминированнее). Даёт боксы блоков, но НЕ структуру ячеек — структуру должен доделать SLANet/TableFormer.
3. **Линеаризация таблиц в Qdrant** — конкретное улучшение, у нас не сделано; повышает попадание по строке («цена: 100») и не мешает точному поиску в Postgres.
4. **Оговорка по русскому в PP-Structure**: официальные веса — только eslav/cyrillic mobile; «русский из коробки» в PP-Structure не даёт server-уровень. Это уже измерено (см. раздел «Победитель» выше).
5. **Поправка по PP-StructureV3 (03.10.2026)**: это НЕ «всё-в-одном OCR», а конвейер из 5 модулей —
   preprocessing → OCRv5 (язык читает он, мы выбрали cyrillic) → layout analysis → document item recognition
   (детектор ячеек таблиц, HTML-структура через SLANet, формулы) → postprocessing (JSON/Markdown). Языковая
   часть изолирована в OCRv5; структура и координаты языко-независимы. Значит PP-StructureV3/SLANeXt —
   готовый Этап 2+координаты для нашего конвейера (wired и wireless), а текст берёт наш OCRv5 cyrillic;
   своя сетка остаётся детерминированным запасным путём для бланков с линиями.
6. **Пауза по таблицам в силе** (решение владельца 28.09.2026): здесь фиксируем стратегию, а не пишем код;
   при возврате к работам начинаем с п. 2 и п. 3.

Что НЕ берём из совета ДС (обоснование):

- «заменить всё на PP-StructureV3» — не даёт кириллицу server-уровня и тянет PaddlePaddle (сотни МБ) в образ;
- «применить поячеечно YOLO и OCR одновременно» — YOLO не даёт структуру, если нет сетки;
- «маркdown в Qdrant плох — только линеаризация» — у нас уже есть dense+sparse RRF и точный SQL-поиск в Postgres, линеаризация только усиливает, а не заменяет.

### Замер RapidTable на накладной (03.10.2026, сервер 41)

**Вывод: RapidTable работает и годится как «Этап 2 + координаты» в нашем флоу.**

Измерено на реальной накладной (`skan-nakladnoj3.png`, с линиями):

- `RapidTable()` → `pred_htmls[0]`: HTML-таблица, **21 строка, 243 ячейки, colspan присутствует** (~2)
- `cell_bboxes` — координаты каждой ячейки (для наложения в просмотрщике)
- **время ~6 с на страницу** (включая встроенный OCR)
- контрольные числа из HTML: **4 из 7** (найдены 13 959,9 / 16 751,90 / 45 305,47 / 43 250,36)
  — это лучше, чем у Occular (3 из 7), и сопоставимо с PP-OCRv5 (5 из 7)

Важная деталь: текст в HTML от RapidTable идёт **латинизированный** («Vicnpasnerse Ne Cee-dna 15855»),
потому что RapidTable использует свой OCR по умолчанию. Структура и координаты ячеек при этом верные, поэтому:

```
наш флоу таблиц = RapidTable (структура + координаты ячеек) + PP-OCRv5 cyrillic (текст ячеек)
```

Это снимает и «порог» по арифметике: структура точная, а текст мы подставляем свой (чтение русского у нас уже есть).

Требования к окружению (питфолы):

- **opencv**: RapidTable тянет `opencv-python` (не headless) → на сервере `import cv2` без `cvtColor/split`.
  Лечится: `pip uninstall opencv-python opencv-python-headless opencv-contrib-python; rm -rf .../site-packages/cv2*;
  pip install opencv-python-headless==4.12.0.88` (проверено, `cv2.__version__` = 4.12.0, `cvtColor`/`split` работают).
- **bs4** не входит в зависимости rapid_table — для разбора HTML использовать `xml.etree` или ставить `beautifulsoup4` явно.
- **ssh с 41 на 18**: по внутреннему имени `18` не резолвится (host key verification) — для scp с 41 на 18 использовать
  `yartsevn@192.168.50.18` и правильный ключ.

Что дальше (по флоу, не «всё сразу»):

1. Замер на «Сложный тест.png» (без линий) — RapidTable + наш OCR cyrillic; цель — подтвердить, что wireless тоже даёт структуру.
2. Проверка арифметики по HTML RapidTable + наш текст (доля строк, где количество × цена = стоимость).
3. Интеграция: в `recover_tables`/`table_strategy` ветка «RapidTable → структура; текст ячеек — PP-OCRv5 cyrillic» с переключателем в настройках.

### Интеграционный замер: bbox RapidTable + наш OCR по ячейкам (03.10.2026)

Результат: связка работает (русский читается верно), но выявила ограничение.

- RapidTable даёт 21 строку HTML, 243 ячейки с bbox (8 точек), colspan/rowspan есть.
- Наш PP-OCRv5 cyrillic по вырезкам bbox читает русский корректно («Счет-фактура №»,
  «ОБЩЕСТВО С ОГРАНИЧЕННОЙ ОТВЕТСТВЕННОСТЬЮ "МЕТБОКС"»), в отличие от встроенного OCR RapidTable (латиница).
- Ограничение: RapidTable местами склеивает по 2–3 товарные строки в одну ячейку → наш OCR по такой большой
  вырезке читает всё подряд и смешивает содержимое; из 243 ячеек непустых — 31, арифметика по строкам не
  сходится (строки смешиваются).

Практический флоу (уточнённый):
```
если линии есть        → своя сетка (детерминированно, строки читаются по отдельности)
если линий нет         → RapidTable (bbox/HTML), затем наш OCR по ВЕРТИКАЛЬНЫМ полосам ячейки
                         (доразбивка), а не по всей ячейке целиком
арифметика (table_validate) → арбитр, включать ли таблицу в поиск
```
Это интеграционная правка (доразбивка ячеек), а не «взять готовое» — честный промежуточный итог.
