# Снимки с телефона: сколько весить и что можно сжать

Документ описывает, что происходит со снимком, который сотрудник загружает с телефона через страницу
«Документы», и почему размер уменьшается именно так. Все цифры — замеры на снимках владельца
(скрипты в `scripts/bakeoff/`, запускаются в контейнере api).

## Что происходит сейчас

1. Снимок с телефона приходит как JPEG 5–8 МБ, 3072×4096 (12 МП).
2. При загрузке `DocumentService._normalize_photo` применяет поворот из метки EXIF (без этого снимок
   лёг бы боком), пересохраняет картинку в JPEG с качеством из админки и снимает метаданные камеры.
   Пиксели по умолчанию **не уменьшаются** (порог 6000 px срабатывает только на очень больших снимках).
3. Нормализация выполняется **до** вычисления хеша, поэтому на диске, в базе и при поиске дублей
   фигурирует один и тот же файл.
4. Настройка живёт в админке: «Загрузка документов» → «Уменьшать снимки с телефона при загрузке»,
   длинная сторона и качество (`system/uploads.photo_*`).

## Замеры

Первый снимок владельца (6,96 МБ, 3072×4096, обычная страница с текстом):

| вариант | вес | распознавание |
|---|---|---|
| оригинал | 6,96 МБ | эталон: 36 строк, 15 чисел |
| JPEG 85, 4:4:4 | 3,88 МБ | потерян один токен-число |
| JPEG 80, 4:4:4 | 3,19 МБ | потеряно 7 чисел |
| уменьшение до 3600 px | 2,46 МБ | числа изменились |
| WebP без потерь | 10,31 МБ | совпадает полностью |
| PNG | 17,51 МБ | совпадает полностью |

Второй снимок (5,21 МБ, плотная страница с мелким шрифтом, 19 строк, числа 0 12 23.2 325 54 8):

| вариант | вес | распознавание |
|---|---|---|
| оригинал | 5,21 МБ | эталон |
| JPEG 95, 4:4:4 | 5,13 МБ | потеряны 0, 54, 8 |
| JPEG 92, 4:4:4 | 3,97 МБ | потеряны 0, 12, 54 |
| JPEG 85, 4:4:4 | 2,66 МБ | потеряны 325, 54, 8 |
| WebP 85 | 1,86 МБ | потеряно 12 |
| WebP без потерь | 9,08 МБ | совпадает полностью |

Последний загруженный документ владельца (страница книги, 1,03 МБ после нормализации, 22 строки):

| вариант | вес | распознавание |
|---|---|---|
| текущее состояние | 1,03 МБ | эталон: 22 строки, номер страницы 113 |
| JPEG 70 | 0,79 МБ | совпадает |
| WebP 90 | 0,57 МБ | совпадает |
| пиксели 60% + JPEG 85 | 0,46 МБ | совпадает |

Снятие метаданных без пересжатия пикселей: 0,2–0,3% веса — не рычаг.

## Выводы

- **Уменьшать пиксели нельзя.** Распознавание меняется даже при уменьшении на 12%: движок распознавания
  сам приводит страницу к своему размеру, и лишняя пересборка пикселей размывает мелкий текст.
- **Пересжатие — риск, а не бесплатная экономия.** На плотных документах теряются числа даже при
  качестве 95 (второе поколение JPEG поверх первого). На обычном тексте распознавание выдерживает
  и качество 70, и уменьшение до 60% пикселей — то есть чувствительность зависит от документа.
- **Без потерь сжать нечем:** WebP без потерь и PNG сохраняют распознавание, но весят больше оригинала.
- Проверять такие изменения нужно **сравнением распознанного**, причём распознавать надо именно
  сохранённый файл (декодировать байты), а не картинку в памяти — иначе замер врёт.

## Рекомендации

- Обычная работа: качество 92, пиксели не трогать (значения по умолчанию).
- Документы с мелким шрифтом, таблицами, суммами: качество 95.
- Место важнее риска единичной цифры: 85.
- Нужен гарантированно исходный файл: снять галочку «Уменьшать снимки» — тогда система ничего не трогает.

## Приборы

- `photo_size_check.py` — перебор размеров и качеств (первый замер).
- `photo_zoom_check.py`, `photo_noise_check.py` — разбор по строкам, фильтры уменьшения, повторяемость движка.
- `photo_format_check.py` — форматы и качества с исправленной методикой (распознаём декодированный файл).
- `photo_last_doc_check.py` — запас сжатия на последнем загруженном документе.
- `photo_meta_check.py` — вес метаданных.
- `photo_normalize_probe.py` — сквозная проверка: нормализация → распознавание → настоящая загрузка через API.
- `show_ocr_lines.py` — показать распознанный текст документа (своим распознаванием, если система ещё не обработала).
