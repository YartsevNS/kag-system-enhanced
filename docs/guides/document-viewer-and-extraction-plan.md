# Выход из тупика: как это делают другие и что берём мы

Дата: 27.09.2026. Основание: три параллельных исследования — (1) промышленные сервисы разбора документов
(Azure AI Document Intelligence Studio, Google Document AI, Amazon Textract + A2I), (2) открытые конвейеры
(docling, MinerU, Marker/Surya, PP-StructureV3, Unstructured, OCRmyPDF, RapidTable), (3) подходы к таблицам и
публикуемые метрики. Ниже — только то, что подтверждено документацией и замерами, со ссылками в
исследовательских логах (`reports/` и логи задач делегирования).

## 1. Что мы называем тупиком (и почему это не тупик в распознавании)

Наш корень был не в OCR и не в модели таблиц. Три вещи, которых у нас не было вовсе, а у всех остальных есть:

1. **Страница документа на экране.** Просмотрщик умел только pdf.js, скан не показывался вообще (исправлено
   27.09.2026: ветка `viewMode` — PDF / картинка / текст, образы 2026.09.27.18).
2. **Нормализованная геометрия + текстовый якорь у каждого элемента.** У всех трёх вендоров каждый элемент
   ответа несёт `polygon`/`BoundingBox` (0..1 или в единицах страницы), номер страницы 1-based и `spans`
   (offset/length в общий текст). Это то, что позволяет нарисовать наложение на любой отрендеренной странице,
   независимо от DPI, и связать «ячейку» со «страницей». У нас координаты есть у OCR-строк, но нет у таблиц в
   том виде, в каком их ждёт вьюер.
3. **Связка «запись ↔ область» двусторонняя.** В AWS A2I выбор пары справа подсвечивает её на документе и
   наоборот; в Azure Studio результаты и таблицы — отдельной панелью рядом со страницей. Без этого человек не
   может ни проверить, ни поправить — и любая ошибка распознавания выглядит как «полная ерунда».

## 2. Общие приёмы, которые повторяются у всех (берём целиком)

| Приём | Как реализован | Что делаем у нас |
|---|---|---|
| Две панели: страница слева, структура справа | Azure Studio, Textract console, GCP Workbench | вторую панель делаем: реквизиты + таблица-грид |
| Единая геометрия: polygon + page + текстовый якорь | Azure `boundingRegions{pageNumber, polygon}` + `spans`; AWS `Geometry{BoundingBox, Polygon}`; GCP `boundingPoly` | храним нормализованный полигон и смещение в тексте для каждого блока и ячейки |
| Типы блоков с разными слоями наложения | слово/строка/абзац, таблица, ячейка, ключ-значение, печать/подпись | слои-переключатели: OCR-строки, таблица, ячейки, реквизиты, печати |
| Уверенность на всех уровнях и разбор сверху вниз | Azure: таблица → строка → ячейка; AWS: отдельно Identification/Qualification confidence | считаем уверенность ячейки/строки/таблицы, а не одну цифру на таблицу |
| Отправка в проверку по правилам, а не «проверяем всё» | AWS: конкретный ключ ниже порога, любой ключ ниже порога, отсутствует ключ, случайная выборка; GCP: слайдер порога | очередь проверки: низкая уверенность + не прошла арифметика |
| Панель сырого ответа (JSON) | Azure results tab, Textract `apiResponse.json` | отдаём JSON разбора рядом с визуализацией |
| Правки хранятся ОТДЕЛЬНО от машинного ответа | AWS S3 output, Azure Cosmos с validation outcomes | машина — неизменяема, правки — отдельно, с автором и временем |
| Вендорский review-UI можно не ждать | Google HITL deprecated (16.01.2024), AWS A2I закрыт для новых клиентов, Microsoft советует строить свой | свой интерфейс проектируем сразу с двусторонней привязкой |

## 3. Что берём из открытого (с лицензиями — это решающий фактор)

| Проект | Лицензия | Что даёт | Вердикт |
|---|---|---|---|
| **docling** (IBM) | код MIT, модели по отдельным лицензиям | `DoclingDocument` с провенансом (page + bbox на каждый элемент), TableFormer: TEDS 96.75 PubTabNet / 96.8 FinTabNet, безлинейные таблицы — штатный кейс, ~3 с/страница на CPU (замер IBM) | **берём**: разбор PDF с текстовым слоем и структуру таблиц |
| **PP-StructureV3 / RapidTable / RapidOCR** | Apache 2.0 | явный `block_order` (порядок чтения), `save_to_img` (готовые картинки layout / OCR / порядка чтения / ячеек), классификатор wired/wireless 94.2 %, SLANeXt (TEDS 0.84 на их наборе), **PP-OCRv5 eslav — русский из коробки** | **берём**: OCR кириллицы и модель структуры как страховка |
| **Docling Studio** (scub-france) | MIT, Vue 3 + FastAPI | браузерный вьюер PDF с цветным bbox-наложением, панель синхронизирована со страницей, чанкинг, экспорт | **берём как каркас UI**, свой бэкенд вместо их пайплайна |
| MinerU | Apache-2.0 **+ доп. условия** (коммерческая лицензия при >100 млн MAU или >$20 млн/мес, обязательная атрибуция при онлайн-сервисе) | лучшая отладка порядка чтения (`layout.pdf` с номерами, `span.pdf`) | не основа; держим как эталон/второй движок |
| Marker + Surya | код Apache-2.0, **веса OpenRAIL-M** (до $5 млн выручки) | качество только в VLM-режиме, на CPU >16 с/страница (замер IBM), на таблицах 46–73 | не берём: и лицензия, и CPU |
| Unstructured | Apache-2.0 | худший в замерах (edit 0.586/0.716), тяжёлые зависимости | не берём |

## 4. Про таблицы — честные числа, которые меняют план

1. **Бенчмарки не про наши сканы.** PubTabNet/FinTabNet — это рендеры цифровых документов. На наборе WTW
   (реальные фото и сканы с деформациями) подход «сетка по линиям» даёт TEDS **26.0**, а на ICDAR-2013 — 84–98 %.
   Значит цифры вида «95 % TEDS» ничего не говорят о скане накладной.
2. **Слитые ячейки — главный нерешённый барьер.** Модели row/column часто не умеют `rowspan/colspan` вовсе; у
   TATR и TableFormer отмечены ошибки over-merge/over-segment; у нас merged cells получаются сами из сетки —
   это наше преимущество, и его нельзя терять.
3. **Безлинейные таблицы — отдельный путь.** Детерминированный разбор по линиям там не работает в принципе,
   нужен второй путь (модель структуры либо модель зрения).
4. **Арифметику (кол-во × цена = сумма, НДС, итоги) не ловит ни одна метрика.** Это надо строить своими руками,
   и это единственная проверка, которая отличает правдоподобную таблицу от верной.

## 5. Что делаем (порядок и причина каждого шага)

1. **Порядок чтения текста страницы** — сейчас фрагменты идут в порядке распознавания строк («цио-
   прослеживаемости нальное) и 16 le …»). В PP-StructureV3 порядок чтения — явный артефакт (`block_order`),
   в MinerU он даже нарисован на `layout.pdf`. Дешёвое решение: раскладывать строки на блоки по геометрии
   (проекции по горизонтали/вертикали, колонки, затем сверху-вниз, слева-направо) — это наша задача, не модель.
2. **Вьюер со слоями и двусторонней связкой** (по образцу Docling Studio и Azure Studio): страница (уже есть)
   + слои «OCR-строки / таблица / ячейки / реквизиты», клик по ячейке подсвечивает её на странице. Это то, что
   превращает черновик разбора в проверяемый результат.
3. **Арифметический валидатор строк УПД**: кол-во × цена = сумма (с допуском в копейки), НДС по ставке,
   итоги, суммы прописью против цифр. Результат — вердикт по строке и по документу, независимый от модели.
4. **Два пути по таблицам, роутинг явный**: линии → наша сетка (уже работает, детерминированно, merged cells);
   без линий/обрывки → модель структуры (SLANet через RapidTable/PP-Structure, Apache 2.0) либо модель зрения
   (уже подключена как опция). Выбор пути — по плотности линий и уверенности.
5. **Замена OCR на PP-OCRv5 (eslav) через RapidOCR** — Apache 2.0, русский из коробки, ONNX на CPU. Это
   закрывает наш пункт техдолга «свои веса вместо Occular» и, вероятно, поднимет качество кириллицы.
6. **Набор для приёмки**: 30–50 страниц реальных УПД/накладных с эталоном по ключевым полям и числам.
   Приёмка — не «выглядит похоже», а: арифметика сходится, поля совпали, время на страницу уложилось.

## 6. Чего не делаем и почему

* не покупаем точность модели там, где нужна точность цифр: TEDS ≠ верные числа;
* не включаем таблицы в поиск до прохождения арифметики и набора (это уже зафиксировано настройкой
  `tables_in_fragments=false`);
* не берём VLM-пайплайны (Marker/Surya) на CPU-сервер: качество на таблицах ниже, а веса ограничивают коммерцию;
* не тащим MinerU как основу: лицензия требует атрибуции и отдельной коммерческой лицензии при росте.
