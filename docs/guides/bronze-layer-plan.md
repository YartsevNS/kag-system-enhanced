# Bronze-слой: сырое извлечение отдельно от онтологии

Дата: 2026-11-13. Основание: разбор внешнего плана (docs/guides/pipeline-proposal-comparison.md),
решение владельца «делай, надо продвинуться в качестве».

## Зачем

Сейчас извлечение сразу пишет в TypeDB. Из этого три следствия:
1. Ошибку модели нельзя пересмотреть без повторного вызова модели — а вызов дорог и нестабилен
   (техдолг п.20: 5–25 элементов на один и тот же документ).
2. Решение «это один объект или два» принимается в момент записи, по ключу, без возможности
   применить нормализацию, блокировку и fuzzy-сравнение.
3. Аудит: что именно извлекла модель до нормализации — нигде не хранится.

Bronze-слой решает всё три: сырое извлечение складывается один раз, а нормализация, дедуп и
запись в онтологию становятся повторяемыми детерминированными шагами.

## Схема (Postgres)

```sql
CREATE TABLE IF NOT EXISTS extraction_bronze (
    id            bigserial PRIMARY KEY,
    document_id   text NOT NULL,
    chunk_id      text NOT NULL,
    structural_key text NOT NULL DEFAULT '',   -- путь: стандарт|раздел|пункт
    kind          text NOT NULL,               -- entity | relation
    type          text NOT NULL,               -- security_measure, requirement_derived_from, …
    payload       jsonb NOT NULL,              -- атрибуты (как пришли от модели)
    participants  jsonb NOT NULL DEFAULT '[]'::jsonb,  -- для связей: [{role, key}]
    quote         text NOT NULL DEFAULT '',    -- цитата/evidence span
    raw_ent_key   text NOT NULL DEFAULT '',    -- ключ, который предложила модель
    model         text NOT NULL DEFAULT '',
    prompt_version integer NOT NULL DEFAULT 0,
    extraction_run uuid NOT NULL,              -- один прогон документа
    created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ... ON extraction_bronze (document_id, extraction_run);
CREATE INDEX ... ON extraction_bronze (structural_key);
CREATE INDEX ... ON extraction_bronze USING gin (payload);
```

Ключевое: `extraction_run` — идентификатор прогона. Переизвлечение документа создаёт новый прогон,
старый остаётся для сравнения; «какой прогон считать действующим» решается флагом у документа,
а не удалением строк.

## Поток

    извлечение (LLM) → extraction_bronze (Silver ещё нет)
      → нормализация (строки, regex-коды, словарь алиасов) → bronze_normalized (view или колонки)
      → блокировка по structural_key + типу
      → дедупликация: точный ключ → fuzzy → эмбеддинги, с conflict guard
      → запись в TypeDB (только разрешённые объекты)

Пока дедупликации нет, шаги 2–4 можно запускать в режиме «как сейчас» (точный ключ), но данные
уже лежат в Bronze — значит следующая итерация не потребует модели.

## Что меняется в коде (минимальный первый шаг)

1. `src/indexing/typedb_writer.extract_and_store_typedb`: после `_collect` писать сырьё в
   `extraction_bronze` (одна вставка пачкой), и только потом вызывать `write_facts` как сейчас.
   Двойной записи бояться не надо: TypeDB получает то же, что и раньше, но у нас появляется след.
2. `src/api/services/document_service`: при старте прогона генерировать `extraction_run`
   (uuid), проставлять его всем строкам прогона.
3. Новая страница/эндпоинт: «прогоны извлечения документа» — сколько сущностей/связей дал каждый
   прогон, что изменилось между прогонами (диф по ключам). Это прямой ответ на техдолг п.20:
   будет видно, ЧТО модель теряет от прогона к прогону.
4. Пустые ответы: причина уже пишется в лог (`empty_kind`: no_content / parse_fail, finish_reason),
   с Bronze её можно связать с фрагментом и таблицей.

## Что сознательно НЕ делаем в первом шаге

- Не выключаем прямую запись в TypeDB (риск сломать работающий контур).
- Не меняем чанкинг и не переиндексируем корпус.
- Не внедряем дедупликацию — сначала данные, потом решения по ним.

## Критерии приёмки первого шага

1. Прогон документа создаёт ровно один `extraction_run`; число строк в Bronze = числу
   извлечённых сущностей + связей (сверить по логу прогона).
2. Повторный прогон того же документа создаёт новый прогон, старые строки целы.
3. Эндпоинт сравнения двух прогонов показывает: сколько ключей совпало, сколько появилось,
   сколько исчезло — по типам.
4. TypeDB после прогона содержит то же, что и без Bronze (сверить отпечатком онтологии
   `scripts/onto_fingerprint.py` до/после).

## Риски

| Риск | Что делаем |
|---|---|
| Bronze разрастается (86 документов × ~600 строк) | это десятки тысяч строк, Postgres держит легко; чистим по возрасту прогонов, не по документам |
| Двойная запись замедляет | вставка пачкой 1 запрос на фрагмент, замер до/после обязателен |
| Расхождение Bronze и TypeDB | сравнение отпечатком онтологии в приёмке п.4 |
| Соблазн «сначала дедупликация» | порядок фиксирован: данные → нормализация → решения |
