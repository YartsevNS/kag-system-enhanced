# Оценка качества ответов (эталонный набор + судья-модель)

Зачем: без эталона любое улучшение (порог отбора, реранкер, промпт, глубина контекста) — это
«кажется, стало лучше». Оценка отвечает на вопрос «стало ли лучше» числом, а не ощущением.

## Как устроено

    eval/golden_dataset.jsonl          — эталонный набор: вопрос + эталонный ответ + метка источника эталона
    scripts/eval_collect_answers.py    — сбор ответов и контекстов (запускается НА СТЕНДЕ, ключ судьи там не нужен)
    scripts/eval_rag_judge.py          — оценка судьёй (запускается на ноутбуке, ключ судьи не покидает его)
    reports/eval/rag_eval_<дата>.json  — отчёт: сводка + разбор по каждому вопросу с причинами оценки

Разделение на два шага сделано специально: ключ судьи лежит только на ноутбуке, а стенд отдаёт
лишь ответы и найденные фрагменты.

## Четыре метрики (те же, что в RAGAS, но своими короткими промптами)

| Метрика | Что измеряет | Что означает низкое значение |
| :-- | :-- | :-- |
| `faithfulness` | Опирается ли ответ только на найденные фрагменты | Ответ «дотягивает» факты из модели — риск ошибок, которые пользователь не заметит |
| `answer_relevance` | Отвечает ли ответ на заданный вопрос | Ответ уходит в посторонние темы или неполон по сути |
| `context_precision` | Доля найденных фрагментов, нужных для ответа | Поиск тянет мусор: платим за него в промпте и путаем модель |
| `context_recall` | Есть ли во фрагментах всё нужное для эталонного ответа | Нужного факта в выдаче нет — система не сможет ответить верно в принципе |

Почему не сам RAGAS: он тянет langchain и datasets в то же окружение, где живёт api. Наши промпты
видны и правятся, метрики те же, стоимость копеечная (ключ судьи — отдельный, модель
`deepseek/deepseek-v4-flash-0731`; замер: ~0,1 ₽ на вопрос за все четыре метрики).

## Порядок работы

```bash
# 1. Ответы и контексты со стенда (внутри контейнера api; пароль админа берётся из окружения)
scp reports/_scratch/eval_collect.py eval/golden_dataset.jsonl <стенд>:/home/<user>/kag-system/data/
ssh <стенд> 'docker exec kag-api python /app/data/eval_collect.py'
scp <стенд>:/home/<user>/kag-system/data/collected_answers.json eval/

# 2. Оценка судьёй (ключ судьи на ноутбуке)
python scripts/eval_rag_judge.py                      # все вопросы
python scripts/eval_rag_judge.py --limit 3            # быстрая проверка правок
```

## Устройство эталонного набора

- Вопросы берутся из реальных: `chat_messages` в Postgres (`role='user'`), плюс вопросы владельца;
  контрольную группу дают вопросы на общеизвестные факты — на них видно, выдумывает ли система
  ответ, когда документа в корпусе нет.
- `gt_source` в каждой строке честно помечает происхождение эталона:
  `verified-user` — проверено владельцем, `verified-sql` — проверено вычислением,
  `verified-corpus` — собрано по тексту документа, `verified-common` — общеизвестный факт,
  `auto` — эталон пока извлекает судья из контекста (ручная сверка не сделана).
- Расширять набор нужно в первую очередь строками с `auto`: ручная сверка эталона — это то, что
  превращает оценку в доверенную.

## Что делать с результатами

1. Смотреть не только средние, но и вопросы с низкими метриками: у каждого в отчёте есть `reasons`
   от судьи.
2. `context_recall` низкий → проблема поиска/чанкинга (факта нет в выдаче).
3. `context_recall` высокий, а `answer_relevance` низкий → проблема генерации (промпт, модель).
4. `context_precision` низкий → лишние фрагменты: рычаг «отбор фрагментов» (min_score_gap) и глубина.
5. Любое изменение считать по одному и тому же набору: иначе сравнение бессмысленно.
