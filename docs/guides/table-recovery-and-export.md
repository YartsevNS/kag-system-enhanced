# Восстановление таблиц из сканов и картинок + выгрузка документа

Решение принято 26.09.2026 по итогам замеров. Документ фиксирует: какой движок, как выбираются страницы
для него, как хранятся восстановленные таблицы и как они выгружаются.

## Движок: Qwen2-VL-2B-Instruct (локально, Apache 2.0)

Замеры на сервере моделей 41 (CPU, 20 ядер), локально, без внешних сервисов:

| что подавали | результат | время |
| :-- | :-- | :-- |
| «Сложный тест.png» (таблица, 790×796) | **правильная markdown-таблица: 11 позиций, чистый русский, числа на своих местах** | 225 с |
| полная страница А4 квитанции (1241×1754) | мусор вида `(10,10),(980,887)` | 98 с |

Вывод: на **компактном** фрагменте модель работает отлично, на полной странице упирается в бюджет
визуальных токенов. Значит: страницу режем на фрагменты (шапка + блоки строк) и подаём по частям.
Плюс проверяем рычаг `max_pixels` — если полная страница заработает, нарезка не понадобится.

**Отложено: Granite-Docling-258M.** На CPU генерация разметки полной страницы не уложилась в 30 минут
(разметка DocTags по каждому блоку и ячейке, до 2500 токенов). Для корпуса в 229 документов это сутки
работы. Вернуться к ней имеет смысл только при появлении GPU; вариант «структура от Docling + текст от
нашего OCR» на CPU закрыт.

## Как выбрать, какие страницы отправлять модели (паспорт страницы)

Решаем **по странице**, а не по документу: большинство страниц в цифровых PDF не требует модели вообще.

| признак | откуда берём | порог / правило |
| :-- | :-- | :-- |
| символов текста на странице | результат парсера/OCR | меньше 200 → текстового слоя нет (скан или картинка) |
| таблицы найдены | `document_tables` | есть и `quality ≥ 0.6` → модель не нужна |
| таблицы с низким качеством | `document_tables.quality` | `< 0.6` → отдать страницу модели |
| таблиц нет, но текст «табличный» | эвристика: доля строк с двумя и более числовыми токенами | `> 0.3` → вероятная таблица без разметки → модель |
| доля «мусорных» символов | метрика починки битого текстового слоя | `> 0.05` → модель |

Маршруты: `parser` (обычный парсер), `ocr` (наш OCR, таблиц нет), `vlm_tables` (страница модели),
`none` (пропустить). У каждого решения сохраняется причина — она попадает в карточку документа и в журнал
обработки, чтобы админ видел, почему страница пошла или не пошла в модель.

Ручные рычаги поверх автоматики: выбор маршрута у документа (авто / только текст / OCR / OCR + таблицы
через модель) и кнопка «переобработать страницу через модель». Уже обработанные моделью страницы помечаются,
чтобы не гонять их повторно.

## Хранение восстановленных таблиц (с провенансом)

Данные кладём в существующий табличный слой (`document_tables`, `table_rows`) — благодаря этому чат и
SQL-вычисления работают с восстановленными таблицами без переделок. Дополнительно к текущим полям:

| поле | зачем |
| :-- | :-- |
| `source` | `parser` или `vlm` — видно происхождение таблицы |
| `source_model` | имя модели (например `Qwen2-VL-2B-Instruct`) |
| `source_page` | номер страницы документа |
| `source_markup` | исходная разметка (markdown) — позволяет перепроверить и пересобрать выгрузку |

Это же закрывает вопрос воспроизводимости: по записи видно, что таблица пришла от модели, какой именно
и со какой страницы, а не «неизвестно откуда».

## Выгрузка документа

Все форматы собираются из одного источника — табличного слоя, поэтому не разъезжаются:

| формат | для чего |
| :-- | :-- |
| HTML | точная структура, включая объединённые ячейки (просмотр, печать) |
| XLSX | по листу на таблицу, числа остаются числами |
| CSV | обмен и загрузка в другие системы |
| Markdown | документы и передача в LLM |
| исходник + страницы-картинки | доказательство: что именно было на странице |

Существующая выгрузка (ZIP с файлами и метаданными) остаётся; новый шаг добавляет к ней восстановленные
таблицы в перечисленных форматах.

## Порядок работ

1. **Паспорт страницы и маршрутизация** — без модели: признаки, решение, причина; видно в карточке
   документа и в журнале обработки. Проверяется на существующем корпусе.
2. **Сервис Qwen2-VL-2B на 41** (по образцу сервиса реранка) + вызов из воркера для отобранных страниц,
   с нарезкой страницы на фрагменты и записью результата в табличный слой с провенансом.
3. **Выгрузка документа** с восстановленными таблицами (HTML/XLSX/CSV) и страницами-доказательствами.

Технические требования, которые не обсуждаются: движок живёт на 41 (в образ api его не тащим — мы
специально убрали torch/docling и уменьшили образ на 3,5 ГБ); при недоступности сервиса ничего не ломается
(текст остаётся, таблица не строится, ошибка видна в метрике); обработка асинхронная (Celery), потому что
страница на модели — это секунды-минуты, а не миллисекунды.

## Полные возможности Occular: замеры 27.09.2026

Прогон на сервере моделей (41), occular 0.4.1, с torch CPU, то есть со ВСЕМИ опциональными моделями
(детектор таблиц, структура таблиц с объединёнными ячейками, порядок чтения, определение ориентации).

### Что оказалось важным при установке

    На сервере 41 `pip install occular-ocr` сам по себе недостаточен: `import occular` падает с
      `libGL.so.1: cannot open shared object file`. Нужно заменить opencv-python на
      **opencv-python-headless** (в наших Docker-образах графические библиотеки есть, поэтому там
      работает и так).
    Веса таблиц (`table_detect_v3_fp32.onnx`, `table_struct_split_merge_v2.pt`) скачиваются сами при
      первом использовании и ложатся в `~/.cache/huggingface` (`models--Shivin11--occular-ocr`).
    Модель порядка чтения ставится отдельно: `download_reading_order()` — 432 МБ. Без неё конвейер с
      `reading_order=True` падает с понятной ошибкой, а не молча.

### API, который реально работает

    `OCRPipeline(Settings(reading_order=True)).process_image(path)` → **список** dict'ов с полями
      `['text', 'quad', 'confidence']`. Координаты лежат в `quad` (четыре точки), а не в `bbox` —
      первая проба из-за этого не нашла ни одной строки.
    `TableRecognizer()(img)` (картинка в формате OpenCV) → список таблиц; у таблицы `rows` и `cols` —
      это **диапазоны координат** (пары), а `cells` — dict'ы только с полями
      `['r', 'c', 'rowspan', 'colspan']`; ни координат, ни текста в ячейках нет.
    Отсюда способ заполнения: рамка ячейки строится из диапазонов
      `(cols[c][0], rows[r][0], cols[c][1], rows[r][1])`, а каждая строка OCR кладётся в ту ячейку, в
      которую попадает её центр. Объединённые ячейки учитываются через `rowspan`/`colspan`.

### Результат на квитанции (1241×1754, таблица с линиями)

| шаг | время | результат |
|---|---|---|
| конвейер с порядком чтения | 13,4 с | 142 строки с координатами и уверенностью |
| таблицы | 0,6 с | 2 таблицы: 8×9 и 21×13, с объединёнными ячейками (48 и 135 ячеек) |
| раскладка текста | — | 24 и 53 строки попали в сетку; заполнено 20 и 51 ячейка |

Что получилось в ячейках (фрагмент): «Итого к оплате — 12 503,51», «Капитальный ремонт — 83,4 м2 —
25,8 — 2 133,3», «ИТОГО к оплате — 37 508,65», шапка «Вид платежа / Объем / Тариф / Начислено».

То есть на решётчатых таблицах свой Occular даёт структуру И числа: быстро, детерминированно, без модели
зрения. Это и есть основной путь для счетов-фактур, квитанций, накладных.

### Результат на таблице без линий (файл владельца, 790×796, цветные заливки)

| шаг | результат |
|---|---|
| `TableRecognizer` даже с полными моделями | **0 таблиц** (0,3 с) |
| обычный OCR | 1302 символа, числа столбца «Кол» теряются |
| Qwen2-VL-2B в Ollama (модель `kag-qwen2vl:2b`) | таблица с числами (4, 28, 2, 43, 4, 12, 8, 1, 4), 304 с |

Вывод: таблицу, нарисованную цветными заливками без линий, детектор таблиц не видит в принципе — нужен
другой инструмент. Модель зрения здесь единственный работающий путь, но её надо ограничивать по
генерации: в замере она зациклилась на повторах (91 строка таблицы вместо ~14), поэтому в вызове нужны
ограничение длины, штраф за повторы и выбрасывание дублей после ответа.

### Модель зрения: рабочая настройка вызова (Qwen2-VL-2B в Ollama)

Первый замер дал зацикливание: 91 строка таблицы вместо ~14. Причина — большой лимит генерации и
длинный промпт. Лечение нашлось замером, а не догадкой:

| настройки | результат |
|---|---|
| `num_predict=4096`, длинный промпт | 304 с, 91 строка, повторы по кругу |
| `num_predict=1200`, `repeat_penalty=1.3` | 102 с, 45 строк, **текст испорчен** («в защитной одежде с колимират») |
| `num_predict=1200`, `repeat_penalty=1.15` | 36 с, 9 строк, чисто, но **колонки сдвинуты**, числа путаются |
| **`num_predict=2048`, штраф не задавать, `stop=["

", "```"]`, `temperature=0`, `top_k=1`** | **39 с, 11 строк, повторов нет, числа верные** |

То есть зацикливание лечится ограничением длины и стоп-последовательностями, а **не** штрафом за повторы:
штраф у этой модели портит распознавание. Промпт — строгий: «только таблица, без пояснений; одна строка
таблицы на строку изображения; повторять строки запрещено; числа сохраняй точно».

Остаточный дефект, который надо помнить: у 2B-модели строки иногда смещены по колонкам (текст примечания
попадает в колонку «назначение»), но числа сохраняются — а именно они и терялись в обычном OCR.

Скрипт для повторных замеров: `scripts/vlm_table_clean.py` (вызов, чистка дублей, печать таблицы).

## Как это работает в системе (подключаемая опция в админке)

Схема подключена к обработке документов и управляется из админки — отдельной карточкой
**«Таблицы без линий: модель зрения (VL)»** (рядом с настройками OCR).

    Админка → карточка: тумблер, адрес API сервиса моделей, модель, таймаут, кнопки «Сохранить» и
      «Проверить связь». Настройки лежат в общем конфиге табличного слоя (`vlm_tables_*`), сохраняются
      только свои ключи — остальные настройки таблиц не трогаются.
    Обработка документа-картинки: сначала свой **Occular** (быстро, детерминированно, с объединёнными
      ячейками). Если он таблиц не нашёл **и** опция включена — вызывается модель зрения по API.
      **Выключенная опция не делает ни одного сетевого вызова**: страница просто пропускается.
    Результат попадает в `parsed.pages[].tables` и дальше сохраняется штатным путём
      (`_save_document_tables`) в `document_tables` и строчный слой — с провенансом:
      `extraction_method` = `occular-table` или `vlm-<модель>`, плюс страница и качество.

Параметры вызова модели подобраны замером и закреплены тестом (`tests/test_vlm_tables.py`):
`temperature=0`, `top_k=1`, `num_predict=2048`, **без** штрафа за повторы, стоп-последовательности.
Три стража в тестах: выключенная опция не ходит в сеть; настройки вызова не теряют измеренный рецепт;
сохранение опции не выключает табличный стек.

Файлы: `src/indexing/vlm_tables.py` (клиент, настройки, статус), `src/indexing/table_strategy.py`
(схема Occular → VL, запись в разбор документа), `src/indexing/tables_settings.py` (настройки),
`src/api/routes/admin_models.py` (ручки `/tables-vlm`), `src/api/static/admin.html` (карточка),
`src/api/services/document_service.py` (вызов схемы для картинок).

## Объединённые ячейки: torch в базовом образе (27.09.2026)

Первый сквозной прогон на стенде показал в логе контейнера:

    PyTorch-путь структуры недоступен (No module named 'torch'); откат на ONNX split —
    сетка строк и колонок без объединённых ячеек.

То есть Occular работал на упрощённом пути: сетку он отдавал, а **объединённые ячейки** (шапка
счёта-фактуры, где одна ячейка на несколько колонок) не восстанавливал. Причина — базовый образ
собирался БЕЗ torch специально (в начале проекта torch тянулся вместе с CUDA и раздувал образ).

Что изменилось:

    в базовый образ ставится `torch` **только CPU-сборкой** с официального индекса
      (`--index-url https://download.pytorch.org/whl/cpu`): CUDA-версия тянет гигабайты драйверов, а нам
      нужен лишь torch-путь структуры таблиц;
    в список предзагружаемых весов добавлена модель объединённых ячеек `table_struct_split_merge_v2.pt`
      — для закрытого контура веса обязаны быть внутри образа, докачиваться на месте они не могут;
    база теперь `kre44et/kag-base:2026.09.27.3`, на неё смотрят Dockerfile, Dockerfile.worker и
      Dockerfile.mcp.

Цена: образ тяжелее — torch CPU добавляет около 900 МБ. Проверка после сборки: запустить
`scripts/occular_tables_probe.py` на странице квитанции внутри контейнера и убедиться, что у ячеек
появились поля `rowspan`/`colspan`, а предупреждение о недоступном PyTorch-пути пропало.

## Рабочая схема: проверено на проде (27.09.2026)

Сквозной путь на живом стенде, документ владельца «Сложный тест.png» (image/png, 790×796):

    1. в админке включена опция (настройки сохраняются; проверено повторным чтением: enabled=true,
       сервис доступен, модель найдена);
    2. документ отправлен на переобработку (задача process_document, force=true) — 128 с;
    3. в журнале воркера: «[tables] восстановлено таблиц для картинки: 1 (Occular таблиц не нашёл за 0.3 с
       (нет линий сетки); распознано моделью kag-qwen2vl:2b за 80.8 с (строк 13))»;
    4. в табличном слое документа: **1 таблица, 12 строк, страница 1, чем распознано — vlm-kag-qwen2vl:2b**.
       Строки дополнительно легли в строчный слой (SQL-вычисления в чате работают по ним как обычно).

То есть путь «картинка → свой Occular → (если он не нашёл и опция включена) VL-модель → табличный слой»
работает в системе, а не только в замерах. Проверка повторяется скриптами
`scripts/verify_tables_vlm.py --check|--enable|--document <id>` и `scripts/e2e_vlm_table_test.py`.

## Таблицы со сканов НЕ идут во фрагменты (27.09.2026, вечер — по жалобе владельца)

Владелец открыл документ и увидел «полную ерунду»: страница «Чанки» и поиск получали markdown восстановленной
таблицы с ЖЁСТКО проставленным качеством 0.6, то есть каша из кусков ячеек выглядела как годный разбор:

```
| Рама Pro MS 20x10 18 531299006458 |  |  |  | 796 | ия |  | 2 341,7 | 9 6,97 | Без нациа | - 20% | …
```

Почему порога по качеству недостаточно: метрика структурная (заполненность, доля осмысленных ячеек) и мусорный
разбор накладной она оценила в **0.72**. Число не отличает годный разбор от каши — значит по нему нельзя решать,
пускать таблицу в поиск.

Решение:

  * настройка `tables.tables_in_fragments` (по умолчанию **false**): таблица со скана/картинки во фрагменты не
    идёт, текст документа формируется обычным распознаванием — как было до табличных правок;
  * порог качества остаётся вторым фильтром, но не единственным;
  * таблица живёт в **табличном слое**: видна в карточке документа и в просмотрщике вместе с честной оценкой,
    где её может оценить человек. В поиск она пойдёт, когда разбор будет проверен на наборе документов.

Проверено на стенде после переобработки накладной: было 9 точек (4 табличных фрагмента + 4 текстовых + карточка),
стало **5** (карточка + 4 текстовых), табличный слой — 1 таблица, 27 строк, качество 0.721 «occular-table».

### Что остаётся (корневая проблема, не косметика)

Текст скана идёт во фрагменты в порядке распознавания строк, без сборки в читаемый текст: фрагмент выглядит как
«цио- прослеживаемости нальное) и 16 le и 126 12 6 22,10 Без лицо 2016 796…». Это не связано с таблицами —
так было и раньше, но именно на этом фоне табличные фрагменты делали страницу нечитаемой. Настоящее лечение —
собирать текст страницы по порядку чтения (модель порядка чтения Occular / геометрия блоков), а не отдавать
поток строк как есть.

## Общность схемы: что перестало быть подгонкой под один документ (27.09.2026, вечер)

Схема изначально работала на одной накладной, и три её решения были привязаны именно к тому скану:

| было | стало |
|---|---|
| увеличение фиксированное ×3 (под мелкий скан: текст в ячейке ~8 px) | масштаб выбирается по измеренной высоте строки сетки (цель ~36 px), пределы — ×4 и по ширине изображения |
| выравнивания нет: линии искали на исходной картинке, а распознавание внутри Occular выравнивало её само — на наклонённом скане координаты сетки и строк расходятся, разбор ломается | страница выравнивается по профилю линий (перебор углов ±4°), распознавание идёт по тому же выровненному изображению |
| ячейка определялась краями строки с точностью до пикселя, разрезка — с произвольным пределом в 6 колонок | колонка «своя», если строка закрывает её не меньше половины; разрезка только по границам, где в тексте пробел |

### Замер на двух разных документах (не на одном)

| документ | сетка | заполнено ячеек | качество | время |

### Ещё НЕ проверено

Страницы ГОСТов, таблицы без линий (скриншот Excel — там резервная модель зрения), фотографии документа,
банковская выписка. Для полной уверенности нужен проверочный набор 6–8 документов разных типов и один и тот же
замер по каждому. Признак приёмки — не «хорошо на накладной», а «на всех не хуже порога и числа сходятся с
картинкой».

## Питфол сборки: SQLAlchemy 2.1 ломает драйвер PostgreSQL (27.09.2026)

Поймано живьём при пересборке базового образа (добавляли torch). Незафиксированная зависимость
`SQLAlchemy>=2.0.0` подтянула 2.1.1, а он для URL `postgresql://` требует драйвер `psycopg` (третья версия),
тогда как в образе стоит `psycopg2-binary`. Последствие коварное: `config_store` перестал читать и писать
настройки (`get` → None, `set` → False) и система молча работала на значениях по умолчанию — внешне это
выглядело как «настройка не сохраняется», хотя причина в драйвере БД.

Фикс: `sqlalchemy>=2.0,<2.1`. Проверка после выката обязательна: `sqlalchemy: 2.0.x`,
`config_store.set(...) → True`, значение читается обратно, здоровье 200.

## Формат ответа модели зрения: замер и выбор (27.09.2026)

Владелец предложил просить у модели HTML. Идея верная по сути — markdown не выражает объединённые
ячейки (ни colspan, ни rowspan), а HTML выражает. Но её надо было проверить цифрами, поэтому замер
(scripts/vlm_format_compare.py) на файле владельца, модель Qwen2-VL-2B, эталон — 10 чисел столбца «Кол»,
прочитанных с изображения:

| формат | время | символов | строк | чисел | совпало с эталоном |
|---|---|---|---|---|---|
| markdown | 43,1 с | 17 | 0 | 0 | 0 из 10 (таблицу не вернул) |
| HTML | 145,8 с | 5275 | 28 | 27 | 10 из 10 |
| **JSON** | **27,6 с** | 1154 | 10 | 10 | **10 из 10** |

Вывод: JSON даёт ту же точность, что HTML, но в пять раз быстрее и в разы компактнее. Поэтому формат
стал настройкой табличного слоя (ключ vlm_tables_format), по умолчанию **json**; в админке — выбор из трёх
вариантов с этой таблицей в подсказке. Разборщики ответов терпимые: HTML разворачивает colspan
в пустые ячейки, JSON переживает markdown-обёртку и текст вокруг ответа.

Остаточный дефект 2B-модели (зафиксирован): начиная со второй строки столбцы иногда сдвигаются —
значение «Назначение» уезжает в предыдущую строку. Числа при этом сохраняются полностью, а именно они
терялись при обычном распознавании. Лечится либо моделью крупнее (qwen2vl 7B), либо постобработкой
по сетке колонок.

Проверка на живом проде (документ «Сложный тест.png», JSON-режим): в табличном слое шапка
«Наименование устройства, блока | Назначение устройства, блока | Количество устройств, блока |
Примечание», 12 строк данных, качество 0,6, распознано vlm-kag-qwen2vl:2b, числа 4, 28, 2, 43, 4, 12.

## Своя сетка таблицы по линиям + распознавание ячеек (27.09.2026)

Проверка на реальном скане накладной (`skan-nakladnoj3.png`, 1024×724) показала, что библиотечный разбор
структуры на плотных бланках не годится: `TableRecognizer` вернул **23 строки нулевой высоты из 30**
(диапазоны вида «652→652»), а из отданной геометрии получалось 20% заполнения с перемешанными значениями.
Текста в ячейках библиотека не даёт вовсе — это её документация и подтверждает.

Что сделано вместо этого:

    **Сетка по линиям бланка** (`src/indexing/table_grid.py`): морфология + проекции находят горизонтальные
      и вертикальные линии. На том же скане — 29 горизонтальных и 21 вертикальная линия за 0,13 с.
      Внутри каждой полосы строки учитываются только реально нарисованные вертикальные линии, поэтому
      **объединённые ячейки получаются сами** (где линии нет — ячейка шире).
    **Увеличение ×3** перед разбором обязательно: у низкоразрежённых сканов текст в ячейке ~8 px высотой,
      и распознавание на таком размере даёт мусор (проверено: уверенность 0,00–0,04 против 0,78–0,97 после
      увеличения).
    **Раскладка текста по ячейкам**: строка внутри одной колонки идёт в ячейку как есть; строка, накрывающая
      несколько колонок («796 шт 796 шт 796 шт»), режется по линиям колонок и распознаётся по частям одним
      пакетным вызовом (`CRNNRecognizerONNX.recognize` принимает список рамок — ~50 мс на ячейку).
    **Честная метрика качества** вместо заглушки 0,6: заполненность + осмысленность ячеек; ниже порога
      таблица признаётся непригодной и включается следующий путь (библиотечный разбор, затем модель зрения).

### Замер до и после на одной накладной

| | библиотечный разбор | сетка по линиям + ячейки |
|---|---|---|
| сетка | 30×15, **23 строки нулевой высоты** | **28×19**, все строки настоящие |
| заполнение | 20% ячеек | **265 ячеек (85%)** |
| шапка | каша из реквизитов | читается: «Наименование товара / Единица измерения / Количество / Цена (тариф) / Стоимость товаров / В том числе сумма акциза / Налоговая ставка / Сумма налога / Стоимость товаров» |
| числа | слипшиеся блоки | построчно: 2 791.98, 3 761,60, 22 500,00, 2 512,30, 25 123.00, 7 208,9, 43 250,36 |
| время | 33,6 с | 24,5 с (в конвейере, модель прогрета) |

В конвейере путь вызывается первым; журнал воркера пишет причину и метрику:
«восстановлено таблиц для картинки: 1 (сетка по линиям: 28 строк × до 19 колонок, качество 0.60, 24.5 с)».

### Доработано 27.09.2026 (вечер)

    **Разрезка по полному набору колонок.** Раньше строка резалась только по линиям своей полосы: в строках
      без внутренних вертикальных линий ячейка выходила широкой и значения смешивались. Теперь границы для
      разрезки берутся из вертикальных линий всей таблицы, с пределом 6 колонок (слишком широкую строку,
      например заголовок на всю таблицу, не режем — иначе теряем текст). Раскладка готовых строк по-прежнему
      идёт по линиям строки, поэтому объединённые ячейки сохраняются.
      Результат на той же накладной: заполнено 373 ячейки вместо 265, колонок 20, и каждая позиция читается
      целиком — «531299000402 | 2 | Балка MS Pro 150 b | 796 | шт | 22 | 6,54 | 13 959,9»,
      «F406180B0 | в | Настил для полки М5 | 96 | и | 11 | 2 150,1 | 23 651.83».
    **Таблицы видны в просмотрщике** (`/viewer`): сворачиваемый блок «Таблицы документа» показывает число
      таблиц, для каждой — страницу, строки, качество, чем распознано и саму таблицу (первые 25 строк, числа
      выровнены вправо). Раньше в просмотрщике был только плоский текст, и восстановленную таблицу увидеть
      было негде.

Осталось: мелкая грязь в отдельных ячейках (лишний код товара перед наименованием, «3 a» в колонке номера
строки) — лечится проверкой по соседним строкам; и модель зрения остаётся резервом для таблиц без линий.
