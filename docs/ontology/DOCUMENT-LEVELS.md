# Иерархия документов ИБ — рабочий промпт владельца

Сохраняется как опорный документ для разметки онтологии: как классифицировать документы
и какие связи строить между уровнями.

## 1. Иерархия документов ИБ

Каждый документ или его фрагмент относится к одному из 4 уровней:

1. ПОЛИТИКА — стратегия, цели, «ЧТО» защищаем и «ЗАЧЕМ», верхнеуровневые требования без конкретных технологий.
2. ВНЕШНИЙ РЕГУЛЯТОР / ГОСТ — законы, ГОСТ Р ИСО/МЭК 27001, требования ФСТЭК/ФСБ, внешние обязательные рамки.
3. СТАНДАРТ / РЕГЛАМЕНТ — процессы организации, «КТО», «КОГДА» и «В КАКИХ ГРАНИЦАХ» выполняет процессы ИБ, метрики и роли.
4. ИНСТРУКЦИЯ / РУКОВОДСТВО — пошаговые технические алгоритмы, «КАК ИМЕННО» настроить, чек-листы для ИТ и ИБ администраторов.

## 2. Базовая онтология сущностей (метамодель)

- Документ — сам нормативный акт, его уровень и статус.
- Требование — конкретное предписание, обязанность или ограничение.
- Роль — субъект, ответственный за выполнение (CISO, Администратор ИБ, Пользователь).
- Ассет / Актив — объект защиты (Данные, Инфраструктура, ИС, Персональные данные).
- Угроза / Риск — от чего защищаемся.
- Контрмера / Контроль — техническая или организационная мера защиты.
- Процесс — регулярная деятельность (Управление инцидентами, Аудит, Логирование).

## 3. Правила связей

- Документ нижнего уровня → ССЫЛАЕТСЯ_НА / ДЕТАЛИЗИРУЕТ → Документ высшего уровня
- Роль → ЯВЛЯЕТСЯ_ВЛАДЕЛЬЦЕМ / ВЫПОЛНЯЕТ → Процесс или Требование
- Контрмера → СНИЖАЕТ → Угроза / Риск
- Требование → ПРИМЕНЯЕТСЯ_К → Ассет

## 4. Формат ответа модели-разметчика

1. ОПРЕДЕЛЕНИЕ УРОВНЯ — уровень и краткое обоснование.
2. КЛЮЧЕВЫЕ СУЩНОСТИ — списком: Роли, Ассеты, Требования.
3. СВЯЗИ ДЛЯ ОНТОЛОГИИ — триплеты «Субъект — Связь — Объект».
4. ПРОБЕЛЫ И ПРОТИВОРЕЧИЯ — например, инструкция декларирует политику, или у требования нет роли-исполнителя.

## 5. Соответствие нашей схеме TypeDB

| пункт промпта | в нашей схеме |
|---|---|
| уровень 1 — политика | `company_document` (source_kind=company) |
| уровень 2 — внешний регулятор | `regulatory_document` + `regulator` |
| уровни 3–4 — стандарт/инструкция | сейчас тоже `company_document`; разделение не введено |
| документ детализирует документ | `document_reference` (документ → документ), `document_hierarchy` (пункт → пункт) |
| роль выполняет процесс/требование | `responsibility` (responsible, duty_requirement, duty_control, duty_process, duty_role) + `actor_role` |
| контрмера снижает угрозу | `control_mitigation` (mitigating_control, mitigated_threat) |
| требование применяется к активу | `requirement_applicability` (requirement, target_system) |
| пробелы и противоречия | функции целостности в functions-v3.tql + очередь разбора |

Пробел для закрытия: у документа нет атрибута уровня (1–4). Политика и инструкция сейчас —
один тип `company_document`, различить их можно только по названию. Кандидат: атрибут
`doc_level` (policy | regulator | standard | instruction) в ядре + определение уровня моделью
при извлечении.

Полный текст промпта владельца:

> Ты — эксперт по информационной безопасности, системный аналитик и специалист по разметке онтологий.
> Твоя задача — анализировать загружаемые документы ИБ и распределять их сущности по уровням иерархии
> и элементам онтологии.
> (см. разделы 1–4 выше)
