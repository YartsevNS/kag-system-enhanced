### ПРАВИЛА:
1. id в JSON = ent-key. Формат "тип:ключ", глобально уникальный. Ключ пиши строчными буквами и одним алфавитом на весь документ, без смеси кириллицы и латиницы: regulator:фстэк, doc:фстэк|приказ|239, element:фстэк|239|3.1, law:фстэк|239|3.1, measure:фстэк|239|ia-1. Один идентификатор на сущность; второй не генерируй.
2. Бери только типы, атрибуты и роли из схемы. Новые не придумывай.
3. Обязательное (@key, @card(1..1)) отсутствует в тексте — сущность не создавай. Опциональное отсутствует — опусти поле. Это правило сильнее правила 2.
4. Даты — строка ISO 8601 ("2026-11-08"). cii-category — целое 1..3 (обязательно для объекта КИИ). version_status обязателен у каждой document_version: действующая редакция — current, заменённая — superseded, отменённая — repealed, проект — draft. requirement_kind — только certification, organizational, technical, process (это КАТЕГОРИЯ требования, а не степень обязательности; степень — obligation-level). Другие значения не пиши: функции вывода ищут точные строки.
5. Акт и редакция — разные сущности: документ (title, document_key) и document_version (version_string, version_status). Все редакции связывай document_has_version; действующую — дополнительно current_version_of, и она у документа одна. Ключи: document_key = "издатель|тип|номер"; у требования requirement_key = document_key + "|" + requirement-id; у меры measure_key = document_key + "|" + код меры. Оба — @key, их обязательно заполнять.
6. Трассировка — связями: document_structure (версия → пункт), requirement_derived_from (требование → пункт), requirement_definition (требование → мера), measure_source (мера → пункт), а для документа компании — requirement_coverage (какое требование он покрывает). Строки source-* — денормализация, они не заменяют связи.
6.1. Остальные связи из схемы создавай при явном основании в тексте: document_issuance (регулятор издал документ), supersedes (новая редакция заменяет старую), document_hierarchy (пункт вложен в пункт), compensatory_relation (мера компенсирует меру), measure_applicability (мера применима к объекту), requirement_evidence (доказательство выполнения требования), requirement_basis (документ — основание требования), document_compliance (документ компании соответствует нормативному), document_assignment (документ закреплён за объектом), asset_protection (СЗИ защищает объект), threat_applicability (угроза применима к объекту), threat_measure (мера закрывает угрозу). Основания в тексте нет — связь не создавай; но и утверждённую текстом связь не теряй.
7. Связи бинарные, кроме certification (три участника: certified_software, certificate, basis_requirement). basis_requirement указывай только при явном основании в тексте.
8. Сертификат: есть номер — создавай certificate (cert_number обязателен, орган и срок — если есть) и связывай certification. Без номера certificate не создавай. Отдельного признака «сертифицировано» у СЗИ в схеме нет: источник правды — объект certificate и связь certification.
9. requirement_applicability — только к конкретному объекту КИИ. Если сказано «для объектов 1 категории», объект не выдумывай: оставь категорию в description требования.
10. Блок «КОНТЕКСТ ДОКУМЕНТА» в начале фрагмента заполняет пайплайн: document_key, title, doc_type, number, version_string, kag_document_id. Эти значения бери буквально, не придумывай и не меняй; повторно указывать их в attributes не обязательно — пайплайн подставит сам. Издатель (первая часть document_key) известен из контекста: создавай regulator и document_issuance, если в тексте или контексте есть название издателя; названия нет — regulator не создавай.
11. Не извлекай по простому упоминанию: нужна утверждающая формулировка. Нет данных — пустые массивы.
12. description требования и text_content пункта — дословно из текста; обрезать можно только по границе предложения. Не пересказывай и не добавляй того, чего в тексте нет.
