# Словарь семантики v0 (гипотеза, проверяется разметкой)

Черновик к дорожной карте `docs/plans/semantics-and-pipeline-roadmap.md` (пункты A1–A3).
Статус: **гипотеза**. Проверяется пробной разметкой через JEV (пункт D3) и правками владельца.
Правило: код типа — латиницей (стабильный, безопасный для движка), русское название — только для показа.

## 1. Три оси + фасеты (напоминание модели)

- **Тема (рубрика)** — дерево «домен → аспект», МНОГОЗНАЧНОЕ, по умолчанию не ограничивает поиск.
- **Вид документа** — один на документ, из словаря ниже.
- **Издатель** — ссылка на класс «Организация».
- **Фасеты** — независимые перечни, могут быть пустыми и многозначными.

| Вид (код) | Название | Пример |

## 3. Типы связей (ядро v0)

Код латиницей; поля обязательны ко всем: определение, направление, классы, пример, «не путать с».

### 3.1. Документ → Документ (основание: словарь DataCite, `relatedIdentifier`)

| Код | Название | Определение | Не путать с |
|---|---|---|---|
| `part_of` | часть целого | документ входит в состав другого (приложение, изменение, раздел, часть) | `belongs_to` (членство в серии), `new_edition_of` |
| `new_edition_of` | новая редакция | заменяет другой как более новая редакция ТОГО ЖЕ документа | `amends` (изменение не заменяет документ), `part_of` |
| `references` | ссылается на | в тексте есть прямая ссылка на другой документ | `based_on` (разработан на основе, а не сослался) |
| `amends` | изменяет | документ изменения вносит правку в другой документ | `new_edition_of` (изменение не новая редакция), `part_of` |
| `repeals` | отменяет | признаёт другой документ утратившим силу | `new_edition_of` (замена ≠ отмена) |
| `based_on` | основан на | разработан на основе другого документа | `references` |
| `belongs_to` | принадлежит к | членство: стандарт принадлежит серии, организация — группе | `part_of` (вложенность) |

### 3.2. Документ → Организация / лицо / значение

| Код | Название | Направление | Пример |
|---|---|---|---|
| `issued_by` | издан организацией | Документ → Организация | Приказ издан Банком России |
| `adopted_by` | принят организацией | Документ → Организация | стандарт принят организацией |
| `addressed_to` | адресован | Документ → Организация/Лицо | информационное письмо адресовано подразделениям |
| `dated` | датирован | Документ → Дата | договор от 09.11.2020 |
| `for_amount` | на сумму | Документ/Обязательство → Сумма | договор на 3,5 млн руб |
| `signed_by` | подписан | Документ → Лицо | акт подписан директором |
| `located_at` | расположен | Организация/Объект → Место | организация по адресу |

### 3.3. Системные (нужны конвейеру, не для человека)

| Код | Назначение |
|---|---|
| `mentions` | фрагмент упоминает сущность (существующая `MENTIONS`) |
| `has_chunk` | документ содержит фрагмент (существующая `HAS_CHUNK`) |
| `related_to` | **временная** общая связь: подлежит замене (см. C1 дорожной карты — сейчас это
   квадратичный шум: полный граф пар сущностей документа, ~74% всех связей) |

## 4. Фасеты (закрытые перечни)

| Фасет | Значения (v0) | Комментарий |
|---|---|---|
| `protection_subject` (предмет защиты) | данные, сети, люди, серверы, сервисы | многозначный |
| `stage` (этап) | проектирование, эксплуатация, вывод из эксплуатации | держим как фасет, логику не строим |
| `status` | проект, действует, приостановлен, отменён, утратил силу | один на документ |
| `normative_force` (нормативная сила) | обязательный, рекомендательный, справочный | один на документ |
| `classification_mark` (гриф) | открытый, ДСП, коммерческая тайна, персональные данные | многозначный |

## 5. Тема (рубрика): первый уровень

`информационная_безопасность`, `юриспруденция` (сквозная — предъявляет требования другим доменам),
`экономика_и_финансы`, `банковское_регулирование`, `медицина`, `пожарная_безопасность`,
`информационные_технологии`, `искусственный_интеллект`, `управление_персоналом`, `иное`.

Второй уровень (аспекты) — внутри домена; дерево наполняется по мере разметки, не выдумывается заранее.

## 6. Как проверяем (что должно случиться дальше)

1. Разметка 500 фрагментов через JEV по этому словарю: вид документа, рубрика, фасеты, тип связи между
   парами сущностей. Смотрим: долю уверенных ответов (>0,9), долю «other», какие варианты модель
   путает (`part_of` vs `belongs_to` — главный риск).
2. Правки словаря по фактам разметки (не по воображению).
3. Только после этого — перенос словаря в код: проверка типов на записи, поля в данных, локальный
   «ученик» вместо облачной модели.
