# План: чанкинг и лексическая ветка поиска (бэклог)

> Составлен 2026-09-12. Статус: **не делаем сейчас**, это заготовка на будущее.
> Предпосылка: гибридный поиск (dense + sparse BM25 + RRF) нужен, но текущая
> BM25-ветка проигрывает плотному поиску и выключена в конфиге.

## 0. Обновление 2026-09-12 (вечер): лексическая ветка починена и включена адресно

Сделано:

- `src/indexing/lexical.py` — нормализация ё→е, ~180 стоп-слов, суффиксный стеммер
  с усечением длинных основ («получение»/«получить» → «получ»); числа и номера
  стандартов не стеммируются;
- IDF включён на коллекции: Qdrant 1.12 принимает `modifier: idf` у sparse-вектора
  на существующей коллекции (`PATCH /collections/kag_documents`), пересоздание не нужно;
- `scripts/reindex_sparse.py` — пересчёт sparse-векторов локально (2049 точек за 1.7 с),
  без эмбеддингов и LLM, через `update_vectors` по id точки;
- гибрид включается адресно: режим `hybrid_auto` в админке («🔍 Настройки поиска»),
  гибрид применяется только к запросам с точными терминами (ГОСТ/ISO/СТО, приказ/
  положение/указание, №, номера 7403-У и 5.2.1, длинные числа, кавычки);
- замеры на 7 вопросах (один индекс): dense hit@1 0.714 / MRR 0.821;
  sparse-only 0.571 / 0.669; hybrid RRF 0.714 / 0.774; hybrid DBSF 0.714 / 0.767;
  hybrid_auto 0.714 / 0.821 — то есть адресное включение не ухудшает ничего,
  а лексическая ветка работает там, где она уместна.

Осталось (и почему): необязательные опции, не задачи

Ничего из перечисленного ниже делать НЕ обязательно. Тюнинг весов и порогов нужен
только если появится конкретная цель, которая без него не достигается. Сейчас такой
цели нет: режим `hybrid_auto` включён, просадки относительно плотного поиска нет,
точные запросы (номера ГОСТ/приказов/пунктов) закрыты двумя механизмами —
маршрутизацией в BM25 и детерминированными фильтрами payload
(`standard_number`/`clause`/`section`).

- Тюнинг весов фьюжна и порогов — нужен ТОЛЬКО если захотим включить
  `hybrid_always` (равноправный гибрид на каждый запрос). Зачем это может
  понадобиться — непонятно: на замерах он проигрывает плотному. Пока не появится
  цель «лексическая ветка должна учитываться всегда», тюнинг — работа в пустоту.
- Набор вопросов 20-30+ — нужен для любой тонкой настройки (веса, пороги, длина
  стема). Пока тонкой настройки нет в планах, набор не нужен; 7 вопросов хватает,
  чтобы ловить грубые регрессии.
- Проверка лексической ветки на «точных» запросах — это проверка гипотезы, а не
  обязательный шаг. Частично она уже сделана: на запросах «требования ГОСТ Р
  57580.1-2017» и «СТО БР БФБО-1.9-2024» режимы дают разные скоры, но ОДИН и тот же
  документ первым — то есть плотный поиск и без BM25 справляется с номерами.
  Возвращаться стоит только если из эксплуатации придут реальные промахи
  (запрос содержит точный термин, документ в базе есть, а поиск его не нашёл).
- Сплиттер и чанкинг по пунктам — пилот, см. разделы ниже. Тоже опция: нужны
  качественные чанки для НПА, а не «потому что у модели красивая карточка».

Что реально повышает ценность поиска (если хочется двигаться дальше):

1. Расширить корпус. 17 документов и 7 вопросов — это стенд, а не показательная
   выборка; любые метрики здесь шумят, и на них нельзя принимать решения.
2. Собирать реальные промахи: логи чата и вопросы из эксплуатации дают то, чего
   не даст синтетический набор, — и именно они станут обоснованием любой правки.
3. Сплиттер по пунктам/семантике — когда появится задача «чанки для НПА должны быть
   самодостаточными».


## 1. Где мы сейчас

- Чанкинг: сегментный (абзац/таблица/страница накапливаются до `chunk_size`),
  сегменты-гиганты режет `RecursiveCharacterTextSplitter`.
  Действующие значения — **1500 символов, overlap 225** (`src/config.py`,
  `CHUNK_SIZE`/`CHUNK_OVERLAP`; в `config_store` ключа `chunking` нет — он
  пропал вместе с томом postgres 2026-09-12, поэтому работают дефолты кода).
- Sparse-ветка: `embeddings_service._tokenize_sparse` — CRC32 от токенов без
  стемминга, IDF, стоп-слов и нормировки длины; Qdrant-фьюжн RRF без весов.
- Замер на 7 вопросах (один индекс): dense MRR 0.821 против hybrid 0.802,
  слабый кейс «текущая ситуация в российской экономике» — 4-е место на dense
  против 9-го на hybrid. Поэтому `search:config.sparse_enabled = false`.
- Важное: sparse-векторы в Qdrant **уже построены** для всех документов, так что
  включение ветки обратно — это флаг в конфиге, без переиндексации.

## 2. Что рассмотрели (артефакты AGmind, Apache-2.0, 2026-09-12)

### agmind-rag-splitter-ru (v2) — режет документ по индексам, текст не переписывает

- LoRA-дообучение `t-tech/T-lite-it-2.1` (Qwen3-8B). Вход — текст, заранее
  разбитый на нумерованные юниты; выход — `{"splits": [...], "topic": "..."}`
  (1-индексные границы), чанки собираются на хосте по этим индексам.
- Почему это ценно: генеративные чанкеры «улучшают» текст (ё → е, кавычки,
  пробелы), из-за чего чанки перестают совпадать с документом байт-в-байт и
  ломаются цитаты/оффсеты. Здесь текст не переписывается, таблицы режутся
  целиком (при корректном апстрим-парсере).
- Размеры: bf16 22 ГБ (4 шарда) или **GGUF Q5_K_M 5.85 ГБ** (отдельный репозиторий
  `…-GGUF`, файл `…-v2-Q5_K_M.gguf`). Сервинг: `llama-server -m <gguf> -ngl 99 -c 8192`.
- Честные цифры (эталон 140 out-of-domain юр. документов, разметка консенсусом
  двух моделей с арбитражем — не teacher-agreement): boundary-F1@0 **0.415**,
  @±1 **0.609**; JSON 100%. По жанрам @±1: судебные решения 0.867, **НПА 0.465**.
- Вывод по применимости: **наш жанр — слабый у модели** (ГОСТы, положения Банка
  России — это НПА). Плюс у нас уже есть детерминированные структурные сигналы
  (`standard_number`/`clause`/`section`, сегменты с типом «таблица»/«страница»),
  на которых для НПА можно сделать чанкинг по пунктам без модели. Пилот нужен, но
  ожидания — «может быть лучше», а не «точно лучше».

### qmd-query-expansion-ru — расширение запроса, а не BM25

- Qwen3-1.7B LoRA (Apache-2.0), GGUF q4_k_m 1.1 ГБ. Контракт: `hyde:` / `lex:` /
  `vec:` — три лексических и две векторные переформулировки.
- Обучалась как drop-in замена английской модели в qmd, ровно из-за того, что
  **BM25 со стеммером Портера не понимает русскую морфологию** — расширения
  должны сами покрывать словоформы («получить получение вернуть возврат»).
- Это прямо отвечает на «возможно BM25 надо будет поменять»: два пути —
  (а) научить нашу sparse-ветку морфологии, (б) оставить её как есть и подавать
  в неё расширенный запрос. Переиндексация для (б) не нужна вообще.

### strizh-ru-retriever — запасной вариант плотного поиска

- 24.4M параметров (layer-pruned RuModernBERT-small), 384 измерения, без
  префиксов, до 8192 токенов, Apache-2.0, ~53 МБ. Сами авторы позиционируют как
  «специалиста, а не лидера качества» и как быстрый first-stage retriever для
  self-hosted RAG (например, когда GPU делится с LLM и реранкером).
- Для нас это вариант on-prem эмбеддингов вместо облачного GigaChat, но смена
  модели = другая размерность = полная переиндексация и правка фильтров
  Qdrant, и без замера на нашем наборе вопросов менять эмбеддер нельзя
  (в плане retrieval это уже отвергалось — см. слот плана).

## 3. Разбор «гибридной нарезки» (три стратегии) против нашей архитектуры

Источник разбора — совет сторонней модели о том, как подружить семантический
сплиттер с фиксированными лимитами Qdrant/Neo4j. Проверено по нашему коду.

### Что у нас уже сделано так же

- **Стратегия 3 (склеивание до лимита) — это и есть наш чанкинг.**
  `src/indexing/chunking.py`: буфер склеивает ЦЕЛЫЕ сегменты парсера
  (абзац/таблица/страница) до `chunk_size`, границы сегментов не рвутся;
  сегмент-гигант режется `RecursiveCharacterTextSplitter`. То есть «семантическая
  единица, обёрнутая в жёсткий лимит», у нас работает с самого начала — просто
  единица берётся из парсера, а не из модели.
- **Связка граф↔вектор уже есть** — то, ради чего в Стратегии 2 предлагается
  двойное хранение: узел `Chunk` в Neo4j хранит ПОЛНЫЙ текст чанка и
  `qdrant_point_id`. Из результата векторного поиска мы уже можем мгновенно
  получить «родителя» (и его текст), а не искать повторно.
- Метаданные чанка (`pages`, `segment_types`, `chunk_seq`) позволяют собирать
  соседние фрагменты без всякой модели.

### Чего нет (и что это даёт)

Двухуровневой вложенности 1:N (мелкие «дети» в Qdrant + крупные «родители» в
Neo4j) у нас нет — сейчас связь 1:1. Но выгоду от неё можно получить дешевле:
собирать контекст для LLM не одним чанком, а чанком плюс ±1 соседом по
`chunk_seq` (и/или по страницам). Это эксперимент на день: без переиндексации,
без модели, без второго уровня хранения.

### Что говорит за осторожность со сплиттером

- собственный эталон модели: boundary-F1@±1 **0.465 на НПА** против 0.867 на
  судебных решениях, а наш корпус — НПА (ГОСТы, положения Банка России);
- модель 8B (GGUF 5.85 ГБ) требует локального инференса (llama.cpp/Ollama) и
  входит в офлайн-бандл поставки;
- любая правка чанкинга = полная переиндексация с пересчётом графа;
- главное: у нас нет ни одного замеренного провала, причиной которого были бы
  именно границы чанков. Слабый кейс («текущая ситуация») — про ранжирование
  (4-е место), а не про разорванный фрагмент.

### Порядок работ, дёшево → дорого

1. **Расширение контекста соседями** (без переиндексации и модели): отдавать в
   LLM чанк + ±1 соседа по `chunk_seq`. Код к этому готов: полный текст есть в
   графе, `chunk_seq` — в payload.
2. **Чанкинг по пунктам для НПА** на существующих структурных полях
   (`clause`/`section`): детерминированно, без модели; для ГОСТов и положений
   пункт — естественная смысловая единица.
3. **A/B по размеру чанка** (например 700/105 против текущих 1500/225) на
   имеющихся 7 вопросах: грубый, но быстрый тест тезиса «эмбеддинги лучше
   работают на коротких отрезках». Стоимость — полная переиндексация (~30 мин).
4. И только потом — **сплиттер как подсказчик границ** (Стратегия 1): на
   подмножестве, с замером, а не как замена чанкинга.
5. **Parent-child (Стратегия 2)** — если выяснится, что узкое место в сборке
   контекста, а не в ранжировании.



### Исходный порядок работ (до этого разбора, для истории)

1. Набор вопросов 20-30 — остаётся опцией, не задачей (см. раздел 0).
2. Query expansion на стороне запроса — не делали: лексическая ветка починена
   стеммингом, стоп-словами и IDF; расширение запроса остаётся вариантом на случай
   реальных промахов.
3. Стемминг + стоп-слова + IDF в sparse — СДЕЛАНО 2026-09-12 (раздел 0).
4. Сплиттер (пилот на подмножестве) — в очереди, см. раздел 3.
5. Чанкинг по пунктам для НПА — в очереди, см. раздел 3 (шаг 2).


## 4. Ограничения и риски

- Air-gapped поставка: веса (5.85 ГБ сплиттер, 1.1 ГБ expansion) должны попасть
  в офлайн-бандл образов/весов — это плюс к размеру поставки.
- Сплиттер на нашем жанре слабее, чем на судебных решениях (0.465 против 0.867
  по @±1) — пилот обязателен, «по статье» принимать нельзя.
- Query expansion добавляет LLM-вызов на каждый запрос (латентность + 429 при
  параллельной индексации — этот класс проблем уже ловили 2026-09-12).
- Любая правка чанкинга = полная переиндексация корпуса (~1400 чанков на 17
  документах занимает ~30 минут, замерено).
