> Составлен 2026-09-12. Статус: **не делаем сейчас**, это заготовка на будущее.
> Предпосылка: гибридный поиск (dense + sparse BM25 + RRF) нужен, но текущая
> BM25-ветка проигрывает плотному поиску и выключена в конфиге.

## 0. Обновление 2026-09-12 (вечер): лексическая ветка починена и включена адресно

Сделано:

- `src/indexing/lexical.py` — нормализация ё→е, ~180 стоп-слов, суффиксный стеммер
  с усечением длинных основ («получение»/«получить» → «получ»); числа и номера
  стандартов не стеммируются;
- IDF включён на коллекции: Qdrant 1.12 принимает `modifier: idf` у sparse-вектора
  на существующей коллекции (`PATCH /collections/kag_documents`), пересоздание не нужно;
- `scripts/reindex_sparse.py` — пересчёт sparse-векторов локально (2049 точек за 1.7 с),
  без эмбеддингов и LLM, через `update_vectors` по id точки;
- гибрид включается адресно: режим `hybrid_auto` в админке («🔍 Настройки поиска»),
  гибрид применяется только к запросам с точными терминами (ГОСТ/ISO/СТО, приказ/
  положение/указание, №, номера 7403-У и 5.2.1, длинные числа, кавычки);
- замеры на 7 вопросах (один индекс): dense hit@1 0.714 / MRR 0.821;
  sparse-only 0.571 / 0.669; hybrid RRF 0.714 / 0.774; hybrid DBSF 0.714 / 0.767;
  hybrid_auto 0.714 / 0.821 — то есть адресное включение не ухудшает ничего,
  а лексическая ветка работает там, где она уместна.

Осталось (и почему):

- набор вопросов 20-30+ — нужен для ЛЮБОЙ тонкой настройки (веса фьюжна, пороги,
  длина стема); сейчас 7 вопросов = 14 п.п. на один вопрос;
- проверить лексическую ветку на запросах, где она обязана выигрывать (поиск по
  номерам документов, аббревиатурам, редким терминам) — на текущих семантических
  вопросах выигрыша нет, поэтому вывод «BM25 полезен» пока не подтверждён;
- сплиттер и чанкинг по пунктам — пилот, см. разделы ниже.

## 1. Где мы сейчас

- Чанкинг: сегментный (абзац/таблица/страница накапливаются до `chunk_size`),
  сегменты-гиганты режет `RecursiveCharacterTextSplitter`.
  Действующие значения — **1500 символов, overlap 225** (`src/config.py`,
  `CHUNK_SIZE`/`CHUNK_OVERLAP`; в `config_store` ключа `chunking` нет — он
  пропал вместе с томом postgres 2026-09-12, поэтому работают дефолты кода).
- Sparse-ветка: `embeddings_service._tokenize_sparse` — CRC32 от токенов без
  стемминга, IDF, стоп-слов и нормировки длины; Qdrant-фьюжн RRF без весов.
- Замер на 7 вопросах (один индекс): dense MRR 0.821 против hybrid 0.802,
  слабый кейс «текущая ситуация в российской экономике» — 4-е место на dense
  против 9-го на hybrid. Поэтому `search:config.sparse_enabled = false`.
- Важное: sparse-векторы в Qdrant **уже построены** для всех документов, так что
  включение ветки обратно — это флаг в конфиге, без переиндексации.

## 2. Что рассмотрели (артефакты AGmind, Apache-2.0, 2026-09-12)

### agmind-rag-splitter-ru (v2) — режет документ по индексам, текст не переписывает

- LoRA-дообучение `t-tech/T-lite-it-2.1` (Qwen3-8B). Вход — текст, заранее
  разбитый на нумерованные юниты; выход — `{"splits": [...], "topic": "..."}`
  (1-индексные границы), чанки собираются на хосте по этим индексам.
- Почему это ценно: генеративные чанкеры «улучшают» текст (ё → е, кавычки,
  пробелы), из-за чего чанки перестают совпадать с документом байт-в-байт и
  ломаются цитаты/оффсеты. Здесь текст не переписывается, таблицы режутся
  целиком (при корректном апстрим-парсере).
- Размеры: bf16 22 ГБ (4 шарда) или **GGUF Q5_K_M 5.85 ГБ** (отдельный репозиторий
  `…-GGUF`, файл `…-v2-Q5_K_M.gguf`). Сервинг: `llama-server -m <gguf> -ngl 99 -c 8192`.
- Честные цифры (эталон 140 out-of-domain юр. документов, разметка консенсусом
  двух моделей с арбитражем — не teacher-agreement): boundary-F1@0 **0.415**,
  @±1 **0.609**; JSON 100%. По жанрам @±1: судебные решения 0.867, **НПА 0.465**.
- Вывод по применимости: **наш жанр — слабый у модели** (ГОСТы, положения Банка
  России — это НПА). Плюс у нас уже есть детерминированные структурные сигналы
  (`standard_number`/`clause`/`section`, сегменты с типом «таблица»/«страница»),
  на которых для НПА можно сделать чанкинг по пунктам без модели. Пилот нужен, но
  ожидания — «может быть лучше», а не «точно лучше».

### qmd-query-expansion-ru — расширение запроса, а не BM25

- Qwen3-1.7B LoRA (Apache-2.0), GGUF q4_k_m 1.1 ГБ. Контракт: `hyde:` / `lex:` /
  `vec:` — три лексических и две векторные переформулировки.
- Обучалась как drop-in замена английской модели в qmd, ровно из-за того, что
  **BM25 со стеммером Портера не понимает русскую морфологию** — расширения
  должны сами покрывать словоформы («получить получение вернуть возврат»).
- Это прямо отвечает на «возможно BM25 надо будет поменять»: два пути —
  (а) научить нашу sparse-ветку морфологии, (б) оставить её как есть и подавать
  в неё расширенный запрос. Переиндексация для (б) не нужна вообще.

### strizh-ru-retriever — запасной вариант плотного поиска

- 24.4M параметров (layer-pruned RuModernBERT-small), 384 измерения, без
  префиксов, до 8192 токенов, Apache-2.0, ~53 МБ. Сами авторы позиционируют как
  «специалиста, а не лидера качества» и как быстрый first-stage retriever для
  self-hosted RAG (например, когда GPU делится с LLM и реранкером).
- Для нас это вариант on-prem эмбеддингов вместо облачного GigaChat, но смена
  модели = другая размерность = полная переиндексация и правка фильтров
  Qdrant, и без замера на нашем наборе вопросов менять эмбеддер нельзя
  (в плане retrieval это уже отвергалось — см. слот плана).

## 3. Порядок работ, когда вернёмся к теме

1. **Расширить набор вопросов до 20-30 с разметкой** (`scripts/eval_questions.json`,
   сейчас 7 вопросов — один вопрос двигает hit@1 на 14 п.п., тюнить на таком нельзя).
   Без этого шага всё дальнейшее — гадание.
2. **Дешёвый вариант без переиндексации**: query expansion на стороне запроса
   (`lex:` → sparse-вектор запроса, `vec:`/`hyde` → при желании dense). Замер
   hybrid vs dense на новом наборе.
3. **Если морфология всё ещё мешает**: стемминг/лемматизация + стоп-слова в
   `_tokenize_sparse`. IDF — либо `modifier: idf` у sparse-вектора коллекции
   (проверить, можно ли задать на существующей коллекции Qdrant; если только при
   создании — либо пересоздание коллекции с переносом точек, либо IDF считаем сами
   по корпусу), либо собственный проход по статистике коллекции.
   Переиндексация — только sparse: вектора обновляются через
   `update_vectors` по `qdrant_point_id`, без обращения к модели эмбеддингов.
4. **Сплиттер — пилот на подмножестве** (10-20 документов): разбить сегменты на
   нумерованные юниты, получить границы, собрать чанки, прогнать eval и сравнить
   с текущим чанкингом. Инференс — GGUF через llama.cpp/Ollama на LLM-хосте
   (5.85 ГБ на CPU сервера 18 будет медленно); для документов длиннее контекста
   окно юнитов и склейка границ на хосте.
5. **Альтернатива сплиттеру для НПА**: чанкинг по пунктам (clause-level) на
   структурных полях — сравнить с моделью на том же наборе.

## 4. Ограничения и риски

- Air-gapped поставка: веса (5.85 ГБ сплиттер, 1.1 ГБ expansion) должны попасть
  в офлайн-бандл образов/весов — это плюс к размеру поставки.
- Сплиттер на нашем жанре слабее, чем на судебных решениях (0.465 против 0.867
  по @±1) — пилот обязателен, «по статье» принимать нельзя.
- Query expansion добавляет LLM-вызов на каждый запрос (латентность + 429 при
  параллельной индексации — этот класс проблем уже ловили 2026-09-12).
- Любая правка чанкинга = полная переиндексация корпуса (~1400 чанков на 17
  документах занимает ~30 минут, замерено).
