# Словарь связей: соответствие опубликованным стандартам

Документ отвечает на вопрос «почему у нас такие типы связей». Ответ: **мы не выдумываем там, где
есть стандарт**. Типы взяты из трёх опубликованных словарей, а свои заведены только там, где стандарт
молчит. Это не косметика: на продаже можно предъявить источник каждого типа, а выгрузки совместимы
с отраслевыми форматами.

## Откуда взяты типы

| Стандарт | Кто издал | Что берём |
|---|---|---|
| **STIX 2.1** | OASIS (безопасность) | `part-of`, `member-of`, `located-at`, `attributed-to`, `authored-by`, `derived-from`, `targets`, `indicates`, `mitigates` |
| **ELI** (European Legislation Identifier) | ЕС (правовые документы) | `amends`, `repeals`, `corrects`, `consolidates` |
| **Dublin Core Terms** | DCMI (документы) | `references`, `has-part`, `is-version-of`, `replaces`, `requires` |
| **своё** | — | `signed-by`, `issued-by`, `dated`, `has-amount`, `defines`, `applies-to`, `establishes-requirement`, `related-to` |

Особенность STIX, из-за которой он нам подходит: в нём типы связей заданы **таблицей допустимых
пар** «тип объекта → тип объекта» — ровно та проверка, которую мы делаем своим словарём. У STIX
перечень открытый: свои названия разрешены, но базовые отношения уже описаны и не требуют
изобретения.

## Соответствие: наш прежний код → канонический

| Прежний код | Канонический | Стандарт |
|---|---|---|
| RELATED_TO | `related-to` | STIX |
| BELONGS_TO | `part-of` (часть целого) или `member-of` (членство) | STIX |
| PART_OF | `part-of` | STIX |
| LOCATED_AT | `located-at` | STIX |
| SIGNED_BY | `signed-by` | своё |
| ISSUED_BY | `issued-by` | своё |
| DATED | `dated` | своё |
| AMOUNT | `has-amount` | своё |
| REFERENCES | `references` | Dublin Core |
| HAS_CLAUSE | `has-part` | Dublin Core |
| SUPERSEDES | `replaces` / `repeals` | Dublin Core / ELI |
| AMENDS | `amends` | ELI |
| REQUIRES | `establishes-requirement` | своё (в Dublin Core `requires` — про другой смысл) |
| APPLIES_TO | `applies-to` | своё |
| DEFINES | `defines` | своё |

Прежние коды **принимаются и читаются**: они перечислены в `graph_ontology.MIGRATION` и в списке
допустимых, поэтому связи, записанные до перехода, видны и не подменяются. При пересборке те же
факты записываются уже каноническими кодами.

## Что это даёт, кроме порядка

1. **Защита на продаже.** На вопрос «почему тип связи называется так» есть ответ: это `part-of` из
   STIX 2.1, а не наша выдумка.
2. **Разделение слипшихся смыслов.** Раньше «принадлежит» было одним типом, из-за чего его
   запретили целиком (модель сваливала туда и «пункт в таблице», и «организация в объединении»).
   Теперь это два разных стандартных типа: `part-of` и `member-of`.
3. **Совместимость.** Появляется путь выгрузки в STIX (безопасность) и ELI-разметку (правовые
   документы) без переписывания модели данных.

## Где это в коде

* `src/indexing/graph_ontology.py` — сам словарь (`RELATIONS`), перевод прежних кодов (`MIGRATION`),
  синонимы, версия онтологии (`ONTOLOGY_EPOCH`), задание для модели (`prompt_rules`).
* `src/indexing/entity_extractor.py` — проверка троек перед записью; прежний запрет `BELONGS_TO`
  снят: тип сводится к стандартному, а допустимость пары проверяет словарь.
* `src/indexing/knowledge_graph.py` — запись связей (единый путь для модели и правил).
* `src/api/static/kg.html` — русские подписи типов для интерфейса.

## Порядок изменения словаря (обязательный)

1. Правка `RELATIONS`/`MIGRATION` в `graph_ontology.py`.
2. **Поднять `ONTOLOGY_EPOCH`**: от него зависит ключ кэша извлечения. Без подъёма модель вернёт
   прежние ответы, и правка молча не подействует (так уже было 10.10.2026).
3. Проверка на выборке 3–5 документов, а не полная пересборка: словарь меняется часто, а прогон
   всего корпуса стоит денег и часов.

## Российские стандарты (обязательный раздел: большинство заказчиков в РФ)

Международные словари (STIX, ELI, Dublin Core) хороши, но в России их упоминание не заменяет
отечественных стандартов. Ниже — прямые аналоги, найденные и проверенные 11.10.2026 по текстам
стандартов. Это то, что предъявляется заказчику в первую очередь.

### ГОСТ 7.25-2001 — тезаурус информационно-поисковый одноязычный

Прямой аналог SKOS и вообще наш главный ориентир по типам отношений. Стандарт задаёт **перечень
видов связей между дескрипторами** (п. 4.5.6.2):

| Связь по ГОСТ 7.25-2001 | Наш тип связи |
|---|---|
| род — вид | `broader-term` |
| часть — целое | `component-of`, `has-part` |
| административная иерархия | `subordinate-to` |
| причина — следствие | `indicates` (частично) |
| процесс — объект, процесс — субъект, свойство — носитель свойства | `targets`, `mitigates`, `applies-to` |
| антонимия, функциональное сходство, сырьё — продукт | (у нас нет; при необходимости — `related-to`) |

Стандарт делит отношения на два класса: **иерархические** (транзитивные и антисимметричные — род-вид,
часть-целое, административная иерархия) и **ассоциативные** (все прочие). Это ровно то разделение,
из-за которого мы разводили `part-of`: смешение транзитивных и нетранзитивных отношений ломает выводы.

Важно для внедрения: стандарт требует **взаимных ссылок** (прямая и обратная связь в словарных статьях).
У нас обратные связи выводятся обходом графа, а не хранятся — это допустимо технически, но при передаче
заказчику стоит объяснить: обратный переход в графе есть, отдельной записью он не занимает место.

### ГОСТ Р 7.0.97-2016 — реквизиты организационно-распорядительных документов

Задаёт **состав реквизитов документа** (30 позиций). Это наши свойства документа, и они совпадают почти
дословно:

| Реквизит по ГОСТ | Наше поле или связь |
|---|---|
| 05 — наименование организации — автора документа | `authored-by` |
| 09 — наименование вида документа | вид документа (словарь видов v0) |
| 10 — дата документа | `dated` |
| 11 — регистрационный номер документа | свойство «номер» |
| 12 — ссылка на регистрационный номер и дату поступившего документа | `references` |
| 13 — место составления (издания) документа | `located-at` |
| 16 — гриф утверждения документа | `adopted-by` |
| 19 — отметка о приложении | `in-collection` |
| 22 — подпись; 23 — отметка об электронной подписи | `signed-by` |
| 20 — гриф согласования; 21 — виза | (у нас нет — при необходимости отдельный тип) |

Тот же стандарт перечисляет **виды документов**: уставы, положения, правила, инструкции, регламенты,
постановления, распоряжения, приказы, решения, протоколы, договоры, акты, письма, справки — это и есть
наша основа для словаря видов. Дополнительно указывается связь с **ОКУД (ОК 011-93,
Общероссийский классификатор управленческой документации, класс 0200000)** — официальный классификатор
видов управленческих документов, на который можно ссылаться в поставке.

### ГОСТ Р 7.0.8-2013 — делопроизводство и архивное дело: термины и определения

Задаёт терминологию: документ, реквизит, вид документа, подлинник, копия, заверение копии и др.
Нужен, чтобы наши типы сущностей и подписи в интерфейсе назывались теми же словами, что в стандарте:
на разборе у заказчика это первое, за что цепляются.

### Как это использовать в поставке

1. В описании продукта писать не «мы придумали типы связей», а: **типы связей соответствуют
   ГОСТ 7.25-2001 (род-вид, часть-целое, административная иерархия), реквизиты документов — 
   ГОСТ Р 7.0.97-2016, терминология — ГОСТ Р 7.0.8-2013**, а для домена безопасности дополнительно
   STIX 2.1.
2. Словарь видов документов строить на перечне ГОСТ Р 7.0.97-2016 и привязывать к ОКУД.
3. При разборе качества ссылаться на классы отношений из ГОСТ 7.25-2001: если связь нетранзитивна,
   она не должна быть в иерархическом классе — это и есть проверка, которую мы делаем словарём.
