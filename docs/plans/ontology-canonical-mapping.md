# Словарь связей: соответствие опубликованным стандартам

Документ отвечает на вопрос «почему у нас такие типы связей». Ответ: **мы не выдумываем там, где
есть стандарт**. Типы взяты из трёх опубликованных словарей, а свои заведены только там, где стандарт
молчит. Это не косметика: на продаже можно предъявить источник каждого типа, а выгрузки совместимы
с отраслевыми форматами.

## Откуда взяты типы

| Стандарт | Кто издал | Что берём |
|---|---|---|
| **STIX 2.1** | OASIS (безопасность) | `part-of`, `member-of`, `located-at`, `attributed-to`, `authored-by`, `derived-from`, `targets`, `indicates`, `mitigates` |
| **ELI** (European Legislation Identifier) | ЕС (правовые документы) | `amends`, `repeals`, `corrects`, `consolidates` |
| **Dublin Core Terms** | DCMI (документы) | `references`, `has-part`, `is-version-of`, `replaces`, `requires` |
| **своё** | — | `signed-by`, `issued-by`, `dated`, `has-amount`, `defines`, `applies-to`, `establishes-requirement`, `related-to` |

Особенность STIX, из-за которой он нам подходит: в нём типы связей заданы **таблицей допустимых
пар** «тип объекта → тип объекта» — ровно та проверка, которую мы делаем своим словарём. У STIX
перечень открытый: свои названия разрешены, но базовые отношения уже описаны и не требуют
изобретения.

## Соответствие: наш прежний код → канонический

| Прежний код | Канонический | Стандарт |
|---|---|---|
| RELATED_TO | `related-to` | STIX |
| BELONGS_TO | `part-of` (часть целого) или `member-of` (членство) | STIX |
| PART_OF | `part-of` | STIX |
| LOCATED_AT | `located-at` | STIX |
| SIGNED_BY | `signed-by` | своё |
| ISSUED_BY | `issued-by` | своё |
| DATED | `dated` | своё |
| AMOUNT | `has-amount` | своё |
| REFERENCES | `references` | Dublin Core |
| HAS_CLAUSE | `has-part` | Dublin Core |
| SUPERSEDES | `replaces` / `repeals` | Dublin Core / ELI |
| AMENDS | `amends` | ELI |
| REQUIRES | `establishes-requirement` | своё (в Dublin Core `requires` — про другой смысл) |
| APPLIES_TO | `applies-to` | своё |
| DEFINES | `defines` | своё |

Прежние коды **принимаются и читаются**: они перечислены в `graph_ontology.MIGRATION` и в списке
допустимых, поэтому связи, записанные до перехода, видны и не подменяются. При пересборке те же
факты записываются уже каноническими кодами.

## Что это даёт, кроме порядка

1. **Защита на продаже.** На вопрос «почему тип связи называется так» есть ответ: это `part-of` из
   STIX 2.1, а не наша выдумка.
2. **Разделение слипшихся смыслов.** Раньше «принадлежит» было одним типом, из-за чего его
   запретили целиком (модель сваливала туда и «пункт в таблице», и «организация в объединении»).
   Теперь это два разных стандартных типа: `part-of` и `member-of`.
3. **Совместимость.** Появляется путь выгрузки в STIX (безопасность) и ELI-разметку (правовые
   документы) без переписывания модели данных.

## Где это в коде

* `src/indexing/graph_ontology.py` — сам словарь (`RELATIONS`), перевод прежних кодов (`MIGRATION`),
  синонимы, версия онтологии (`ONTOLOGY_EPOCH`), задание для модели (`prompt_rules`).
* `src/indexing/entity_extractor.py` — проверка троек перед записью; прежний запрет `BELONGS_TO`
  снят: тип сводится к стандартному, а допустимость пары проверяет словарь.
* `src/indexing/knowledge_graph.py` — запись связей (единый путь для модели и правил).
* `src/api/static/kg.html` — русские подписи типов для интерфейса.

## Порядок изменения словаря (обязательный)

1. Правка `RELATIONS`/`MIGRATION` в `graph_ontology.py`.
2. **Поднять `ONTOLOGY_EPOCH`**: от него зависит ключ кэша извлечения. Без подъёма модель вернёт
   прежние ответы, и правка молча не подействует (так уже было 10.10.2026).
3. Проверка на выборке 3–5 документов, а не полная пересборка: словарь меняется часто, а прогон
   всего корпуса стоит денег и часов.
