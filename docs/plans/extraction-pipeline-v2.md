# Новая схема извлечения графа (v2) — по образцу щупа, параллельно существующей

Основание: замеры 11.10.2026. Щуп (`scripts/bakeoff/probe_chunks.py`) на чистом документе даёт
81 процент подтверждённых цитат, а конвейер на том же документе — 0. Разница не в модели и не в
провайдере (оба используют deepseek-v4-flash, температура 0.05, размышления отключены), а в том,
ЧТО и КАК отправляется. Новая схема переносит в продукт ровно то, что доказано щупом.

## Что делает щуп (и что переносим)

1. Системная часть — минимальная и язык-нейтральная (в щупе её нет вовсе; в продукте — одна строка).
2. В запросе ПОЛЬЗОВАТЕЛЯ лежит: список типов связей, сам фрагмент ЦЕЛИКОМ, ОБРАЗЕЦ ответа с полем
   подтверждения и правила. Образец — обязателен: доказано, что без него модель не отдаёт цитату,
   а строгая формулировка «нет цитаты — не выводить» даёт пустой ответ.
3. Правила мягкие: «выведи все связи, для каждой дай дословную цитату; не подобрать — null,
   но связь выведи». Запрет вывода парализует модель.
4. Разбор ответа терпимый: снимает markdown-обёртку, берёт от первой фигурной скобки до последней.
5. Проверка цитаты — по нормализованному тексту (только буквы и цифры), применяется и к свежему
   извлечению, и к ответу из кэша.
6. Цитата СОХРАНЯЕТСЯ на связи в графе (поле evidence) — доказательство рядом с фактом.

## Чего в конвейере НЕ делать (найденные дефекты)

- Не подставлять в запрос урезанный фрагмент: медиана фрагмента 1572 знака, максимум 1725, а в
  запрос уходили первые 1000 — модель не видела треть текста, проверка её не подтверждала.
- Не подставлять типы связей из доменной схемы документа, если она пуста: модель без списка типов
  отвечает пустым списком связей. Брать полный словарь онтологии (prompt_rules).
- Не терять поле при разборе: разбор строил связь заново из source/target/type и выбрасывал цитату.
- Не делать отпечаток кэша из частей запроса: правки шаблонов при неизменном отпечатке возвращали
  старые ответы (три прогона подряд давали одни и те же числа).

## Как встроить ПАРАЛЛЕЛЬНО (ничего не ломая)

Настройка `system/graph_quality.extraction_scheme`: `current` (как сейчас) | `v2` (новая схема).
Новая схема — отдельный модуль `src/indexing/extraction_v2.py` с одной точкой входа:
`extract_chunk_v2(chunk_text, chunk_id, cfg) -> {"entities": [...], "relations": [...]}`
(связи — с полем evidence). Выбор схемы — в одном месте, где сейчас вызывается `extract_from_chunk`.
Старая схема остаётся рабочей и переключается обратно той же настройкой.

## Порядок работы

1. Модуль v2 + переключатель; по умолчанию остаётся `current`.
2. Замер на фиксированных фрагментах ГОСТ 57580 (щуп и v2 должны совпасть по доле подтверждённых).
3. Проверка на целом ГОСТ 57580 со строгим режимом: доля подтверждённых около 80 процентов,
   цитата видна в графе.
4. Пятёрка документов — по решению владельца.
5. Переключение по умолчанию на v2 и пересборка корпуса.

## Метрики приёмки

- Доля связей с цитатой, найденной в тексте фрагмента: не ниже 75 процентов (щуп даёт 81).
- Ноль неразобранных ответов.
- У каждой записанной связи в графе есть непустое поле evidence.
- Число связей с точным типом не падает относительно текущей схемы.

## Замер 11.10.2026 (чем закончилось; прибор `scripts/bakeoff/audit_v2.py`)

Список типов в задании — КОМПАКТНЫЙ, а не обрезок правил. `relations_compact()` в
`graph_ontology.py`: 31 тип по строке, 1214 знаков; смыслы — словарь `SHORT_MEANING` (одна точка
правды рядом с онтологией, полноту стережёт `tests/test_graph_prompt.py`). Прежняя обрезка
`prompt_rules()[:3000]` рубила список ПОСРЕДИНЕ описания типа — до модели не доходили 17 типов из
31 (subordinate-to, classified-as, adopted-by, has-part, is-version-of, replaces, signed-by,
issued-by, effective-from, dated, has-amount, defines, applies-to, establishes-requirement и др.).

| уровень | фрагментов | связей | цитата найдена в тексте | время | токены (запрос/вывод) |
| :-- | --: | --: | --: | --: | --: |
| чанк | 1 | 7 | 100 % | 2,0 с | 878 / 437 |
| набор | 10 | 78 | 96 % | 2,3 с на фрагмент | 10 879 / 4 101 (37 % из кэша) |
| документ ГОСТ 57580 | 180 | 1418 | 94 % | 2,1 с на фрагмент | 198 819 / 75 285 |

Неразобранных ответов — 0 на всех 191 фрагменте. Распределение связей по фрагментам документа:
0 связей — 1 фрагмент, 1-3 — 12, 4-7 — 65, 8-12 — 97, 13+ — 5 (медиана 8, максимум 20). То есть
длина фрагмента выхода не определяет: фрагмент на 1718 знаков дал 0 связей.

### ЗАКРЫТО: пачка фрагментов в одном запросе (не берём)

Замер `scripts/bakeoff/audit_batch.py` на тех же 10 фрагментах, режим против режима:

| режим | связей | подтверждено | время | токены запрос / вывод |
| :-- | --: | --: | --: | --: |
| по одному | 70 | 94 % | 19,6 с | 10 879 / 3 609 |
| пачкой по 4 | 61 | 96 % | 16,8 с | 6 308 / 5 074 |

Выигрыш времени — 14 % (время определяется длиной ответа, а не числом вызовов), входные токены
−42 %, но связей −13 % (потеря полноты), вывод +40 %. Батч в конвейер НЕ берём: скорость почти не
растёт, а связи теряются. Это совпадает с прежним сравнением режимов (`compare_batch_modes.py`).

### Правка правила пар `references` (ONTOLOGY_EPOCH 8 → 9)

Замер документа показал: ВСЕ 59 отказов схемы «пара тип-связь-тип» были ссылками из ПУНКТА —
46 «пункт → пункт», 13 «пункт → стандарт». Это нормальные связи живого текста ГОСТ («в
соответствии с мерами КЗИ.1 — КЗИ.7 настоящей таблицы», «приведен в таблице 51»), то есть правило
браковало не дефект графа, а дыру в схеме. Разрешены пары clause → clause / standard / document_ref.
Пересчёт по сохранённым связям (`scripts/bakeoff/recheck_pairs.py`, без новых вызовов модели):
проходят схему 113 (было 54), нарушают 0 (было 59).

### ОСТАЛОСЬ перед подключением v2 в конвейер

1. ТИПЫ СУЩНОСТЕЙ (главное). v2 отдаёт только связи, а `validate_triple` и запись в Neo4j требуют
   типов обоих концов: 1305 из 1418 связей (92 %) не проверяемы по этой причине — типы концов
   определяются лишь правилами формы (ГОСТ → standard, «п. 5.2.1» → clause, дата → date), а
   организации, люди, термины так не разметить. Варианты: вернуть пары «имя → тип» тем же вызовом
   (десятки токенов) или брать тип у существующего узла графа.
2. Ускорение по фактам замеров: кэш извлечения на своей стороне (в одиночном режиме 81 % входных
   токенов пришло из кэша провайдера на повторе), параллельные вызовы (время делится на число
   потоков), пропуск служебных и коротких фрагментов (14 коротких дали 4 % связей).

### Как мерить без выката

`scripts/bakeoff/run_audit_v2.sh` (уровни chunk / set / doc): правленый код кладётся в КОПИЮ src
внутри контейнера (`/tmp/v2src`, запуск с `PYTHONPATH` на неё), рабочие контейнеры не трогаются,
отчёт с СЫРЫМИ ответами модели забирается файлом. Прибор вызывает ровно `extract_chunk_v2` — не
свою копию промпта; на расхождении копии и конвейера прошлый заход потерял день («щуп 81 %,
конвейер 0 %»).

## Типы сущностей в v2 (сделано 11.10.2026)

v2 теперь просит типы сущностей ТЕМ ЖЕ вызовом: в ответе два поля — `entities` (имя → тип) и
`relations` (source/target/type/evidence). Второго прохода нет; список типов сущностей берётся
из `entity_types_compact()` (одна точка правды рядом с онтологией).

Тип из СТРОГОЙ ФОРМЫ записи перебивает ответ модели: «ГОСТ Р 57580.1—2017» → standard, «п. 5.2.1»
→ clause, «15.06.2026» → date. Выдуманный моделью тип не берётся вовсе.

Замер набора (10 фрагментов) до и после:

| что | без типов | с типами |
| :-- | --: | --: |
| связей от модели | 78 | 94 |
| цитата найдена | 96 % | 94 % |
| связей БЕЗ типа концов | 95 % (74 из 78) | 12 % (11 из 94) |
| проходят схему пар | 3 | 73 |
| нарушают схему | 1 | 10 |
| время на фрагмент | 2,3 с | 2,8 с |
| токены запрос/вывод | 10 879 / 4 101 | 13 359 / 5 946 |

### Найденный дефект правила формы (важно)

Обозначения стандартов печатают с ДЛИННЫМ тире: «ГОСТ Р 57580.1—2017» (U+2014), а правило формы
ждало дефис — 6 имён из 19 с «ГОСТ» в документе не типизировались. Исправлено в
`entity_typing.py` (любое тире + склеенное «ГОСТР»), `ENTITY_RULES_EPOCH` 2 → 3. То же для
«152—ФЗ» и реквизитов актов.

### Расширение правил пар (ONTOLOGY_EPOCH 9 → 10)

Типы концов стали видны, и обнаружилось, где узко ПРАВИЛО, а не связь: `defines` не разрешал
определять термин из пункта, `applies-to` — из пункта/требования. Разрешено. Пересчёт по данным
набора (`recheck_pairs.py`): проходят 73, нарушают 10 (было 17); осталось только то, где ошибается
модель («таблица 26 является редакцией таблицы 26»).

## Подключение v2 в конвейер (сделано 11.10.2026)

Переключатель — настройка `system/graph_quality.extraction_scheme`: `current` (по умолчанию) |
`v2`. Выбор схемы — в одном месте: `EntityExtractor._extract_chunk`, дальше путь записи общий
(фильтр самообозначений → уточнение типов правилами → канонизация алиасов → проверка пар →
запись с цитатой). v2 вызывается в отдельном потоке (это синхронный HTTP-запрос; иначе встаёт цикл
событий воркера). Сбой v2 не роняет обработку — работаем прежней схемой.

Стражи: `tests/test_extraction_v2.py` (подделанный ответ модели: разбор, типы, цитата, диагностика,
включение схемы настройкой, откат при сбое) и `tests/test_graph_prompt.py`, `tests/test_entity_typing.py`.

ОСТАЛОСЬ: кэш извлечения для v2 (у прежней схемы он есть; здесь повторные прогоны пока полные),
замер на целом документе с включённой схемой, выкат образов api И worker (worker-maintenance тоже).
