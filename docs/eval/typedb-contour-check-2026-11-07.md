# Проверка связки Qdrant + TypeDB в чате, 07.11.2026

Задача: Neo4j выведен из флоу, второй контур ответа — TypeDB. Проверялось не наполнение
по отдельности, а именно связка: гибридный поиск Qdrant даёт фрагменты → TypeDB отдаёт
верифицированные факты по этим фрагментам → оркестратор собирает контекст → модель отвечает.

Стенд 192.168.50.18, база `cybersecurity_ontology_v2`, код из `/home/yartsevn/kag-live/src`
(коммит `67508ce`).

## 1. Neo4j выключен в контуре ответа

**Было:** шаг 2b в `chat_service.generate_response` вызывал `kg_service.hybrid_search()` при
КАЖДОМ запросе чата и добавлял в контекст секцию «--- ГРАФ ЗНАНИЙ (Neo4j) ---». Флага отключения
не было: `system/graph.skip=true` выключал только построение, но не чтение. Проверка: лог
`[rag] граф: 0 связей за 50 мс` на каждом вопросе.

**Стало:** чтение графа разрешено только при `system/graph.read_enabled=true`. Флага на стенде
нет → выключено. Проверка после правки: на трёх запросах чата строк `[rag] граф:` и
`Neo4j: найдено` нет ни одной.

## 2. TypeDB-контур работает как механизм

`typedb_facts.is_available()` → True, `_cfg` → `cybersecurity_ontology_v2`, вызов занимает 79–80 мс.
Факты фильтруются по видимым `chunk_id` (ADR-002).

    видимые чанки 187-ФЗ + демо-нарушение   → 1 факт
    невидимый чанк ({"чужой_chunk"})        → 0 фактов
    после удаления демо-набора              → 0 фактов

Блок для промпта:

    - 'Положение о защите информации в АСУ ТП (демо-набор)': нарушено требование
      ФСТЭК-239-п11.1 (Применение сертифицированных средств защиты информации)
      [чанк 913ba708-…_chunk_00003, demo-seed]

## 3. Факт доходит до ответа

Чтобы проверить сквозной путь, в базу был поставлен демо-набор (помечен
`source_origin="demo-seed"`, привязан к реальным чанкам документа 187-ФЗ, чтобы пройти ACL):

    company_document   «Положение о защите информации в АСУ ТП (демо-набор)»
    cii_object         АСУ ТП цеха №1, cii-category 1
    security_software  СЗИ без сертификата, is-certified false
    security_requirement  ФСТЭК-239-п11.1
    связи              document_assignment, asset_protection

Вопрос: «Что относится к объектам критической информационной инфраструктуры? Какие нарушения
требований к защите таких объектов выявлены?»

    лог: TypeDB: 1 фактов нарушений за 79 мс
    ответ (фрагмент): «По выявленным нарушениям: в материалах есть единственная запись —
    по "Положению о защите информации в АСУ ТП (демо-набор)" нарушено требование
    ФСТЭК-239-п11.1 "Применение сертифицированных средств защиты информации"»

То есть связка проходит целиком. Демо-набор после проверки удалён: `company_document` 0,
`security_software` 0, `security_requirement` 0, объектов с `source-origin=demo-seed` 0,
`violated_documents()` 0.

## 4. Почему в обычной работе фактов нет

Демо-набор понадобился потому, что правило опирается на типы, которых в базе нет:

    company_document       0
    security_software      0
    security_requirement   0
    cii_object с cii-category 1   нет (есть 4 объекта без категории)

`typedb_writer` создаёт только: regulator, regulatory_document, structural_element,
security_measure, cii_object, threat_source. Документы компании и СЗИ из нормативки не выводятся —
это данные заказчика. Плюс оба правила жёстко привязаны к `requirement-id = "ФСТЭК-239-п11.1"`,
то есть даже с данными сработают только для одного требования.

Записано в `docs/tech-debt.md`, п. 16.

## 5. Важное следствие для ACL

Факт выдаётся, только если чанк-источник факта попал в выдачу поиска. На вопросах про
ФСТЭК-239 поиск возвращал другие документы («перечень документов по КИИ 2.pdf»), и факт
отсекался — хотя он существовал. Это правильное поведение (нельзя показывать факт по
невидимому фрагменту), но означает: факты о нарушениях будут появляться в ответе только
на вопросах, которые находят сами документы компании. Для «нарушения по организации» этого
может не хватать — понадобится отдельный путь поиска по документам компании.
