# Связи между документами: что послужит триггером

Раздел заведён 11.10.2026 по вопросу владельца: **как продукт будет находить связи между документами после
продажи, что служит спусковым крючком для документного слоя, и что об этом думают в мире — или там это
игнорируют.** Нужен, чтобы к моменту передачи было чётко: какие связи мы гарантируем, какие помечаем
предположением, а какие не берём вообще.

## 1. Постановка задачи

Смысловые связи сейчас ищутся **по фрагментам** (так работает и мир: Microsoft GraphRAG извлекает по
фрагментам, LightRAG — один вызов на фрагмент). Это даёт главное свойство: у факта есть источник-фрагмент,
на который можно сослаться.

Но фрагмент не отражает документ целиком. Поэтому **документные связи** — «новая редакция», «взамен»,
«входит в состав», «приложение к», «во исполнение», «отменяет» — не находятся и не могут находиться
фрагментно. Вопрос: чем запускается их поиск?

## 2. Что делают в мире

| Система | Документный слой | Триггер |
|---|---|---|
| Microsoft GraphRAG | Нет отдельного слоя «документ→документ». После извлечения фрагментами строятся сообщества сущностей (Leiden) и по ним сводки | Загрузка корпуса (пакетно), затем агрегация |
| LightRAG | Сущностно-центричен: одинаковые сущности из разных фрагментов сливаются инкрементально | Появление нового фрагмента/документа |
| LazyGraphRAG | Индексация без модели; работа переносится на момент запроса | Запрос пользователя |
| Юридический поиск (Shepard’s, KeyCite и клоны) | **Есть и является ядром продукта**: граф цитирований между документами | Разбор ссылок при индексации + классификация типа ссылки |
| Делопроизводство (records management) | Есть, ведётся по номерам и датам; «взамен», «приложение», «во исполнение» | Регистрация документа человеком |

Вывод по вопросу «игнорируют или нет»: RAG-фреймворки — да, практически игнорируют (они сущностно-центричны).
Там, где документные связи действительно нужны и работают — юридический поиск и делопроизводство — их строят
**не «умной моделью», а разбором ссылок и сопоставлением идентификаторов, причём на входе**.

## 3. Четыре триггера (с нашей спецификой)

### 3.1 Загрузка документа — по умолчанию

Не «отдать документ модели целиком» (дорого и неточно), а узкий срез: заголовок, вид, номер, даты, раздел
ссылок. В нашем домене этого достаточно, потому что документы **сами себя связывают текстом**:
«вводится взамен ГОСТ Р 57580.1-2017», «во исполнение приказа № 123», «настоящее дополнение к …».
Это один дешёвый вызов на документ плюс правила.

### 3.2 Появление нового документа рядом с существующими — самый точный триггер

Если новый документ говорит «взамен ГОСТ Р X», а в базе есть документ с номером «ГОСТ Р X», связь ставится
**сопоставлением по идентификатору, без модели**. Это самое точное место во всей цепочке и оно дешёвое:
сопоставление по номерам — это индекс, а не перебор. Именно так устроены графы цитирований в юридическом
поиске.

### 3.3 Действие человека — для продукта самый выгодный

Оператор открывает карточку документа и нажимает «связанные документы». Система целенаправленно ищет по
номеру, издателю, датам, упоминаниям. Триггер — не пакетный прогон, а конкретный рабочий вопрос; стоимость
платится только там, где она нужна, а точность видна сразу.

### 3.4 Запрос — ленивый режим (как в LazyGraphRAG)

Связи строятся в момент вопроса, если без них вопрос не решается. Дорого на каждый запрос, зато нулевая
стоимость на документах, к которым никто не обращается.

### 3.5 Отдельно: изменение разметки

Метаданные и индексы впереди графа (идея владельца 10.10.2026). Новая разметка — вид, тема, фасет,
издатель — это тоже триггер: изменил разметку документа → пересчитал его документные связи, **не трогая
фрагментный граф**.

## 4. Что предлагаем закладывать в продукт (по возрастанию цены)

1. **При загрузке**: правила по идентификаторам (номер, вид, издатель, даты) + один узкий вызов модели по
   «шапке» документа. Даёт связи «взамен», «во исполнение», «приложение к» и, главное, «документ A
   ссылается на документ B» по номеру. Сюда же — уже существующий слой правил по стандартам и пунктам.
2. **При изменении разметки**: пересчёт документных связей одного документа.
3. **По действию человека**: кнопка «связанные документы» в карточке документа; добирает то, что пропустили
   первые два триггера.
4. **По запросу**: редкий режим для вопросов, которые без документных связей не решаются.

**Чего делать не следует**: массовый прогон всего корпуса «ради связей между документами». Он не улучшает
точность таких связей (они либо есть в тексте, либо их нет), а стоит как весь фрагментный граф.

## 5. Что честно остаётся нерешённым

* «Является приложением» и «отменяет» часто не написаны в тексте, а подразумеваются по номеру и дате —
  правила будут ошибаться. Без человека не обойтись: либо проверка оператором, либо пометка
  **«предположение»** вместо факта (в происхождении это отдельный слой, не `regex` и не `model`).
* Документы без идентификаторов (письма, служебные записки) по номерам не свяжутся — только по упоминаниям
  и датам, точность ниже.
* Масштаб: при 10 тысячах документов сопоставление по номерам — индекс, не страшно; при 50 тысячах ту же
  схему надо проверять отдельно (второй этап развития).

## 6. Что это значит для продажи

Формулировка «любой документ, который мы формируем, опирается на законность других документов» требует именно
документного слоя. Поэтому в поставке нужно разделять три класса связей:

| Класс | Как получаем | Как показываем |
|---|---|---|
| Гарантируем | Сопоставление по идентификаторам + разбор ссылок в тексте | Как факт, с фрагментом-источником |
| Помечаем предположением | Вывод модели по «шапке» документа | Как предположение, с возможностью подтвердить или снять (журнал действий) |
| Не берём | Связи, требующие внешнего знания вне корпуса | Не показываем |

## 7. Ближайшие шаги

1. Проверить, сколько документов корпуса вообще несут идентификаторы (номер, вид, издатель, дата) — от этого
   зависит доля связей, которые мы можем гарантировать. Это дешёвый замер по метаданным.
2. Написать правила сопоставления по идентификаторам и посмотреть точность на реальных парах
   («взамен», «во исполнение»), как мы делали для словаря связей.
3. Кнопка «связанные документы» в карточке — после того, как есть что показывать.

## 8. Первый замер (11.10.2026): сколько документов вообще несут идентификаторы

Прогнал по текущему корпусу (296 документов), по распознанному заголовку:

| Признак | Документов | Доля |
|---|---|---|
| Всего | 296 | 100% |
| Есть идентификатор (ГОСТ/СТО/№/приказ/постановление/указание/инструкция/положение/регламент/правила) | 57 | 19% |
| Есть номер (знак «№») | 26 | 9% |
| Стандарты (ГОСТ/СТО) | 25 | 8% |
| Акты (приказ/постановление/указание/распоряжение/письмо) | 18 | 6% |
| Без распознанного названия | 3 | 1% |

**Важная оговорка, без неё цифра обманчива.** Корпус неоднороден и это тестовая свалка: в нём есть счёт на
оплату хостинга, распоряжение губернатора, статистический бюллетень Банка России — и ноты («Соната для
фортепиано № 14»). Ноты и счета попали в выборку «с номером» и искажают обе стороны измерения.

**Что из этого следует.** На реальном документообороте заказчика (приказы, стандарты, регламенты,
инструкции, положения) идентификатор есть у почти каждого документа, поэтому доля гарантируемых связей
будет высокой. На нашем текущем корпусе измерять бессмысленно — сначала нужно вычистить посторонние
документы или считать по размеченным видам, а не по всему массиву. Это отдельный маленький замер по полю
вида документа, когда словарь видов утверждён.
