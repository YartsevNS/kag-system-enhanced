## 1. Что это за проект и для чего он делается

KAG — self-hosted система работы с документами: загрузка → распознавание (OCR) → табличный слой →
векторный поиск → граф знаний → чат по найденным фрагментам с цитированием источника.

**Главное, что нельзя забывать: проект разворачивается у заказчика, в чужих сетях, на другом
оборудовании.** Поэтому сборка идёт образами (реестр kre44et), все настройки — в админке
(config_store), внешний адрес задаётся после развёртывания (см. §6), веса моделей вшиты в образ, а
интернет при работе не требуется. Всё, что мы делаем, должно переживать переезд и передаваться как
артефакт: образ + настройки + документация, а не как «работающая сейчас инсталляция».

## 5. Процедуры

**Сборка и выкат** (подробно — `docs/guides/deploy.md`):
1. изменения в git → `git push origin paddle-ocr`;
2. на стенде: `git fetch` в сборочное дерево `/home/yartsevn/kag-build-new` (detached на origin/paddle-ocr);
3. при изменении requirements/весов/Dockerfile базы — сначала `kag-base` (образ собирается из
   `docker/base/Dockerfile`, веса детекторов берутся из `assets/models/` — каталог в build-контексте,
   в .gitignore), затем тонкие `kag-api`/`kag-worker`/`kag-mcp`; FROM в трёх Dockerfile и теги в
   `/home/yartsevn/kag-system/docker-compose.yml` обновлять В GIT до сборки;
4. `docker-compose up -d --force-recreate --no-deps api worker worker-maintenance mcp-server`
   (без `--no-deps` пересоздаются postgres/redis/qdrant — была такая грабля);
5. проверка: `curl localhost:8000/api/v1/health` → 200, `docker ps` — все healthy, и что новый код в
   контейнере (`grep` по файлу), потому что образ мог собраться не из того коммита.

**Переезд в другую сеть** — встроенный кейс: внешний адрес вводится в админке и применяется к Keycloak
(`PUT /api/v1/admin/models/system-config` → система прописывает `KC_HOSTNAME` и переключает Keycloak из
dev mode в prod mode). Правки redirect URIs руками НЕ требуются. После переезда проверить: сайт и
`/architecture` по новому адресу, вход SSO, отсутствие редиректов на старый адрес, `/metrics` наружу не
опубликован.

**Откат**: теги-наборы в реестре + офлайн-архив прежнего OCR (`C:/VSCODE_PROJECT/docker arhiv/`,
подробности — в память и в `docs/guides/deploy.md`).

## 6. Что уже сделано и чем это подтверждено

Все решения принимаются ЗАМЕРОМ, а не репутацией. Инструменты и цифры — `scripts/bakeoff/README.md`.

- OCR: PP-OCRv5 вместо прежнего движка (Apache-2.0, без torch), служба на 41 + локальный запасной путь.
- OpenVINO FP32: 1,6–2,35× без изменения цифр (принято). INT8 распознавателя: медленнее и теряет цифры
  (отклонено). Батч ячеек: медленнее (отклонено). INT8 детекторов: точность держится, взят ради размера.
- Таблицы: числовые — своя сетка по линиям (27×20 на накладной); прозаические — детектор ячеек
  (конспект 13611481-3: 38 строк → 5×3, quality 1.000). Маршрутизация по признаку, а не «один движок».
- Схема стенда — страница сайта `/architecture` (открыта без входа, ссылка в левом меню всех страниц).

## 7. Границы применимости и открытые хвосты (не забывать!)

- Пороги признака «числовая/прозаическая» калиброваны на ПЯТИ страницах → на корпусе заказчика
  перепроверить. Это важнее железа: железо влияет на скорость, корпус — на точность.
- Детектор ячеек: 2 страницы из 6 дали плохой результат (1×7; таблица не найдена) — не «работает везде».
- Все выводы по INT8/батчу условны для Broadwell (нет AVX-512/VNNI) — на новом CPU перемерить
  (`scripts/bakeoff/`: `int8_hypothesis.py`, `openvino_and_batch.py`, `cell_int8_test.py`).
- Server-распознавателя для кириллицы не существует (только mobile) — точность брать не размером модели,
  а разделением движков, дочитыванием ячеек и дообучением своей mobile-модели.
- Отложено владельцем: модуль съёмки с телефона (`docs/tech-debt.md` п.10).
- `docs/README.md` долго был устаревшим (23.08.2026) — обновлён вместе с этой картой.
