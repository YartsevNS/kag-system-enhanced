# ADR-010. Ядро и доменные модули в одной базе TypeDB (мульти-доменная онтология)

Статус: предложено (ждёт утверждения владельца)
Дата: 2026-11-15
Связанные документы: `docs/changes/2026-11-15-yadro-moduli-vyravnivanie/`

## Контекст

Проект перестал быть одно-доменным. Помимо информационной безопасности (`sec`) появляется
второй домен — информационные технологии (`it`), и дальше доменов будет больше. Требуется
универсальный принцип: единый нейминг, единая нумерация сущностей внутри домена, возможность
связывать требования разных доменов между собой.

Ограничения платформы (проверено по документации TypeDB):

- базы TypeDB полностью изолированы: «No operations or data can cross between them» —
  транзакция работает с одной базой, кросс-базовых запросов нет
  (typedb.com/docs/core-concepts/typedb/databases);
- `@abstract` в TypeDB 3 означает только «тип не инстанцируется» и НЕ навязывает подтипам
  контракт (non-infectious abstractness): гарантировать «у каждого требования есть ключ»
  схемой сейчас нельзя, это делает конвейер валидации
  (typedb.com/docs/academy/9-modeling-schemas/9.8-abstract-contracts);
- подтипы умеют переопределять наследуемые владения и роли через `owns X as Y`,
  `relates r as s` — это механизм специализации ядра без копирования типов
  (typedb.com/docs/reference/typedb-2-vs-3/process);
- рекомендации по неймингу: сущности, роли, атрибуты — существительные; связи — отглагольные
  существительные; функции — по тому, что возвращают (typedb/typedb-skills, modeling.md).

Текущая схема — монолит под один домен: `security_requirement`, `security_measure`,
`cii_object` — конкретные типы с доменным именем; абстрактные есть только у документа и
`identified_entity`. Роли связей привязаны к конкретным типам домена, поэтому ИТ-требование
не может участвовать в тех же связях, что и требование по безопасности. Идентичность
требования — `sha256(текст)`, что не даёт сравнивать версии документов.

## Решение

1. **Одна база, много модулей.** Все домены живут в одной базе TypeDB. Физическое разделение
   баз допускается только по требованию заказчика; тогда появляется внешний федеративный
   слой, и выравнивание переезжает туда. По умолчанию — модули в одной базе.

2. **Ядро — абстрактные типы (контракты) без доменных имён:**
   `document`, `clause`, `requirement`, `control`, `version`, `evidence`, `alignment`.
   Ядро держит общие атрибуты (`key`, `text`, `valid_from`, `valid_to`, `ordinal`) и роли связей.

3. **Домен — префикс в имени типа.** Доменные типы — подтипы ядра:
   `sec_requirement sub requirement`, `it_requirement sub requirement`,
   `sec_measure sub control`, `it_control sub control`.
   Префикс — единственный признак домена; связям и ролям доменный префикс не нужен.
   Добавление домена = новый файл модуля схемы, ядро не правится.

4. **Единая нумерация внутри домена (универсальные правила ключей):**

   | категория | правило ключа | пример |
   | :-- | :-- | :-- |
   | документ | `домен:издатель\|вид\|номер` (нет — `домен:kag:<uuid>`) | `sec:fstek\|приказ\|17` |
   | структурный узел | `документ + structural_path` | `sec:fstek\|приказ\|17#7.7.1.5` |
   | требование | `документ + structural_path + порядок` | `…#7.7.1.5#3` |
   | мера/контроль | `домен:код` (нормализованный) | `sec:авз.1`, `it:ac-2` |
   | редакция | `документ + версия` | `…#ред-2` |
   | регулятор/орган | `домен:код органа` (`issuers`) | `sec:fstek` |

   `ent-key` = `<тип>:<sha1(правило ключа)>`; домен входит в ключ, поэтому `авз.1` в `sec`
   и `ac-2` в `it` не сталкиваются, а одно и то же значение в разных доменах — разные объекты.

5. **Слой выравнивания — данные, не код.** Связь `alignment(source, target, kind, confidence)`
   с `kind ∈ {exact, close, related}`; маппинги хранятся YAML и загружаются в граф.
   Новый домен приносит свои маппинги, не меняя ядро.

6. **Валидация контрактов — в конвейере.** Так как TypeDB 3 не навязывает контракт подтипам,
   обязательность атрибутов и допустимые роли проверяются функциями проверки (у нас уже есть
   `_integrity_in_tx` и локализация конфликтов) и на записи (guard'ы), а не только схемой.

## Последствия

- Схема переезжает в модули: `src/ontology/core.tql`, `modules/sec.tql`, `modules/it.tql`,
  сборка — конкатенация + проверка на дубли имён. Позже — генерация из YAML.
- Существующие данные мигрируются: `security_requirement` → `sec_requirement`,
  `security_measure` → `sec_measure`; ключи пересчитываются по новым правилам, со сверкой
  множеств до/после.
- Контур «документ компании → покрытие требований → новая версия» строится поверх ядра и
  одинаков для любого домена: в нём участвуют `clause`, `requirement`, `document`,
  `version`, `evidence`.
- Проверки: запрос по абстрактному `requirement` должен возвращать требования всех доменов;
  добавление нового домена не требует правки ядра и не меняет существующие запросы.

## Что НЕ меняется

Слои Bronze/Silver/Gold, нормализация, блокировка, дедупликация, guard'ы, очередь разбора,
страница очереди, порядок «детерминированное до модели». Меняется организация схемы,
идентичность требования и добавляется выравнивание.
